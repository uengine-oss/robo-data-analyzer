## 실험 A — LLM 값 실행 (머릿속 실행)

| 케이스 | 정답 | 결과 | 비고 |
|---|---|---|---|
| VIP (100→80) | ret 80, UPD 80, log(1,20) | **3/3 정답** | |
| 일반 (250→250) | ret 250, UPD 250, log(2,0) | 2/3 | 1회 log 호출을 "미실행(null)"로 오답 |
| **음수 (−50 VIP)** | v_final=−40<0 → **ret −1, UPD·log 미실행** | **0/3 전패** | 3회 모두 동일 오답: ret −40 + UPD −40 실행 + log(3,10) — 가드(IF v_final<0) 누락 + 부호 오류 |
| checksum (C 루프 산술) | 1·4+2·5+3·6=32 | 3/3 정답 | 순수 산술은 맞춤 |

**판정: 합격선 미달 (4케이스 중 2케이스 실패).** 핵심 발견 2개:
1. 실패 지점은 산술이 아니라 **분기 가드 적용** — 정확히 우리 분기표가 결정론으로 못 박는 그 부분이다.
2. **오답이 3회 반복 간 완전히 동일** — 다수결·재시도로 걸러지지 않는, 가장 위험한 형태의
   "일관된 자신 있는 오답". 문서 §3의 주장("그럴싸한 이야기 + 틀린 숫자") 실증.
   단, 순수 산술 루프(checksum)는 맞았다는 것도 정직하게 기록한다.

## 결론 (사전 등록 예상과 대조)

1. **예상 적중**: 파이썬 subset 최상위(파싱 100%·재현 100%), KDM·SBVR 환각 다발 탈락.
2. **예상 밖(정보량 최대)**: ① 판독(Q3) 문항에서 치명 환각 2건 — "KDM=한국기계규격협회",
   "S-FEEL=에어컨" — 지식이 얕은 표준은 읽기조차 위험. ② Gherkin이 명시 제약("코드 리터럴만")
   아래서도 3/3 값을 창작 — **EXAMPLE 값을 모델에 맡기면 안 된다는 기존 결정(결정론 합성)의 직접 실증**.
3. 커스텀 JSON 폐기(대조군) — 결론은 파이썬 subset 단독으로 성립: **"모델이 이미 아는
   표기(파이썬) + 짧은 선택형 출력"이 실측 최적점.** 다른 표준 표기로 갈아탈 근거 없음.
4. **이번 성공과 과거 실패는 모순이 아니다 — 재는 것이 달랐다.** 이번 시료는 20줄·분기 2개·
   출력 ~100tok 단건이고, 이 규모에선 GPU가 항상 잘한다("가상 코드로는 되던데" 관찰과 동일).
   과거 실패는 규모에서 났다(행 4,100·긴 자유 출력·동시 64콜 → 반복 폭주·붕괴·오염).
   폭주의 원인은 파이썬 문법의 까다로움이 아니라 **긴 자유 문자열 생성 자체의 디코딩 불안정**이며,
   그래서 refs 와이어(출력=번호 몇 개, 자유 문자열은 nl 한 문장)가 위험 표면을 없앤다.
5. 값 실행: 장난감 산술은 되나 분기 가드에서 일관 오답(0/3 동일 오답) — 실전 산수(긴 소수·절사·
   반복 복리)는 미검증 영역으로 남김(2차 실측은 사용자 중단 지시). "값은 LLM에 못 맡긴다" 결론 불변.

## 3차 — 자유 파이썬 생성 규모 실측 (실제 코퍼스 함수, 분기표 대조)

"잠깐, 파이썬 제대로 되는 거 아님?"에 대한 직접 답. 실제 함수 2개(소형 42줄 / 대형 534줄·기대 행 60)에
자유 파이썬 규칙 생성([{line, cond, then}])을 시키고 분기표와 기계 대조. 각 3회.
운영과 달리 한 콜 통짜(스트레스 상한) — 단, 과거 CSV·then-union 실패는 행 배치 상태에서도 났음을 병기.

| 함수 | 행 커버리지 | cond 파싱 | then 파싱 | 재현율 |
|---|---|---|---|---|
| b100 (기대 6행) | 4/6 — in-branch return 2행 누락 | 4/4 | **3/10 (70% 파싱 불가)** | 3회 완전 동일 |
| b140 (기대 60행) | **40/60 — 20행(33%) 조용히 누락** + 과잉 7 | **32/47 (32% 파싱 불가)** | **46/111 (59% 파싱 불가)** | 3회 완전 동일 |

판정:
- **규모 열화 곡선 실측**: 20줄 시료 완벽 → 42줄 실제 함수부터 then 70% 파싱 불가 →
  534줄에선 의무 행의 1/3이 **조용히 증발**. 폭주(반복 루프)는 6k 토큰 단건에선 미발생 —
  이번 붕괴는 디코딩이 아니라 **품질(누락·비파이썬 출력)** 축이다.
- 파싱 불가의 주범 = **C 잎사귀의 파이썬화 실패**(`itf->out` 의 `->`, 매크로 등) —
  모델 스스로도 C 조각을 파이썬으로 못 옮긴다. F("원문") 보존 결정의 직접 실증.
- 누락 20행은 오류 신호 없이 사라진다 — refs 와이어가 행을 **미리 열거해 강제**하는 이유
  (출석부 회계가 잡는 바로 그 사고 유형).
- 3회 완전 동일(결정론 디코딩) = 재시도·다수결로 못 거르는 일관 누락.
- 종합: "파이썬 표기를 안다"(1차)와 "실전 함수에서 파이썬만으로 된다"는 다르다 — **후자는 부정됨.**
  현행 구조(행 강제 + refs + F(원문) + nl)가 세 실측 모두에서 유일하게 살아남는 조합.

## 4차 — 공정 조건 재실측: 지침 강화 + 운영식 행 배치 ("지침 강화해도 똑같음?")

사용자 반론 2건 반영: ①운영은 행을 배치로 쪼갠다(747콜/416함수) ②지침이 약했다.
→ 분기표에서 행 목록을 10행씩 배치로 명시 제공(커버리지 강제) + 변환 규칙 명시
("`->`는 `.`로, 절대 `->`를 남기지 마라 / strncpy는 대입 / ast.parse 가능해야" 등). 각 3회, 21콜.

| 함수 | 행 준수 | cond 파싱실패 | then 파싱실패 | `->` 잔존 | 재현율 |
|---|---|---|---|---|---|
| b100 | 18/18 (강제됨) | 0% | **67%** (통짜 70%와 동일 수준) | 0 | 3회 동일 |
| b140 | 180/180 (강제됨) | 27% (통짜 32%) | **80% (통짜 59%보다 악화)** | **79건 — "절대 남기지 마라" 명시 지침 위반** | 배치 2/6만 동일 |

판정:
- **행 누락은 사라졌다 — 단, 그건 지침이 아니라 "행 목록을 결정론이 만들어 강제"한 효과**다.
  즉 쪼개기 반론은 현행 구조의 절반(분기표 행 열거)을 빌려야 성립한다.
- **잎사귀 파이썬화는 지침 강화로 안 고쳐졌다**: 단순 비교식(cond)은 원래 잘 되고,
  효과문(then — C 대입·매크로·가변 인자)은 67~80% 파싱 불가, 명시 금지한 `->`가 79건 잔존.
  실패가 몰리는 곳이 정확히 F("원문") 보존 + 효과 분류(call/set/ret)가 맡는 자리다.
- 배치 조건에선 재현율도 깨진다(6배치 중 2개만 3회 동일) — 재시도 다양성은 늘지만 품질은 그대로.
- **결론: "지침 강화해도 똑같음?" → then 축은 같거나 더 나쁨. 자유 파이썬 노선 최종 기각.**

## 5차 — 모델 교체 실측: gpt-5.4-mini (OpenAI 직통, reasoning_effort=none)

"모델을 바꾸면 되나?"의 답. v3와 동일 조건(행 배치 + 지침 강화) 21콜.
**채점기 교정 병기**: 종전 채점기가 eval 전용이라 지침이 허용한 대입문을 오판 — 대입 인정으로
교정 후 GPU도 재채점(아래 수치는 교정판, 원본 jsonl 로 재검증 가능).

| 지표 (b140) | GPU(qwen 로컬) | gpt-5.4-mini(추론 끔) |
|---|---|---|
| 행 준수 | 180/180 | **150/180** (3콜 JSON 미완·잘림) |
| cond 파싱실패 | 27% | 35% |
| then 파싱실패 | **57%** | **60%** |
| `->` 잔존 | 79 | 0 |
| 배치 3회 동일 | 2/6 | 0/6 |

**실패 4분류 (양 모델 공통 — 파싱 불가 then 330여 건 전수 집계):**
1. `return RC_ERR` (양쪽 최다 66~72회) — 표기 규약 부재: ret() 관례를 가르치지 않으면 모델은
   자연스러운 `return`을 쓰고, 이는 식 표기가 아니다. "같은 뜻 여러 표기" 문제의 실물.
2. **`itf.in.pay_mthd_cd` 류 — 파이썬 예약어 충돌 (`in` 은 키워드라 `.in.` 은 문법 위반).**
   레거시 식별자가 파이썬 키워드와 충돌하는 경우로, **어떤 지침·모델로도 원리적으로 못 피하고**
   개명하면 원문 왕복성이 깨진다. F("원문") 보존의 결정적 실증.
3. 따옴표 소실(`PFM_MSGE(T_S, ZNGME0000, %T%s, ...)`)·`&` 잔존·자연어 혼입
   (gpt가 then에 "prepare ... and copy input fields" 문장을 출력) — 자유 생성의 훼손/창작.
4. gpt 3콜은 4096tok 잘림으로 JSON 미완 — 배치로 쪼개도 출력 상한 관리가 또 하나의 축.

**판정: 모델을 갈아도(추론 꺼도) 본질 동일 — 잎사귀 파이썬화 실패는 모델 급이 아니라 과제 구조의
문제다.** (미검증으로 남김: reasoning 켠 gpt — 단 그 경우 비용·시간이 분석 규모에서 비현실적)

## 6차 — 생존 형식 표기법 DRL 규모 실측 (Gherkin은 자연어 표기라 사용자 지시로 제외)

blind에서 유일하게 합격권이던 형식 표기(DRL)를 같은 공정 조건(행 배치+지침, 운영 GPU, 21콜)으로.

| 지표 | b100 | b140 |
|---|---|---|
| 행 커버(L줄번호 블록) | 18/18 | 180/180 |
| when/then 구조 결손 | 0 | 0 |
| `->` 잔존 | 0 | **87 (파이썬 때 79보다 많음)** |
| **따옴표 밖 자연어(주석 탈출) 블록** | 0 | **78/180 (43%)** |
| 배치 3회 동일 | 0/1 | 0/6 |

**핵심 발견 — 내용의 형식 밖 탈출**: 모델이 형식(rule/when/then/end)은 100% 지키면서,
어려운 조건은 `when eval(true)`(항상 참)로 비워 두고 실제 조건을 **주석으로** 밀어냈다:
```
when eval(true) then // 조건: tmth_drw_yn ==  AND gc_drw_yn ==
```
비교 값까지 소실된 채로. 즉 표기법 준수율이 높아 보일수록 내용은 채점 불가능한 곳(주석·자연어)으로
숨는다 — "그럴싸한 가짜"의 심화형. 파이썬 잎사귀 문제(`->` 87)도 그대로 남는다.

**최종 종합 (1~6차)**: 형식 표기법 전 후보 실측 완료 — 파이썬 subset(잎사귀 실패·예약어 충돌),
DRL(내용 탈출·잎사귀 동일), 기타(환각·자연어) 전부 기각. 살아남는 조합은 하나:
**행 강제 열거(결정론) + 보기 선택(refs) + 잎사귀 원문 보존(F) + 자연어는 nl 한 층** = 현행 구조.

## 7차 — "의미-파이썬" (사용자 제안 2026-08-05): 코드 변환이 아니라 의미 요약을 파이썬 표기로

제안의 정확한 내용: nl(의미 요약 층)의 표기를 자연어 문장 대신 **모델이 판단한 의미를 파이썬
표기 한 줄**로. 기계 검증층(cond/then refs)은 불변이므로 보증 손실 없음 — nl과 동급 성질
(의미 재량 → 사람 표본 검증). 운영 GPU, 행 배치, 각 3회, 21콜.

| 지표 | b100(단순) | b140(복잡) |
|---|---|---|
| 행 커버 | 18/18 | 180/180 |

## 10차 — 관계 등식 추출 ("이해한 관계를 파이썬 등식으로" — 사용자 의도 정조준)

코드를 읽고 이해한 **결과 관계**를 자연어 대신 파이썬 등식으로: 할인/입금/체크섬 시료 3종
(관계 정답 사전 정의), json_schema 강제, 각 3회.

실물 (전부 모델 출력 그대로):
```
given: v_type == 'VIP'      then: v_final == v_amount * 0.8
given: in_amt > 0           then: acct.balance_after == acct.balance + in_amt - fee
given: in_amt > 0           then: fee == in_amt / 100
given: v_final >= 0         then: log_discount_인자 == v_amount - v_final
루프:  i_Sum_after == i_Sum + atoi(w2[li]) * atoi(w1[li])   ← 반복을 단계 관계식으로
```

| 시료 | 관계 의미 정확(3회) | 파싱 | 값 창작 |
|---|---|---|---|
| discount | **3/3 전부 정확** (가드 `v_final<0 → ret==-1` 포함) | 100% | 0 |
| deposit | 3/3 정확 | rep1만 `acct->` 2건 실패, 이후 100% | 0 |
| checksum(루프) | 3/3 정확 — 루프를 불변식형 단계 관계로 | 100% | 0 |

**핵심 발견**: 2차 값 실행 실험에서 3/3 틀렸던 바로 그 가드(`v_final < 0`)를, 관계식으로 시키니
3/3 정확히 뽑았다 — **LLM은 값 계산은 못 하지만 관계 추출은 잘한다.** "값 포기 + 관계 표현"이라는
사용자 방향이 모델 능력의 결과 축과 정확히 일치함이 실측됨.

정직한 한계: ①시료가 소형·정갈(복잡 실코드 b140 급에서는 7·8차의 24~50% 후퇴 위험 미해소 —
관계식 프레이밍으로 재실측 필요) ②표면 변주 잔존(인자 명명·슬라이스 표기 — 문자열 동일 비교는
불가, 정규형·심볼 대조 수준의 결정론 비교는 가능) ③관계 정답지는 이 실험에선 수제 —
운영에선 파싱·어휘 폐쇄·심볼 대조 + 사람 표본이 검증 수단(nl과 동급).

## 14차 — rel 의미 정확도의 골든셋 측정 (사용자 설계: 표본 정답지 직접 구축 → 결정론 대조)

방법: 분석자가 소스를 읽고 표본 행의 **정답 rel을 직접 작성**(골든셋, 같은 표기 규약) →

|---|---|
| 정규형 완전 일치 | **8/12 (67%)** |
| 불일치 | 4/12 |

불일치 4행의 실패 유형 (전부 교훈적):

깊이·누적) — 지침 보강 + 재요청으로 공략 가능한 표적. 다음: 골든셋을 표본 20함수 전체로 확장
