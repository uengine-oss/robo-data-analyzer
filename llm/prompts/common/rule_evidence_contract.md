## RULE / EXAMPLE / QUESTION 핵심 증거 계약 — 모든 언어·도메인 공통

이 절은 아래의 세부 작성법보다 우선한다. 프로젝트명·언어 문법·산업 관례가 아니라 현재 루틴의
활성 본문, 주입된 심볼 값, 직접 읽기/쓰기, 명시된 외부 근거만 사용한다.

## 누락 방지 결정 절차

다음 순서로 Rule 후보를 먼저 완성하고 그 뒤에만 문장과 Example을 쓴다.

1. SOURCE의 무조건 주동작·위임·변환·반환을 위에서 아래로 적는다.
2. `branch_index`/`CONTROL_FLOW_INDEX`의 각 decision·complement를 SOURCE와 대조하여,
   서로 다른 호출·반환·상태·외부 I/O·후속 진행 결과를 적는다.
3. 오류 후 종료뿐 아니라 오류를 무시하고 계속함, 변경 없이 통과함, 성공 여집합, default를
   별도 관측 결과로 회계한다.
4. 반환·저장·전송·외부 호출의 인자로 이어지는 키·메시지·레코드 조립을 최종 소비 지점까지
   추적한다. 작업용 임시값인지 외부 결과의 일부인지 이름이나 연산 종류로 추측하지 않는다.
5. 각 후보를 정확히 한 Rule이 담당하는지 확인한다. 같은 조건과 같은 결과만 합칠 수 있다.
   여러 독립 단계나 서로 다른 분기를 한 개의 “전체 처리” Rule로 압축하지 않는다.
6. Rule 목록을 모두 확정한 뒤 각 Rule에 대표 Example을 하나씩 만들고 마지막에 Question을
   판정한다.

- 잘못: 여러 승인·거절·전송 분기를 “요청을 검증하고 조건에 따라 후속 처리를 수행한다” 한
  Rule로 축약.
- 좋음: 승인, 거절, 전송, 전송 생략처럼 호출자가 구별하는 조건과 결과를 각각 복원 가능한
  Rule로 작성.
- 잘못: 조회 실패 분기가 `return`하지 않는다는 이유로 삭제.
- 좋음: 조회 실패 시 기본 상태를 유지하고 다음 단계로 계속한다면 그 무변경·계속 계약을 기록.

## 외부 결과로 이어지는 데이터 조립

복사·패딩·연결·마스킹·인코딩·직렬화 자체가 언제나 내부 구현인 것은 아니다. 만들어진 값이
반환 객체, 출력 파라미터, 저장 레코드, 메시지, 조회 키, 외부 호출 인자로 이어지면 그 최종
관측 결과와 값 구성 규칙은 Rule 후보이다. 최종 소비와 연결되지 않는 지역 작업 버퍼만 제외한다.

- 잘못: 고정 길이 전송 레코드의 필드 배치와 공백 패딩을 “버퍼 조작”이라며 모두 생략.
- 좋음: 각 입력을 정해진 폭으로 배치하고 남는 자리를 공백으로 채운 레코드를 전송한다고 작성.
- 잘못: 지역 문자열 둘을 합쳤다는 사실만으로 외부 검색 키를 만든다고 주장.
- 좋음: 합친 값이 실제 조회 호출의 키 인자로 전달되는 SOURCE가 있을 때만 조회 키 구성을 기록.

## 성공·무변경·실패 후 계속

거절 조건의 부정이나 여집합이 곧 허용 조건이면, 거절 Rule만 쓰고 허용 계약을 숨기지 않는다.
여러 대체 입력 중 하나만 있어도 통과하는 검증은 “모두 없을 때 거절”과 “하나 이상 있으면
통과”를 Example에서 검증 가능하게 보존한다. 실패를 잡아 기본값으로 진행하거나 아무 변경 없이
계속하는 경로도 현재 루틴이 직접 정한 결과다.

- 잘못: 이메일·전화·회원번호가 모두 없을 때 거절한다고만 쓰고 어떤 대체 입력이 허용되는지 생략.
- 좋음: 세 값이 모두 없으면 거절하고, 셋 중 하나 이상 있으면 다음 단계로 진행한다고 작성.
- 잘못: 선택 조회 실패를 일반 오류 반환으로 바꾸거나 실패 경로 자체를 삭제.
- 좋음: 실패 시 상태를 `UNKNOWN`으로 두고 후속 처리를 계속한다면 그 결과를 그대로 작성.

0. **Rule은 관측 가능한 루틴 계약**: 조건 분기뿐 아니라 주요 무조건 변환·위임·I/O·상태 변경,
   반환 계약도 Rule 후보이다. 제거했을 때 호출자·사용자·외부 데이터가 관측하는 결과가 달라지면
   의미가 있다. 임시변수 대입·로그 문구·버퍼 조작처럼 외부 계약을 따로 만들지 않는 내부 단계만
   독립 Rule에서 제외한다.
   - 잘못: "분기가 없는 단순 변환"이라는 이유로 입력을 정규화해 반환하는 주동작까지 `rules:[]`.
   - 좋음: "입력을 정규 형식으로 변환해 반환한다"를 한 Rule로 쓰고 내부 임시버퍼 대입은 생략.
   - 잘못: 하위 호출 실패와 대상 없음이 서로 다른 반환값인데 둘 다 기술 오류라며 삭제.
   - 좋음: 활성 본문이 구분해 내보내는 정상·오류·대상 없음 결과를 각각 보존.
1. **조건 방향과 범위 보존**: 부정, AND/OR, 바깥 가드, `else/default`의 여집합, `>`/`>=`,
   `<`/`<=`를 바꾸지 않는다.
   - 잘못: 실제로 "사용 불가가 아니면 허용"인데 "사용 불가이면 허용"으로 부정을 제거.
   - 좋음: 부정과 바깥 조건을 함께 유지해 도달 가능한 경우만 규칙으로 작성.
2. **종료 계약 분리**: 정상 반환, 업무 오류, 조기 종료, 대상 없음(no data), 변경 없이 통과,
   fallback을 서로 합치거나 생략하지 않는다.
   - 잘못: 정상·대상 없음·오류를 모두 "처리 결과를 반환한다" 한 사례로 합침.
   - 좋음: 활성 본문에서 관측 결과가 다른 각 경로를 독립 Example로 보존.
3. **활성 코드만 사실**: 주석 처리되거나 비활성인 예전 코드는 현재 Rule/Example이 아니다.
   - 잘못: 주석 블록의 옛 경곗값과 반환값을 현재 정책으로 생성.
   - 좋음: 활성 분기에 있는 경곗값과 결과만 사용하고, 주석의 희망 동작은 제외.
4. **호출·필드 소유권 보존**: 자식 호출의 내부 규칙, 다른 필드의 의미, 다른 루틴의 테이블·
   Example을 현재 루틴 것으로 끌어오지 않는다.
   - 잘못: 현재 루틴이 단순 전달만 하는데 호출 대상 내부의 검증 규칙을 복제.
   - 좋음: 현재 본문이 직접 판단한 조건만 Rule로 만들고 위임 자체의 관측 효과만 설명.
5. **값과 fallback 회계**: 결과를 가르는 명시 값, 구별 경계, catch-all fallback은 각각 정확히
   한 번 포함한다. 같은 결과의 값 변주는 집합으로 합치되 값→결과 대응은 유지한다.
   - 잘못: 첫 번째 값만 예시로 쓰거나, 같은 fallback을 표현만 바꿔 여러 번 생성.
   - 좋음: 명시 값 전체와 fallback을 누락·중복 없이 파라미터화해 한 번씩 검증.
6. **QUESTION은 실제 공백만**: 본문·분기·주입 근거에 답이 있으면 질문하지 않는다.
   - 잘못: `else/default`에 답이 있는데 "그 밖의 값은 어떻게 처리되는가?"라고 질문.
   - 좋음: 결과에 필요한 외부 정의가 모든 입력 근거에서 실제로 빠진 경우만 이유와 함께 질문.
7. **지원되지 않은 추가 의미 금지**: 관례, 이름, 도메인 상식으로 상태명·기관·약어·오류 의미를
   만들지 않는다.
   - 잘못: 뜻이 없는 코드 리터럴에 익숙한 업무 라벨을 추측해 붙임.
   - 좋음: 값 표기만 보존하고 뜻이 필요하지만 근거가 없으면 QUESTION으로 드러냄.
8. **연산 범위와 결과 종류 보존**: 길이·부분범위·단위·산술 결과와 정상/대상 없음/오류의
   구별은 활성 SOURCE가 직접 입증한 만큼만 쓴다.
   - 잘못: 길이 인자가 가리키는 범위를 확인하지 않고 부분 복사를 “첫 글자 복사”로 축소.
   - 좋음: 심볼 값까지 입증되면 정확한 범위를 쓰고, 그렇지 않으면 “지정된 범위를 복사”로 유지.
   - 잘못: 하위 호출의 `NOT_FOUND`를 이름이 부정적이라는 이유로 일반 오류로 바꿈.
   - 좋음: 현재 본문이 대상 없음과 오류를 서로 다른 반환으로 보존하면 그 종류를 그대로 유지.
   - 잘못: 용량 부족 분기에서 쓰기보다 `break`/`return`이 먼저인데 “일부 단위를 쓴 뒤
     멈춘다”고 실행 순서를 뒤집음.
   - 좋음: 분기 안의 쓰기·증가·종료 순서를 그대로 따라, 종료 전에 실제 수행된 효과만 서술.
9. **같은 효과 값은 완전하게 그룹화**: 여러 case/분기 값이 같은 활성 효과로 이어지면 해당
   값 집합을 빠짐없이 한 Rule에 묶고, 다른 효과의 값은 섞지 않는다.
   - 잘못: 같은 반환으로 이어지는 `{A, B, C}` 중 첫 값 `A`만 작성.
   - 좋음: `{A, B, C}`가 같은 효과임을 SOURCE로 확인해 한 집합으로 보존.
10. **숫자 결과는 SOURCE 연산으로 검산**: 이름, 순번, 관례만으로 구체 숫자를 만들지 않는다.
    - 잘못: 증가 함수라는 이름과 이전 번호만 보고 최대값이나 증가폭을 계산해 추가.
    - 좋음: 활성 식과 입력 단위가 직접 보일 때만 계산값을 쓰고, 아니면 관측 가능한 증감
      동작까지만 설명.
11. **모든 Rule은 양의 절대 근거 줄을 가진다**: 조건 Rule은 결과를 선택하는 decision/
    complement 줄, 무조건 Rule은 관측 효과를 직접 수행하는 첫 활성 SOURCE 줄을
    `anchor_line`으로 쓴다. 같은 statement가 다른 줄에서 실제 반복되면 별도 발생이지만,
    statement·anchor_line·Examples가 모두 같은 출력은 완전 중복이다.
    - 잘못: 분기가 없다는 이유로 `anchor_line: 0`, 또는 같은 발생을 두 번 출력.
    - 좋음: 무조건 반환은 실제 return의 절대 파일 줄에 한 번 anchor하고, 같은 의미가 다른
      활성 줄에서 반복될 때만 각 줄의 발생을 별도로 보존.

`rules:[]`는 선언·빈 구현처럼 활성 본문에 관측 가능한 동작이나 계약이 실제로 없을 때만 쓴다.
제출 전 무조건 주동작과 활성 분기를 위에서 아래로 다시 대조하여, 서로 다른 관측 결과가 누락되지
않았고 같은 `(Rule + 원문 분기 + 관측 결과)`가 두 번 나오지 않았는지 확인한다.

## 구조 인덱스 회수와 압축 금지

`branch_index`는 요약 참고문이 아니라 누락 검사표다. SOURCE와 함께 위에서 아래로 읽고,
각 `[decision]`·`[complement]`가 만드는 서로 다른 반환·상태 변경·직접 I/O·조기 종료를
어느 Rule이 담당하는지 확인한다. 관측 결과가 다른 두 갈래는 Rule을 합치지 않는다.

다음 표현은 조건과 결과를 그 문장만으로 복원할 수 없으므로 금지한다: “조건에 따라 처리”,
“적절한 값 설정”, “결과 반영”, “오류이면 처리”, “여러 검증 수행”.

값 집합과 결과가 모두 같은 경우에만 한 Rule로 합친다. 합친 Rule 안에서도 모든 명시 값,
부정, AND/OR, 경계, fallback과 값→결과 대응을 쓴다.

- 잘못: “회원 상태에 따라 이용 여부를 설정한다.”
- 좋음: “회원 상태가 `ACTIVE`이면 이용 가능으로, `SUSPENDED`이면 이용 불가로 설정하고,
  그 밖의 상태이면 기존 값을 바꾸지 않는다.”
- 잘못: 정상·대상 없음·오류가 서로 다른데 “조회 결과를 반환한다”로 합친다.
- 좋음: “대상이 없으면 상태를 바꾸지 않고 대상 없음 결과를 반환한다”와
  “조회 오류이면 오류 결과를 반환한다”를 별도 Rule로 둔다.

## Example 수와 길이

먼저 Example 수를 전혀 고려하지 않고 관측 계약별 Rule 목록을 완성한다. 출력 길이·Rule 수·
Example 수를 줄이기 위해 서로 다른 조건·결과·예외를 한 Rule로 합치지 않는다. Rule 목록이
완성된 뒤에만 각 Rule의 Example을 작성한다.

Example은 Rule의 모든 문장을 다시 풀어 쓰는 두 번째 규칙 목록이 아니다. 같은 조건과 같은
관측 결과를 내는 값 집합은 한 Rule과 대표 Example 1개로 검증한다. 조건이나 관측 결과가
다르면 Example을 한 Rule 아래 늘리지 말고 Rule 자체를 분리한다. 값이 많으면 한 사례의
`given`에 실제 전체 집합·매핑을 넣고 값마다 Example을 만들지 않는다.

- 잘못: 같은 결과를 내는 코드 12개를 Example 12개로 반복한다.
- 좋음: 실제 전체 값 집합을 한 `given`에 넣어 Example 1개로 검증한다.
- 잘못: Example을 줄이려고 서로 다른 성공·거절·fallback을 “조건에 따라 처리한다” 한
  Rule로 압축한다.
- 좋음: 성공·거절·fallback을 각각 독립 Rule로 나누고 각 Rule에 대표 Example 1개를 둔다.
- 잘못: 출력이 짧아야 한다는 이유로 서로 다른 관측 계약 12개를 포괄문 3개로 축약한다.
