## TABLE / COLUMN 통합 의미 계약

입력 evidence는 테이블 하나에 대한 원래 스키마 설명과 코드노드별 직접 사용 후보다.
테이블·컬럼마다 자기 근거만 종합하고 다른 테이블·컬럼의 책임을 가져오지 않는다.
`table_usages[*].usage_summary`는 바로 이 테이블의 직접 사용 설명이며 함수 전체 summary가
아니다.

### 근거 우선순위

1. `source_description` / `source_comment`
2. 현재 테이블·컬럼의 직접 사용으로 입증된 후보
3. 위 근거가 말하는 최소 역할

상위 근거와 충돌하는 후보는 버린다. 물리 이름·업계 관례로 기관, 식별자 종류, 단위,
보호 방식, 상태 의미를 만들지 않는다.

- 잘못: 원래 설명이 “횟수 초기화 제외 여부”인데 후보 하나를 따라 “실패 신청 제외 여부”
- 좋음: 원래 설명을 보존하고 직접 사용으로 확인된 맥락만 덧붙임
- 잘못: 암호화된 부분정보를 익숙한 표현이라는 이유로 마스킹 정보로 변경
- 좋음: 근거가 말하는 암호화와 부분정보 범위를 그대로 유지

### TABLE

`description`은 이 테이블이 어떤 데이터를 담고 어떤 업무에서 직접 조회·저장되는지
사용자 친화적인 1~2문장으로 설명한다. 여러 사용 후보를 종합하되 한 함수가 함께 사용한
다른 테이블의 효과를 섞지 않는다.

`logical_name`은 무엇에 관한 데이터인지 구별되는 짧은 명사구다. 마스터·이력·임시·집계
성격은 근거에 있을 때만 붙인다. 근거가 부족하면 빈 문자열이며 물리명을 번역해 꾸미지 않는다.

- 잘못: A에서 상태를 조회하고 B에 원문을 저장한 함수 때문에 A를 “원문 적재 이력”으로 설명
- 좋음: A는 상태 조회 기준, B는 원문 적재 이력으로 분리
- 잘못: 여러 usage_summary 중 첫 문장을 그대로 테이블 전체 설명으로 채택
- 좋음: 서로 양립하는 직접 사용을 종합하고 충돌하는 후보는 상위 source 근거로 판정

### COLUMN

입력 허용 컬럼 이름을 정확히 한 번씩 반환한다. 새 컬럼 생성, 누락, 다른 컬럼 후보 복사는
금지한다. `logical_name`은 표시명, `description`은 저장 값의 의미와 현재 사용 역할이다.
DDL 타입이나 물리 컬럼명 자체를 설명으로 반복하지 않는다.

- 잘못: 소유자 참조값을 이름만 보고 이메일 주소로 좁힘
- 좋음: source가 계정번호라고만 말하면 그 범위를 유지
- 잘못: 날짜를 일시로 확대
- 좋음: source가 날짜면 날짜로 유지

출력은 `TableDescription`의 `db`, `schema`, `name`, `logical_name`, `description`,
`columns:[{name, logical_name, description}]`만 포함한다.
