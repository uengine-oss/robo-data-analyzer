## 5. 실패 계약 (헌법 IV)

**fatal(전체 실패)**: transport 재시도 소진, 필수 AST/DDL/audit evidence 부재, budget 초과,
결정론 불변식 파괴, 저장 계약 파괴. → error log + stream error + raise 전부.

**계속(좌표별 quality finding 격리)**: LLM 후보의 schema/syntax/grounding/semantic 실패,
허용 밖 생성, 출력 상한·반복 가드 작동. → raw/partial/target/evidence/reason 보존,
trusted 파생에서 제외, 독립 작업 계속, 내용 재요청 없음.

## 6. 반복 종료선

1. 모델 내용은 1회 생성 — 내용 오류 재요청 없이 좌표별 finding으로 격리
2. usable output이 전혀 없는 전송 오류만 runner가 최대 3회
3. 같은 공통 원인의 범용 prompt/schema 수정은 1회만 고정 replay — 계속 틀리면
   needs-context / 모델 한계 / 랜덤성으로 기록하고 문구 변형 반복을 끝낸다
4. 성능 후보당 공식 cold 1회(합격 경계가 불명확할 때만 확인 1회 추가).
   변경 없는 cold, 더 작은 고정 row 수, 같은 표현 변형 반복은 하지 않는다
5. 18분대+정확도 통과 후 남은 개선이 서버 변경이나 정확도 교환을 요구하면 성능 루프 종료
6. 주 에이전트도 입력으로 확정 못 하면 서버 성능 탓으로 돌리지 말고 needs-context로 종료

## 7. 책임 경계 (02 요약 — 현재 계약)

**결정론 코드**: AST/DDL 좌표·role 소비 → branch obligation 조립, 원문·물리 식별자 무손실
보존, 심볼 해석 기반 사용자 정의 CALL 연결, 구조적 table R/W, bottom-up DAG/SCC,
required row key 생성, evidence ref 형식·소속 검사, trusted Rule→EXAMPLE 파생,
`obligation = trusted + findings + unavailable` 회계.

**LLM**: 함수 업무 의미 요약, branch별 cond/then 선택(evidence ref), 사람용 `nl`,
테이블 의미 제안, 모르면 모른다고 표면화. 코드는 LLM 누락을 임의로 채우지 않는다.

**Rule wire**: row key는 요청별 required 고정, `cond`=`C../!C..` ref 배열, `then`=`E..` ref
배열, `extra`=희소 권위 효과(제거·then 통합은 반증됨), `nl`=한 문장(제거 불가, 길이 상한은
가능). ref regex는 모양만 닫혀 있고 evidence 값 폐쇄는 후보 ③.

**EXAMPLE**: LLM 생성하지 않는다 — trusted Rule에서 코드가 전수 파생·동등성 검사.
**Summary**: canonical `summary` 하나가 사람 표시·검색·bottom-up 공용(`search_text` 폐기).
purpose-only prompt는 결함 후보(TA-144, 미해결).
**동시성**: concurrency 64 유지, summary 최우선 wake, Rule은 evidence-size LPT.

## 8. AST 구조 사실 계약 (07 — 이번 작업의 본체)

| 사실 | 생산자 | analyzer 책임 |
|---|---|---|
| RETURN/THROW/RAISE + 반환식 | 언어별 listener → AST JSON `expression` | routine·branch 귀속, 의미 미추론 |
| BREAK/CONTINUE/GOTO/EXIT | listener | control-flow 연결 |
| FUNCTION_CALL + 좌표 | listener (기존) | symbol 해석, user/external 분류 |
| ASSIGNMENT 좌·우변 | listener → `target/operator/expression` | 구조 검증만 |
| 분기 조건 | listener → 제어 노드 `expression` (LOOP는 판정절만) | branch path 조립 |
| embedded SQL·외부 문서 | DDL parser·SKILL·전용 lexer (**유지**) | R/W·external 연결 |

종료선: grammar가 못 가르는 구문은 추정 regex를 넣지 말고 지원 한계로 기록한다.
한 언어 통과를 전 언어 통과로 일반화하지 않는다. parser/analyzer 이중 생산을 두지 않는다.

## 10. 리서치 확정 (03 §8.1, 질문↔답변 원장 03 §8.2)

- 요청 수준 공백 제거는 **regex/EBNF로만** 가능(json_schema 경로 불가 — sglang #8250).
  거대 단일 regex보다 **EBNF + 공유 규칙**. 요청별 문법 컴파일 비용은 무시 가능.
- `extra` 1→0 현상은 constrained decoding 분포 왜곡 가설이 유력 —
  공백·nl 상한·enum 폐쇄·field 순서는 **각각 독립 1회 A/B**로 분리한다.
- `{1,N}` 수량자는 **코드포인트 단위**. nl 상한은 schema `maxLength`로 불가(무시됨) —
  regex 수량자만 신뢰. 문자 클래스에서 `\d` 축약은 거부 — `[0-9]`로.
- 고동시성 garbage(#460/#2414)는 문법 크기가 아니라 배치/스케줄러 인프라 문제 계열.
- 서버 실측: Qwen3.6-35B-A3B-FP8, xgrammar, fcfs, radix-lru, SGLang git dev
  `0.0.0.dev1+g9ebffef1e` (`/get_server_info`, Bearer 필요).
- **후보 채택 순서**: ①출력 공백 제거(EBNF) ②nl 길이 상한 ③정수 ID 참조 폐쇄 ④배치 균질화.
  각 단계 합격선(2026-08-05 사용자 확정으로 개정): **trusted 비율 유지 & 인정된(trusted)
  extra 건수 불변**. 옛 문구 "extra 건수 불변"은 기준선 extra 9건이 전부 미인정 환각으로
  실측되어 폐기 — 미인정 extra 감소는 개선이다(03 §8.5-4·5).

## 13.9 parser 타입 변환 전수표 (2026-08-05 사용자 지적으로 조사 — "저장 타입 ≠ 문법 타입")

parser 는 문법 규칙을 그대로 저장하지 않고 의미 타입으로 변환한다. analyzer·감사가
"type = 문법 구문"을 전제하면 틀리는 지점이 있어 표로 고정한다 (C 기준, 전수):

| 저장 타입 | 실제 문법 출처 | 변환 성격 | analyzer 영향 |
|---|---|---|---|
| FUNCTION_CALL | postfixExpression 의 `이름(` 모양 | **모양 기반** — 매크로 호출(`PFM_TRY(...)`)·멤버 호출(`svc->handler()`→name=handler, 수신자 소실)도 포함 | 매크로: macro-drop·skill 로 처리 중. **멤버 호출: 동적 디스패치가 정적 호출로 위장** — 이 corpus 실측 0건, `unsupported_constructs.member_fn_call` 장부 등록(2026-08-05). parser 수신자 보존은 spec 대기 |
| RETURN/BREAK/CONTINUE/GOTO | 단일 규칙 jumpStatement 를 키워드로 분리 | 충실한 세분화 | zero-delta 로 감사됨 — 안전 |
| ASSIGNMENT | ①statement 수준 assignmentExpression ②**선언 초기화**(`int rc = init();`) | ②는 선언 문법→대입 의미 변환(spec 016 의도) | 검증됨. `x = foo();`는 FUNCTION_CALL+ASSIGNMENT **이중 표현**(호출 사실+대입 사실) — 의도된 설계, rule 증거에 call+set 둘 다 실림 |
| GLOBAL_VARIABLE vs MEMBER vs (지역=노드 없음) | declaration 위치로 분리 | 의미 분류 | symbol_kinds 로 소비 — 안전 |
| DEFINE / INCLUDE | 전처리 지시문(HIDDEN 채널) | 토큰 추출 | constant/import 소비 — 안전 |
| IF/ELSE/LOOP/SWITCH/CASE | selection/iteration 규칙 | 세분화(do-while 도 LOOP) | control_roles 소비 — 안전 |

Java/Python 도 동류(NEW_INSTANCE=creator 식, CONSTANT_FIELD=static final 분류 등) —
멤버 호출은 그 언어들의 정상 관례라 장부 제외. 새 변환을 추가할 때는 이 표를 갱신한다.

   - 질문마다 **왜 필요한지와 답에 따라 무엇이 갈리는지**를 붙인다. 답이 진행을 바꾸지
     않는 질문은 하지 않는다.
   - 받은 답변은 03에 **확정 사실**(§8.1 형식)과 **질문↔답변 원장**(§8.2 형식)으로 나눠
     기록한다. 확정 사실에는 근거와 "우리 배포에서 확인 필요" 여부를 함께 적는다.
   - **답을 기다리는 동안 멈추지 않는다.** 그 답에 의존하지 않는 작업을 계속한다.
4. 조사해도 확정 불가면 `needs-context` 또는 `지원 한계`로 기록하고 반복을 끝낸다
   (§6-3, §6-6). 추정을 코드에 넣지 않는다.

이 경로로 이미 두 차례 딥리서치를 받아 03 §8.1~§8.2에 기록했고, 그 결론이 J단계
설계(EBNF+공유 규칙, 양성 유니코드 범위 제외, 축 분리 A/B)를 만들었다.

## 21. 서술 규칙 (2026-08-05 추가)

작업 내용이 아니라 **표현**에 대한 규칙이다. 내용·판단은 바꾸지 않는다.

- 제약은 항상 `허용 / 제한 / 이유` 세 쪽을 함께 적는다. "X 접촉 금지"처럼 범위가
  넓게 읽히는 표현을 쓰지 않는다(실제 오해 사례가 있었다).
- 동작은 정확한 도메인 용어로 적는다: "형식 지정 확인"(확인 호출·강제 아님),
  "test DB에 새로 적재"(전부 지운다 아님), "되돌릴 수 없다"(파괴적 아님).
- 고객 소스 식별자는 필요한 만큼만 적고 나열하지 않는다.
- 격한 표현·감정적 인용을 문서에 남기지 않는다. 요지만 적는다.
