# 05. spec 116 정정표

spec/plan/tasks는 긴 실험 원장을 포함하므로 과거의 완료 체크가 현재 채택을 뜻하지 않는다.
이 문서는 삭제하지 않고 보존해야 할 역사와 현재 계약을 구분한다.

## 1. 현재 권위로 읽을 것

- 헌법 1.3.2의 operational failure / model-quality finding 구분
- 모든 branch row obligation 보존
- 동적 required row key 구조화 출력
- transport retry만 허용
- model candidate 실패의 좌표별 격리와 finding
- trusted Rule에서 EXAMPLE 파생
- cache-off cold 실측과 직접 의미 검증
- 원칙 위반의 tasks 즉시 편입
- parser가 식별 가능한 구조 구문은 AST JSON이 생산하고 analyzer는 소비·검증만 수행
- 내용 1회, transport 최대 3회, 후보별 제한 A/B/cold의 명시적 종료선

## 2. 현재 계약으로 읽으면 안 되는 역사 문구

| 과거 문구/설계 | 현재 판단 |
|---|---|
| 값·객체 추적기 신규 구현 | 전면 폐기. 동적 의미를 고정하고 언어별 유지보수 결함을 만든다. |
| 위치별 마지막 대입을 의미 증거로 사용 | 폐기. source literal/상수와 exact return expression만 허용. |
| cond/then을 arbitrary Python leaf로 모델이 작성 | 현재는 짧은 evidence ref 선택 구조. 임의 언어 번역기로 읽지 않는다. |
| grader가 source 의미를 결정론적으로 완전 비교 | 불가능. 구조/소속/문법/파생 검증까지만 결정론. 의미는 직접 대조. |
| 행 단위 content retry 최대 3회 | 폐기. transport retry만 허용. |
| schema/content 실패면 호출 전체 실패 | 폐기. 좌표별 quality finding으로 격리하고 독립 작업 계속. |
| `search_text` 별도 생성 | 폐기. canonical summary 하나를 사람/검색/bottom-up에 사용. |
| Rule의 `questions`를 항상 생성 | 현재 Rule wire 핵심이 아님. 정보 부족은 finding/명시 계약으로 다룬다. |
| `nl`은 불필요하므로 제거 가능 | 제거 금지. 사람이 의미를 이해하고 semantic review하는 필드. 짧게 강제 가능. |
| `extra`는 드물므로 제거/then 통합 | 폐기. 의미 손실과 invalid union이 실측됨. |
| required row key면 ref까지 완전 closed | 오해. 현재 ref 모양만 regex, evidence 소속은 grader가 확인. |
| input token 7.9M→4M이면 KV cache 성립 | 잘못된 지표. 논리 prompt token과 실제 KV cache hit는 구분. |
| 전체 context 자동 요약이 작동 | 사실 아님. 중첩 DBMS child-body compaction만 존재, C run hit 0. |
| purpose-only summary로 충분 | 미검증이 아니라 결함 후보. canonical summary의 역할과 충돌(TA-144). |
| analyzer가 source에서 return/call/assignment를 정규식으로 추출해도 범용 | 폐기 대상. grammar가 아는 구문은 parser listener/AST JSON의 책임이다. |
| AST가 RETURN을 이미 완전하게 제공 | 사실 아님. C 실제 AST에는 RETURN node가 없고 analyzer가 한 줄 원문에서 재추출한다. |
| 계속 prompt를 바꾸면 모델 오류가 언젠가 해결 | 금지. 범용 수정 1회 replay 후 needs-context/model limit/randomness로 종료한다. |

## 3. 현재 spec 본문에서 특히 주의할 위치

- spec §2의 “값·객체 추적기” 포함 문구: 역사 기준선
- spec §3의 `[값추적]` 목표 배선: 폐기된 목표
- spec §4의 arbitrary Python leaf/상한 있는 재요청: 현재 wire·retry 계약과 다름
- plan §1~§6: 구현 착수 당시 기록. plan 서두의 현행 보정과 최신 절을 우선
- tasks 2단계 완료 체크: 당시 구현 증거이지 현재 채택 증거가 아님
- tasks의 과거 cold 성공 체크: 당시 계약/품질 구성이므로 현재 합격을 자동 증명하지 않음
- spec/plan의 “branch_inventory가 종료문·호출·대입을 source에서 추출” 문구: legacy 역사.
  현재 목표는 parser AST producer 계약이며 `07`/TA-151이 우선

## 4. 문서 동기화 규칙

- spec에는 목표/계약과 acceptance criteria를 둔다.
- plan에는 현재 구현 순서와 소유권을 둔다.
- tasks에는 현재 미완료/미검증과 실제 증거를 둔다.
- 이 handoff에는 세션 재개에 필요한 현 상태·실측·폐기 이유를 둔다.
- 역사 실험은 삭제하지 않되 `역사/폐기/반증` 표식을 붙인다.
- 새로운 현재 계약이 과거 문구와 충돌하면 spec/plan/tasks의 첫머리 정정표를 먼저 갱신한다.

## 5. 헌법에 올릴 것과 올리지 않을 것

헌법은 범프로젝트 불변 원칙만 가진다. 다음은 이미 헌법에 충분히 반영되어 있다.

- Determinism-First
- No Silent Failure와 quality finding 구분
- KV-cache-friendly prompts
- minimal structured output
- ownership/dependency direction

Rule의 필드명, 8-row batching, 4,100행 기준, 특정 run id처럼 spec 116 전용 사실은 헌법에
넣지 않는다. 대신 “결정론이 업무 의미를 추론하지 않는다”라는 경계가 다른 spec에서도 반복
위반된다면 헌법 I의 해석 문구를 governance 절차로 개정하고 버전을 올린다. 임의로 무버전
수정하지 않는다.
