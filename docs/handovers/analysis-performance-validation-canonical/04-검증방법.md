# 04. 검증 방법

> **이 문서는 헌법 IX(3층 검증 의무)가 가리키는 절차 정본이다.** 권고가 아니라 구속력이
> 있으며, 여기 조문 중 실행하지 않은 항목은 반드시 `미검증`으로 보고한다. 어느 한 층도
> 다른 층을 대신하지 않는다. 원인 추적 순서는 헌법 X가 소유한다.

검증은 테스트 통과, 정답지 자동 비교, 주 에이전트 직접 의미 대조의 세 층을 모두 요구한다.

## 0. 원인 추적 순서 (헌법 X — 무엇이 잘못됐을 때)

**통계가 아니라 틀린 좌표 하나에서 출발한다.** "누출 5%"를 보고 프롬프트를 고치는 것이
아니라, 누출한 행 한 개를 잡아 아래 순서로 앞에서부터 확인한다. **모델은 마지막 용의자다.**

| 순 | 확인 대상 | 여기서 발견되는 결함 |
|---|---|---|
| 1 | 원문 소스 | 애초에 코드가 그렇게 생겼는가 (원문이 정답지) |
| 2 | parser AST | 원문 구문이 AST에 실재하는가 — 누락·범위·부모 오귀속 (§3.3) |
| 3 | analyzer 결정론 조립 | 분기표·의무 행·증거가 맞는가 — **의무 0건은 여기** |
| 4 | 모델이 **실제로 받은** 프롬프트 | 준 줄 알았던 것과 실제로 간 것이 다를 수 있다 |
| 5 | **정보 충분성** (§4.4-3) | 나도 못 푸는가 → `needs_context`, 고칠 곳은 2·3 |
| 6 | 채점기·정답지 | 모델이 맞고 grader가 틀렸을 수 있다 (§1 첫 줄) |
| 7 | 모델·프롬프트·스키마 | 위 여섯이 깨끗할 때만 |

실측 대조(2026-08-07): 트리거 fatal은 3에서, nl 참조번호 누출은 4에서 원인이 잡혔다.
어느 쪽도 모델 잘못이 아니었다.

## 1. 검증 전 원칙

- 정답지와 grader도 틀릴 수 있다. 불일치가 나오면 모델보다 source/분기표/grader를 먼저 연다.
- 문자열 일치가 아니라 의미 동등성을 판정한다. “사과는 빨간색이다”와 “사과는 빨갛다”는 통과다.
- 검증하지 않은 항목은 “모름/미검증”으로 남긴다.
- 검증용 LLM을 추가 호출하지 않는다. 주 에이전트가 입력 증거와 결과를 직접 읽고 판단한다.
- 특정 샘플의 정답을 생산 코드에 하드코딩하지 않는다.
- 골드셋을 전제하지 않는다. 정답지는 요청 안의 결정론 사실(`when`/`direct`)과 원문에서
  독립 추출한 occurrence이며, 코퍼스에 gold 자산이 있으면 **추가** 대조로만 쓴다.

## 2. 실행 무결성

1. 정확한 env/cache/concurrency/database 기록
2. run id, HEAD, dirty 상태, prompt hash 기록
3. usage의 calls/input/output/latency/finish reason/response cache hit 집계
4. error/finding/raw/partial 파일 존재와 좌표 조인
5. branch obligation 회계:
   `모든 branch rows = trusted RULE + quality findings + unavailable`
6. unavailable은 0이 목표이며, 존재하면 원인을 모두 열어본다.

## 3. 결정론 정답지와 전수 대조

### 3.1 CALL

- repository symbol table과 scope/import/inheritance 해석으로 사용자 정의 함수 간 CALL 정답지를 만든다.
- 언어 표준 라이브러리와 외부 라이브러리는 사용자 정의 CALL edge에서 제외한다.
- 이름 prefix/대문자/고객 관습으로 분류하지 않는다.
- AST에 없던 linker CALL edge는 source callsite와 resolved target을 전수 대조한다.
- missing, extra, wrong-target, ambiguous를 각각 집계한다.

### 3.2 R/W

- AST/DDL/embedded SQL/skill이 구조적으로 보증한 table access occurrence를 정답지로 만든다.
- READ/WRITE 종류, 함수 소유권, table target을 전수 비교한다.
- callee의 R/W를 caller 직접 R/W로 오귀속하지 않는다. lineage 관계와 direct access를 구분한다.
- 문자열에 우연히 등장한 table 이름은 R/W 증거가 아니다.

### 3.3 RETURN

- 각 지원 언어의 parser grammar/listener에서 RETURN AST occurrence와 정확한 반환 표현을 수집한다.
- source occurrence는 독립 정답지로 사용해 AST 누락·추가·범위 오류를 먼저 전수 대조한다.
- 표현 집합과 source line의 누락·추가·오귀속을 비교한다.
- 반환 코드의 업무 의미는 명세 증거 없이는 정답지에 쓰지 않는다.
- multiline, inline, value 없는 return, nested branch, throw/raise, SQL return 변형을 경계 fixture로
  검사한다.
- analyzer의 첫 토큰/정규식 fallback 없이 AST만으로 동일 obligation/evidence가 만들어지는지
  생산자→소비자 통합 테스트한다.

### 3.3.1 AST 구조 사실 전수 감사

1. analyzer의 source pattern scanner를 전수 검색한다.
2. 각 scanner가 찾는 것이 host-language grammar가 아는 구문인지, embedded text/skill 영역인지
   분류한다.
3. grammar 구문이면 모든 지원 언어 listener의 emit 여부와 AST JSON 필드를 표로 만든다.
4. source occurrence ↔ AST node ↔ analyzer context/evidence ↔ graph/finding을 같은 좌표로 대조한다.
5. parser 지원 언어에서 누락 0·추가 0·wrong owner 0이 확인된 뒤에만 analyzer legacy scanner를
   삭제한다.
6. 새 언어는 listener/ontology role/consumer contract test를 함께 추가하지 않으면 지원 완료로
   세지 않는다.

### 3.4 Rule ↔ branch table

- 모든 분기 행에 정확히 한 obligation이 있는지 뺄셈한다.
- trusted Rule row key가 해당 함수 branch table에 존재하는지 확인한다.
- cond/then ref가 그 요청 evidence에 실제 존재하는지 확인한다.
- negation, nesting, default/complement, exit/handler 행을 별도 집계한다.
- extra는 source/DDL/skill evidence로 직접 판정한다.
- 현행 Rule은 LLM 0의 결정론 구조 산출물이다. `nl`은 없거나 빈 호환 필드여야 하며, 사람용
  표시는 같은 cond/then을 해석 없이 구조 렌더링한다. `rule-structures/deterministic-rule-v1`
  감사 산출물의 row coverage·중복 0·재물질화 동등성과 graph cond/then exact를 전수 비교한다.
- 과거 run에 실제 Rule 자연어가 존재할 때만 역사 결과의 `nl`과 cond/then 모순을 직접 판정한다.

### 3.5 EXAMPLE ↔ accepted Rule

- 모든 trusted Rule을 대상으로 EXAMPLE 존재 여부를 전수 검사한다.
- `given`은 Rule cond의 canonical materialization과 같아야 한다.
- `then`은 Rule then/accepted extra의 canonical materialization과 같아야 한다.
- rejected/unverified Rule에서 trusted EXAMPLE이 나오면 결함이다.
- Python/DSL parser 통과, literal/reference 보존, graph HAS_EXAMPLE 관계를 모두 검사한다.

## 4. 직접 의미 대조

### 4.1 표본

- 코드노드 고정 20개: 단순/복잡, leaf/parent, CALL/RW/RETURN, 분기·상태·오류,
  finding 포함 표본을 층화한다.
- 테이블은 **전부** 검사한다.
- 표본 선택 기준과 ID는 run 전에 고정해 결과를 보고 바꾸지 않는다.

**난이도·중복 규칙 (2026-08-07 사용자 확정)**

- **어려운 것을 기반으로 뽑는다.** 쉬운 함수로 자리를 채워 통과율을 부풀리지 않는다.
- **유형이 겹치지 않게 한다.** 층화 축(분기 깊이·행 수·CALL/RW/RETURN 보유·오류 경로·
  finding 보유·stereotype 종류)마다 서로 다른 유형을 배정한다.
- **겹칠 수밖에 없으면 그 유형 안에서 가장 어려운 것을 고른다** — 깊이가 크고, 행이 많고,
  finding이 있는 쪽.
- 선정 규칙과 확정 ID는 **결과 열람 전에 파일로 고정**한다(스크립트에 규칙을 박아 결과를
  보고 바꿀 수 없게 한다).

### 4.2 코드노드에서 검사할 모든 LLM 속성

- canonical summary
- stereotype/role 분류
- module/component 의미 이름과 설명 중 해당 node에 귀속되는 값
- Rule의 cond/then/extra와 구조 표시(현행 `nl`은 absent/empty; 과거 run만 자연어 판정)
- 질문/needs-context가 있는 경우 그 타당성
- AST에 직접 없던 의미 관계와 table 영향 관계

### 4.3 테이블에서 검사할 모든 LLM 속성

- logical name
- description
- column logical name/description이 생성된다면 전부
- table insight, business role, 관계 설명
- 물리 DDL과 code usage에 없는 상태값/업무 의미를 창작했는지

### 4.4 직접 판정 절차

각 대상마다 다음을 기록한다.

1. 모델이 실제로 받은 prompt/evidence를 읽는다.
2. source/DDL/callee summary/구조 관계를 주 에이전트가 직접 읽는다.
3. **정보 충분성**을 먼저 판정한다.
   - 주 에이전트도 확정 불가: `needs_context`; GPU 성능 탓으로 세지 않는다.
   - 충분한데 모델이 틀림: model/prompt/schema 결함.
   - 입력에는 있는데 좌표/구조로 연결되지 않음: input production 결함.
4. 독립적인 기대 의미를 짧게 작성한다.
5. 모델 출력과 의미 동등/부분/모순/창작/누락으로 판정한다.
6. 다른 표현이나 동의어는 통과한다.
7. 실패는 공통 원인으로 묶어 범용 수정한다.
8. 한 차례 범용 증거/구조/프롬프트 개선 후 같은 입력에서 다시 본다.
9. 충분한 입력과 안정된 계약인데도 반복적으로 변동하면 모델 한계/랜덤성으로 기록하고
   더 이상 맨땅에 헤딩하지 않는다.
10. 같은 공통 원인의 범용 수정은 1회만 replay한다. 이후 동일 실패면 종료선에 따라 분류한다.

## 4.5 검증 자동화의 소유자 — `scripts/judge_run.py`

§2·§3의 기계 가능한 축은 **상설 도구가 소유한다.** 일회용 스크립트를 매번 새로 쓰지 않는다
(2026-08-07 `_runs` 관행 폐지). 도구는 임의 run 폴더를 인자로 받고, `--baseline`으로 직전
run과 행 단위 대조한다. 새 검증 축이 생기면 이 도구에 추가해 **매 run 상시로 돌게 한다.**

§4(직접 의미 판정)는 자동화 대상이 아니다 — 주 에이전트가 원문을 읽고 판단한다.

## 4.6 실행 표준 (2026-08-07 사용자 확정)

- **대상은 항상 `project\data`.** 보관소(`분석대상모음`) 경로를 직접 겨냥해 돌리지 않는다.
  코퍼스 교체 = 보관소에서 data 로 옮겨 넣는 절차이며, 그때 이전 코퍼스를 보관소로 되돌린다.
- **전략별 DB 분리**: framework는 `test`, DBMS는 `neo4j`. 서로 덮지 않아야 양쪽 그래프를
  동시에 보존·대조할 수 있다.
- **DDL은 코퍼스가 실제로 사용하는 테이블만** 담는다. 전체 스키마 덤프·프로시저 번들을
  ddl 에 섞지 않는다(안 쓰는 테이블 설명 생성과 중복 정의 fatal의 원인).
- **재실행 상한**: framework 2회 · DBMS 4회. 상한 소진 시 수치 그대로 `한계/미검증` 보고.

## 5. 성능 변경의 정확도 승인 게이트

compact wire, batching, scheduling 변경은 다음을 모두 통과해야 한다.

1. 동일 저장 prompt의 제한 replay 집합: 단순, 다행, 긴 출력, extra, 기존 finding 포함
2. row keys/cond/then/extra/nl의 좌표별 비교
3. grader 결과 및 finding reason 비교
4. 주 에이전트의 직접 의미 판정
5. 전체 cold에서 trusted >= 4,016, obligation 4,100, unavailable 0
6. 전체 테스트·prompt byte identity 통과
7. wall과 per-agent latency/output 개선

한 지표라도 미검증이면 채택하지 않는다.

성능 계약 승인 뒤 다음을 이전 accepted baseline과 비교해 보고한다.
