## 3. 작업 순서 (역사 — A~H 는 TA-151/성능 트랙에서 완료됨. 현재 순서는 09 §17)

### A. AST 구조 사실 생산자 계약 정리

1. `07-AST-구조사실-생산자계약.md`와 parser spec 016을 읽는다.
2. analyzer의 source pattern scanner를 전수 분류한다.
3. grammar가 아는 RETURN/CALL/ASSIGNMENT/종료/조건 구문은 언어별 parser listener와 AST JSON
   계약으로 이동한다. 기존 parser `switch/case` dirty WIP는 덮지 않는다.
4. parser source occurrence↔AST 전수 테스트와 analyzer AST-only 소비 통합 테스트를 먼저 만든다.
5. 지원 언어 누락 0을 확인한 뒤 legacy scanner를 삭제한다. source fallback 병존은 금지한다.

### B. compact regex 의미 차이 판정

1. 저장된 실제 prompt/evidence에서 extra 차이가 난 대상을 연다.
2. source/DDL/branch evidence를 읽어 old extra와 new omission 중 어느 쪽이 맞는지 직접 판단한다.
3. grader/finding이 틀렸을 가능성도 함께 검사한다.
4. 결과를 tasks와 `03-성능실측과-원인.md`에 기록한다.

### C. 공식 자료와 현재 배포 조사

1. SGLang 공식 문서/소스에서 request `regex`, JSON schema, whitespace, grammar cache,
   structured output 성능 특성을 확인한다.
2. 현재 서버 OpenAPI와 실제 probe가 문서와 같은지 확인한다.
3. server launch 설정 변경 없이 적용 가능한 request-level 방법만 후보로 둔다.
4. 외부 자료의 일반 결론과 현재 배포 실측을 구분한다.

### D. 범용 compact 계약 설계

- named `cond/then/extra/nl` 유지
- row keys 요청별 required
- 가능하면 condition/effect refs도 요청별 enum으로 제한
