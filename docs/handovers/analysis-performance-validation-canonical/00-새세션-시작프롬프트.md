사용자 판단이 필요한 항목 (임의로 정하지 말고 물어라):

  현 기준선의 extra 9건이 전부 미인정(unverified 8·rejected 1)이라, 원문 그대로 적용하면
  오류 메시지 문자열에서 테이블명을 읽은 환각을 보존하게 된다.

핵심 방향과 제약 (08 §4~§6 요약 — 상세는 반드시 08에서 확인):
- 정확도와 속도를 맞바꾸지 않는다. 합격선 trusted >=4,016 · obligation 4,100 ·
  unavailable 0. wall만 빨라지고 이 구성이 나빠지면 실패다.
- Neo4j 기본 DB는 **읽어도 된다**. 제한되는 것은 전체 재분석 실행뿐이며 그것은
  --database test로만 한다. 이유: 기본 DB에 비교 기준선이 있고 실행은 대상 DB를 비우고
  새로 채우므로, 덮이면 Stage 8 delta를 낼 상대가 사라지고 되돌릴 수 없다.
- canonical D:\work\robo\project\data 도 **읽어도 된다**. 제한되는 것은 새 AST 생성으로
  덮어쓰는 것뿐이며 검증·사용자 승인 후에만 한다. 신 AST는 _runs 격리 corpus에 있다.
- 추론 서버는 요청 수준 파라미터만 쓴다. 서버 설정·모델·launch flag는 바꾸지 않는다.
- 응답 캐시를 켠 상태로 성능을 비교하지 않는다.
- LLM 내용 오류는 재요청하지 않는다(전송 오류만 최대 3회). 별도 LLM judge·repair를
  해결책으로 추가하지 않는다. 오답은 좌표별 finding으로 격리하고 계속 진행한다.
- 입력이 없으면 낡은 경로(소스 정규식 재추출)로 조용히 되돌아가지 말고 좌표 있는 오류로
  실패하라. 한 기능에 여러 갈래 경로를 만들지 마라.
- 특정 언어명·함수 접두·고객 코드값·상태값에 맞춘 결정론 분기를 만들지 마라. 값·객체
  상태 추적, 상태코드 의미 추론, 임의 언어→Python 의미 번역은 폐기 확정이다.
- AST 전환과 출력 형식 변경을 한 A/B에 섞지 마라. 성능 후보당 공식 cold 1회.
  변경 없는 cold나 같은 문구 변형 반복을 하지 마라.
- 실패 후보를 빈 성공으로 저장하지 마라. 위반 1건으로 전체 run을 끝내지 마라.
- .env·키·고객 원문을 문서·로그·커밋에 복사하지 마라. 커밋·푸시는 명시 지시가 있을 때만.
- 자동 테스트 통과만으로 의미 정확도를 주장하지 마라. 검증하지 않은 것은 "모른다"고 보고하라.

행동 규칙 (사용자 확정 지시):
1. 사용자 메시지를 확인하면 도구 호출 전에 **사용자가 채팅에서 읽을 자연어 문장**으로
   먼저 답하라. 생각 속 정리나 작업 보고에 섞은 한 줄은 답변이 아니다.
2. 답을 낸 뒤에는 승인을 기다리지 말고 곧바로 작업을 이어서 진행하라. "진행할까요?" 금지.
3. 의미 단위(테스트 실행·파일 수술 완료·단계 경계)마다 번호 붙은 중간 보고를 스스로 내고,
   보고 뒤에도 멈추지 말고 계속하라.
4. 도구만 연달아 실행하는 침묵 주행을 하지 마라. 호출 사이에 지금 무엇을 왜 하는지
   한두 줄씩 써라.
5. 막히면 우회 땜빵을 만들지 마라. 대신 이 순서로 뚫어라 (08 §20.1):
   ① 스스로 조사한다 — 코드·로그·설정·git·실제 실행으로 확인 가능한 사실은 묻지 말고
     직접 확인하라. 저장된 prompt record·finding·usage 원장 열기, 격리 스크립트로 1콜
     확인 호출 보내기, 대조군을 만들어 역실험하기가 여기 포함된다.
   ② 웹으로 조사한다 — 저장소 밖 사실(외부 도구의 버전별 동작, 알려진 이슈, 사양)은
     직접 검색·문서 확인하라. 외부 자료의 일반 결론과 우리 배포 실측은 구분해 적어라.
   ③ 그래도 확정 안 되면 **stop 하고 사용자에게 딥리서치를 요청하라**. 질문은 문서에
     넣지 말고 채팅으로만 내고, 질문마다 왜 필요한지와 답에 따라 무엇이 갈리는지를
     붙여라. 받은 답변은 03에 확정 사실과 질문↔답변 원장으로 나눠 기록하라.
     **답을 기다리는 동안 멈추지 말고** 그 답에 의존하지 않는 작업을 계속하라.
   ④ 조사해도 확정 불가면 needs-context 또는 지원 한계로 기록하고 반복을 끝내라.
     추정을 코드에 넣지 마라.
6. 다음 세 가지는 혼자 정하지 말고 먼저 물어라: ①되돌리기 어려운 작업(canonical 덮어쓰기,
   대량 삭제, 커밋·푸시) ②정본에 없는 새 설계 방향 ③정확도와 무언가를 맞바꾸는 선택.
   그 외 실행은 전부 자율로 진행하라.
7. 작업 중 사용자 메시지가 감지되면 하던 작업보다 답변이 우선이다. 사용자가 연속으로
   끊거나 "왜 대답 안 하냐"고 하면 답이 과녁을 빗나갔다는 신호다 — 작업을 재개하기 전에
   자연어로 다시 답하라.
8. 원칙 위반이나 잘못된 설계를 발견하면 범위 밖으로 미루지 말고 tasks에 즉시 편입하라.
9. 작업하면서 08을 즉시 갱신하라(끝난 뒤 몰아쓰기 금지). 완료·미완료·미검증·반증을
   구분해 보고하라.
10. 대량 반복 작업(전수 조사, 다파일 전환)은 시작 전에 규모와 계획을 한 번 보고하고
    진행하며, 중간에 예상과 다른 패턴이 나오면 그 시점에 보고하라.
11. 서술은 정확한 도메인 용어로 하라(08 §21). 제약을 쓸 때는 허용 범위도 함께 적어라.
