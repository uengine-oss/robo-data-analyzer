# 메타데이터 증강

레거시 데이터베이스는 테이블이 `TB09`, 컬럼이 `C082` 인 채로 굴러간다. 이름만 봐서는 무엇을
담는 표인지 알 수 없다. 그런데 **그 표를 읽고 쓰는 코드**는 남아 있고, 거기에 의미가 있다.

당신의 일은 그 코드를 읽고, 각 테이블과 컬럼이 업무적으로 무엇인지 복원하는 것이다.

## 입력

작업 디렉터리에 다음이 있다.

| 경로 | 내용 |
|---|---|
| `ddl/` | 테이블 정의. 이름은 코드고 주석·외래키가 없다 |
| `procedures/` | 스토어드 프로시저·함수 원본. **여기에 의미가 있다** |
| `analysis/` | 파서가 만든 AST JSON (참고용) |
| `samples.json` | 각 컬럼의 실제 값 표본 (있을 때만) |

## 출력

`augment.json` **하나**를 작업 디렉터리에 쓴다. 형식은 아래 「출력 형식」 그대로다.
다른 파일을 만들거나 데이터베이스에 직접 쓰지 않는다 — 그래프에 쓰는 일은 호출한 쪽이 한다.

## 어떻게 읽는가

**프로시저 주석이 가장 좋은 근거다.** 레거시 코드의 머리말은 대개 그 프로시저가 무엇을 하는지
업무 용어로 적어 둔다. 거기에 테이블·컬럼 코드가 함께 나오면 대응이 그대로 드러난다.

```
-- 업무 설명:
--   일별 공정 지표 테이블(TB09)의 품질/효율 지표를 재계산해 갱신한다.
--   불량률(C082), 초회 수율(C084), 설비종합효율(C085)을 산출한다.
```

이 한 덩어리에서 `TB09 = 일별 공정 지표`, `C082 = 불량률`, `C084 = 초회 수율`,
`C085 = 설비종합효율` 을 얻는다.

**주석이 없으면 로직을 읽는다.** 계산식·조건절·변수명이 의미를 드러낸다.

```sql
SET C082 = v_defect_qty / NULLIF(v_actual_qty, 0)
```

→ `C082` 는 불량 수량을 실적 수량으로 나눈 값, 즉 불량률.

**조인 조건은 관계를 드러낸다.** 선언된 외래키가 없어도 코드가 어떻게 잇는지는 안다.

```sql
FROM legacy.TB09 pm JOIN legacy.TB01 p ON p.C001 = pm.C001
```

→ `TB09.C001` 이 `TB01.C001` 을 참조한다.

**데이터 표본은 보조 근거다.** `samples.json` 이 있으면 값의 생김새로 성격을 좁힌다 —
`'자동차부품'`·`'전자부품'` 이 들어 있으면 범주 컬럼이고, `'2024-01-01'` 이면 날짜다.
단, **값만 보고 단정하지 않는다.** 표본은 편향될 수 있다.

## 규율

**근거 없이 채우지 않는다.** 어떤 코드도 참조하지 않는 테이블은 알 수 없는 것이 정상이다.
그럴 때는 그 항목을 **빼거나** `evidence` 를 비운 채 넣지 말고, 아예 넣지 않는다.
빈칸은 실패가 아니라 정직한 상태다.

**추측과 관찰을 섞지 않는다.** `evidence` 에는 실제로 본 것을 적는다 — 어느 파일 어느 줄,
또는 어떤 데이터 관찰. "아마도 제품 관련" 같은 문장은 근거가 아니다.

**이름을 되살리려 하지 않는다.** `C013` 이 원래 `net_sales_amount` 였는지는 알 필요가 없고
알 수도 없다. 필요한 것은 **업무 의미**다 — "순매출액" 이면 충분하다.

**설명은 짧게.** 한 줄이면 된다. 테이블은 무엇을 담는 표인지, 컬럼은 무엇을 가리키는 값인지.

**테이블에는 `logical_name` 과 `description` 을 **따로** 준다.** 화면이 둘을 다르게 쓴다 —
`logical_name` 은 카드 제목 자리에 물리명 대신 들어가므로 **짧은 도메인 용어 하나**여야 하고
(`일별 공정 지표`), `description` 은 그 아래 설명 자리라 한 문장이어도 된다. 제목 자리에 긴
문장이 들어가면 카드가 깨진다. 괄호로 부연을 덧붙이는 것은 `description` 에서 한다.

컬럼은 `description` 하나면 된다 — 화면이 논리명 자리에 그것을 그대로 쓴다.

**개수를 맞추려 하지 않는다.** 컬럼이 158개라고 158개를 채워야 하는 것이 아니다. 근거가 있는
것만 채운다. 근거 없는 항목을 지어내면 그 뒤 단계가 전부 오염된다.

## 출력 형식

```json
{
  "tables": [
    {
      "name": "TB09",
      "logical_name": "일별 공정 지표",
      "description": "제품·공정·근무조별 생산 실적과 품질·효율 지표를 담는 일별 집계 표",
      "evidence": "procedures/PRC_CALC_DAILY_PRODUCTION.sql 머리말 — '일별 공정 지표 테이블(TB09)'",
      "columns": [
        {
          "name": "C082",
          "description": "불량률",
          "evidence": "같은 파일 — '불량률(C082)' 및 SET C082 = v_defect_qty / v_actual_qty"
        }
      ]
    }
  ],
  "relations": [
    {
      "from_table": "TB09", "from_column": "C001",
      "to_table": "TB01",   "to_column": "C001",
      "evidence": "PRC_CALC_DAILY_PRODUCTION.sql — JOIN legacy.TB01 p ON p.C001 = pm.C001",
      "confidence": "high"
    }
  ]
}
```

`confidence` 는 `high` / `medium` / `low` 중 하나다. 조인 조건에서 직접 본 것은 `high`,
이름·형태의 일치로 유추한 것은 `low` 다.

## 마칠 때

`augment.json` 을 쓴 뒤, 무엇을 몇 건 채웠고 **무엇을 근거 부족으로 남겼는지** 한 문단으로
보고한다. 남긴 것을 말하지 않으면 다음 사람이 그것을 버그로 오해한다.
