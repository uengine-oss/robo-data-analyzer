# Feature Specification: 그래프 스키마 정합 — DBMS 흐름·구조 복원 + 두 전략 관계 범용 통합

**Feature Branch**: `018-graph-schema-realign`

**Created**: 2026-06-18

**Status**: Draft

**Input**: User description: DBMS 그래프 구조 정합 — refactor 가 옛 main 대비 깨뜨린 부분(구문 실행흐름 NEXT, 선언부 노드) 복원 + 두 전략(framework/dbms) 관계·라벨을 "같은 뜻=같은 이름, 종류 차이는 노드 라벨" 원칙으로 범용 통합.

## 개요 *(맥락)*

분석기는 소스코드를 파싱해 **그래프**(노드 + 관계)로 만든다. 이 그래프를 화면(frontend NVL/네비게이터), 카탈로그, 설계연계(architect)가 소비한다. 두 분석 전략이 있다: **Framework**(Java/C/Python — 클래스·함수 단위)와 **DBMS**(PL/SQL — 프로시저 + 그 안의 구문 흐름).

직전 refactor 가 식별자(id)를 통일한 것은 좋았으나, 그 과정에서 **DBMS 그래프의 핵심 정보를 잃거나 왜곡**했다(코드 전수조사 + 옛 main 대조로 확정):

1. **구문 실행 흐름(NEXT) 소실**: 옛 main 은 `(이전 구문)→(다음 구문)` 순서 관계가 있었으나, refactor 는 NEXT 를 다른 용도로 전용해 **절차적 로직의 흐름을 그래프에서 따라갈 수 없게** 됐다.
2. **선언부(구조) 노드 누락**: DECLARE 가 노드로 안 만들어진다(파서 reader 가 통째 스킵). 그러나 자체 스펙(009)·배치 플래너는 "그래프엔 유지, LLM 분석만 제외"라고 명시 → **코드가 자기 계약을 위반**.
3. **소속 관계 과다 적용**: "그릇이 함수를 가진다(HAS_FUNCTION)"가 **모든 구문에까지** 남발됐다(한 모듈에 456개). 옛 main 은 파일→프로시저에만 적용했다.
4. **구문을 "함수"로 취급**: SELECT 같은 구문이 함수처럼 모델링돼 의미가 흐려졌다.

동시에, 두 전략의 관계명·라벨이 일관 기준 없이 섞여 있어 소비처가 복잡하다. 본 기능은 **잃은 것을 복원**하고 **관계/라벨 모델을 범용 원칙으로 정리**한다. 식별자 id 통일은 그대로 유지한다.

**설계 원칙(확정)**: "같은 뜻이면 같은 관계명(통일), 한 전략에만 있는 개념은 그대로 둔다. 종류 차이는 전부 노드 라벨이 표현하고, 관계(엣지)는 범용." (업계 표준 — CodeQL의 공유코어+언어별 추출기, CPG의 층 분리, Kythe의 확장가능 스키마와 동일 방향.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - DBMS 프로시저의 실행 흐름을 따라간다 (Priority: P1)

분석가가 DBMS 프로시저를 그래프에서 볼 때, 내부 구문들이 **실행 순서대로** 연결되어(예: SELECT → IF → INSERT) 로직이 어떤 순서로 흐르는지 눈으로 따라갈 수 있다.

**Why this priority**: 절차적 코드(PL/SQL)는 "무슨 순서로 실행되나"가 이해의 핵심이다. 현재 이 흐름이 그래프에 없어 흐름 분석이 불가능하다 — 가장 큰 손실.

**Independent Test**: 한 프로시저를 분석한 뒤, 그 안의 인접 구문들이 순서 관계(NEXT)로 연결되어 첫 구문부터 끝 구문까지 따라갈 수 있는지 확인한다. Framework 함수는 이 흐름이 없어야 한다(개념 부재).

**Acceptance Scenarios**:

1. **Given** 여러 구문이 든 DBMS 프로시저, **When** 분석 후 그래프를 보면, **Then** 같은 부모 아래 형제 구문들이 실행 순서대로 NEXT 관계로 연결된다.
2. **Given** Framework(Java) 함수, **When** 분석 후 그래프를 보면, **Then** 구문 단위 흐름(NEXT)은 생성되지 않는다(함수 단위까지만 분석).

### User Story 2 - 코드가 빠짐없이 그래프에 있고, "구조"와 "분석 누락"이 구분된다 (Priority: P1)

분석가가 그래프를 볼 때 모든 코드 부분(변수 선언부 포함)이 노드로 존재한다. 분석 대상이 아닌 구조 부분(선언부·예외 블록 등)은 **"구조"로 명확히 표시**되어, "여기 분석이 빠졌나?"라는 오해가 없다.

**Why this priority**: 노드 누락은 결과 신뢰를 깨뜨린다. 현재 선언부가 통째로 사라져 사용자가 데이터 결손으로 오인한다. 또한 "분석 비대상(구조)"과 "분석 실패(버그)"는 사용자가 반드시 구분할 수 있어야 한다.

**Independent Test**: 선언부가 있는 프로시저를 분석한 뒤, 선언부가 노드로 존재하고 "변수 선언부 (구조)"로 표시되며, 비즈니스 분석값(요약·규칙)은 비어 있어도 "구조라 원래 대상 아님"으로 읽히는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 선언부가 있는 프로시저, **When** 분석 후 그래프를 보면, **Then** 선언부가 노드로 존재한다(누락 0).
2. **Given** 구조 노드(선언부/예외블록/트리거본문), **When** 논리명 표시 모드로 보면, **Then** 종류별 한글 라벨 + "구조" 표시가 보이고 분석 누락과 구분된다.
3. **Given** 구조 노드, **When** 분석 단계를 보면, **Then** LLM 분석은 제외되지만 그래프 노드는 유지된다.

### User Story 3 - "무엇을 담고 있나"를 한 가지 관계로 조회한다 (Priority: P2)

소비자(화면·질의)가 어떤 그릇(파일·클래스·패키지)이 무엇을 담고 있는지 **단일 관계 하나로** 조회한다. 담긴 것의 종류(함수/변수/상수…)는 노드 라벨로 구분한다.

**Why this priority**: 같은 뜻의 관계가 여러 이름(HAS_FUNCTION/HAS_VARIABLE…)으로 흩어지면 소비처가 매번 여러 관계를 처리해야 해 복잡·취약해진다. 하나로 통일하면 소비가 단순해진다.

**Independent Test**: 함수와 변수를 모두 가진 그릇을 분석한 뒤, 단일 "가짐(HAS_MEMBER)" 관계 하나로 그 그릇의 모든 멤버를 조회할 수 있고, 멤버의 종류를 노드 라벨로 구분할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 함수·변수·상수를 가진 그릇, **When** "가짐" 관계로 조회하면, **Then** 종류 불문 모든 멤버가 한 번에 조회된다.
2. **Given** 조회된 멤버들, **When** 종류를 구분하면, **Then** 노드 라벨(PROCEDURE/VARIABLE/CONSTANT…)로 100% 구분된다.

---

### User Story 4 - 노드가 "정체대로" 보인다 (Priority: P2)

> **★분할(2026-06-19)**: 본 US4의 두 부분 중 — **(a) HAS_MEMBER 루틴 한정**(구문은 PARENT_OF+NEXT)은 **US3 producer 구현에 포함=완료**. **(b) 그릇 라벨 정체화(MODULE→FILE/CLASS)**는 framework 용어 부채라 **spec `019-terminology-realign`로 이관**(거기 최종모델 = 타입 단일 라벨·역할 라벨 폐기). 따라서 본 US4의 라벨 관련 FR/태스크(FR-008·T025·T027·T028·D5·D10·V5)는 **019가 권위** — 018에선 참고용.

사용자가 노드를 볼 때 실제 종류대로 표시된다 — 파일은 파일, 클래스는 클래스, 프로시저는 프로시저, 구문은 자기 종류. "함수가 아닌 것이 함수로" 같은 왜곡이 없다.

**Why this priority**: 비개발자가 그래프를 이해하려면 라벨이 실제와 맞아야 한다. 현재 SELECT 같은 구문이 "함수"로 묶여 혼란을 준다.

**Independent Test**: DBMS 파일을 분석한 뒤, 그릇이 FILE(또는 PACKAGE)로, 실제 루틴만 함수처럼 담기고(HAS_MEMBER), 구문은 자기 종류 라벨로 중첩(PARENT_OF)·흐름(NEXT)으로만 연결되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 여러 프로시저가 든 .sql 파일, **When** 분석하면, **Then** 그릇은 FILE 로(MODULE 강제 아님), 프로시저만 "가짐" 관계로 매달린다.
2. **Given** 프로시저 내부 구문, **When** 그래프를 보면, **Then** 구문은 "가짐" 관계가 아니라 중첩·흐름으로만 연결된다.

---

### User Story 5 - 비즈니스 규칙이 중복·품질저하 없이 생성된다 (Priority: P3)

분석 산출물(규칙·예시·질문)이 단위(프로시저/함수) 기준으로 생성되어, **중복 없이** 그리고 **세부 정확도 손실 없이** 만들어진다.

**Why this priority**: 산출물 품질 문제이며 P1(구조 복원)보다 후순위. 단 결과 신뢰에 직접 영향.

**Independent Test**: 한 프로시저를 분석한 뒤, 규칙이 의미상 중복되지 않고, 세부(하위 구문) 정보가 요약 압축으로 인해 손실되지 않았는지 원문과 대조한다.

**Acceptance Scenarios**:

1. **Given** 한 번에 처리 가능한 크기의 프로시저, **When** 분석하면, **Then** 통째로 1회 처리되어 부모/자식 간 규칙 중복이 없다.
2. **Given** 너무 커서 분할이 필요한 프로시저, **When** 분석하면, **Then** 하위의 정확한 산출물이 상위로 올라가 상위가 한 단계 추상화해 재생성하며, 하위 산출물을 그대로 복제하지 않는다.
3. **Given** 분석 완료, **When** 최종 산출물을 보면, **Then** 의미 중복이 제거되어 있다.

### Edge Cases

- **프로시저가 하나도 없는 .sql / 빈 선언부**: 그릇 노드는 존재하되 멤버 0 으로 정상 처리.
- **파일에 프로시저가 1개 / 여러 개 / 패키지**: 개수·패키지 유무와 무관하게 "그릇이 멤버를 가진다(+패키지면 한 단계 더)"로 일관 처리.
- **Java에서 한 파일에 클래스 여러 개**: 각 클래스가 그릇, 파일 노드는 만들지 않음(클래스가 그릇).
- **중첩 함수(Python/JS 클로저)**: Framework 도 중첩(PARENT_OF)을 쓰는 드문 경우 — 정상 허용.
- **구조 노드 안의 실제 코드(예: TRY 블록 안 DML)**: 구조 노드는 분석 제외하되, 그 자식 코드는 가장 가까운 분석 대상 조상에 정상 연결.
- **관계명 변경으로 소비처가 옛 이름을 찾는 경우**: 모든 소비처를 새 이름으로 정합(회귀 0). 옛 이름 잔재 0.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 DBMS 구문 사이에 **실행 순서 관계(NEXT)** 를 생성해야 한다 — 같은 부모 아래 형제 구문을 등장(실행) 순서대로 `(이전)→(다음)` 연결. Framework 는 구문 단위 흐름 개념이 없으므로 생성하지 않는다.
- **FR-002**: 시스템은 **모든 코드 노드를 그래프에 생성**해야 한다. 분석 비대상(구조) 노드도 **노드로 보존**하되 LLM 분석만 제외한다(누락 0). 구조 노드를 노드 자체로 삭제하면 안 된다.
- **FR-003**: 구조 노드(선언부·예외 블록·트리거 본문 등)는 **종류별 한글 라벨**과 **"구조" 표시**를 가져야 하며, 그 라벨 정의는 **단일 정의처 한 곳**에서만 관리된다(여러 곳·노드별 중복 정의 금지).
- **FR-004**: "그릇이 멤버를 가진다"는 **단일 관계(가짐, HAS_MEMBER)** 로 표현하고, 멤버의 종류(함수·변수·상수·필드·파라미터…)는 **노드 라벨**로 구분한다. (옛 HAS_FUNCTION/HAS_VARIABLE/HAS_MEMBER 를 하나로 통합.)
- **FR-005**: "네임스페이스에 속한다"는 **단일 관계(소속, BELONGS_TO)** 로 표현한다(폴더·패키지·스키마 소속 공통). (옛 BELONGS_TO_PACKAGE/BELONGS_TO 통합.)
- **FR-006**: **중첩(PARENT_OF)** 관계는 두 전략 공통으로 쓰되, "가짐(HAS_MEMBER)"·"소속(BELONGS_TO)"과 의미가 구분되어야 한다(세 관계는 서로 다른 개념).
- **FR-007**: "가짐(HAS_MEMBER)"은 **그릇→실제 루틴(프로시저/함수)에만** 적용한다. 루틴 내부의 구문은 가짐 관계가 아니라 **중첩(PARENT_OF) + 흐름(NEXT)** 으로만 연결한다.
- **FR-008**: 그릇(컨테이너) 노드는 **실제 종류대로 라벨링**한다(파일=FILE, 클래스=CLASS, 패키지=PACKAGE). 단일 라벨(MODULE)로 강제 통일하지 않는다. **파일은 그 자체가 그릇일 때만** 노드로 만든다(클래스가 그릇인 언어는 파일 노드 생략).
- **FR-009**: 같은 의미의 관계는 두 전략에서 **같은 이름**을 쓴다. **한 전략에만 존재하는 개념만** 전략 전용으로 둔다 — 흐름(NEXT)=DBMS 전용, 상속/구현(EXTENDS/IMPLEMENTS)=Framework 전용.
- **FR-010**: 비즈니스 산출물(규칙·예시·질문)은 **단위(프로시저/함수) 기준**으로 생성한다. 단위가 한 번에 처리 가능하면 **통째로 1회** 처리한다(분할로 인한 중복·품질저하 0).
- **FR-011**: 단위가 너무 커서 분할이 필요하면, 하위 부분이 **실제 코드로 만든 정확한 산출물**을 상위로 전달하고(요약 압축본이 아니라 — 품질저하 방지), 상위는 그것을 **복제하지 않고 한 단계 추상화해 재생성**한다.
- **FR-012**: 각 산출물(규칙 등)은 **자기 주인 노드에만 1회 저장**한다(복제 금지). 최종 결과에서 **의미 중복을 제거**한다(안전망).
- **FR-013**: 노드 **식별자 단일화(id)** 정책은 변경하지 않고 그대로 유지한다.
- **FR-014**: 본 변경으로 기존 그래프 소비처(화면·카탈로그·설계연계)가 깨지지 않아야 한다(**회귀 0**). 관계명·라벨 변경 시 **모든 소비처를 전수 정합**하고 옛 이름 잔재를 0 으로 만든다.
- **FR-015**: 매 분석은 기존 정책대로 **파괴적 전체 재빌드**(그래프 초기화 후 재생성)로 동작하며 본 변경이 이를 바꾸지 않는다.

### Key Entities *(그래프 = 노드 + 관계)*

- **네임스페이스 노드**: FOLDER(폴더) · PACKAGE(Java/PL-SQL 패키지) — 그룹/소속 단위.
- **그릇(컨테이너) 노드**: FILE(C/Python/DBMS 파일) · CLASS(Java 등) · PACKAGE — 멤버를 담는 단위. 실제 종류대로 라벨.
- **멤버 노드**: 루틴(PROCEDURE/FUNCTION/METHOD/TRIGGER) · 데이터(VARIABLE/CONSTANT/FIELD/PARAMETER).
- **구문 노드(DBMS)**: SELECT/INSERT/UPDATE/IF/LOOP/CALL/COMMIT… 및 **구조 노드**(DECLARE="변수 선언부"/TRY="예외 처리"/TRIGGER_BLOCK="트리거 본문").
- **DB 노드**: TABLE · COLUMN · SCHEMA.
- **의미 노드(예제매핑)**: RULE · EXAMPLE · QUESTION.
- **관계(범용)**: BELONGS_TO(소속) · HAS_MEMBER(가짐) · PARENT_OF(중첩) · CALLS(호출) · READS/WRITES(테이블 접근) · REFERENCES/INIT_BY(변수 참조/초기화) · HAS_COLUMN/FK(DB 구조) · HAS_RULE/HAS_EXAMPLE/HAS_QUESTION/AFFECTS_TABLE(의미).
- **관계(전략 전용)**: NEXT(실행 흐름 — DBMS) · EXTENDS/IMPLEMENTS(상속 — Framework).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: DBMS 프로시저의 인접 구문이 실행 순서로 연결되어, 첫 구문에서 끝 구문까지 흐름을 끊김 없이 따라갈 수 있다(대상 형제 구문의 순서 연결율 100%).
- **SC-002**: 분석 결과 그래프에 원문의 모든 코드 부분이 노드로 존재한다(원문 대비 노드 누락 0). 구조 부분은 100% "구조"로 구분 표시된다.
- **SC-003**: 그릇의 멤버를 **단일 관계 하나**로 조회할 수 있고, 멤버 종류를 노드 라벨로 100% 구분할 수 있다.
- **SC-004**: "가짐" 관계가 **실제 루틴에만** 연결되고 일반 구문에는 연결되지 않는다(구문에 가짐 관계 0건).
- **SC-005**: 같은 입력을 다시 분석해도 동일 결과(재현성)이며, 기존 소비처(화면·카탈로그·연계) **회귀 0건**, 옛 관계명/라벨 잔재 0건.
- **SC-006**: 비즈니스 규칙의 **의미 중복이 제거**되고(중복 0 목표), 하위 세부 정보가 요약 압축으로 인해 손실되지 않는다(원문 대조 시 세부 누락 0).

## Assumptions

- 대상 = `robo-data-analyzer`(그래프 생산자). 소비처 = catalog·frontend·architect(연계).
- 매 분석은 파괴적 전체 재빌드(그래프 초기화) 정책을 유지한다.
- refactor 의 노드 식별자 id 통일은 올바른 변경이므로 유지한다(되돌리지 않음).
- 관계명/라벨 변경은 **소비처 전수 정합**을 동반한다 — 별도 계획(plan/tasks) 단계에서 영향범위(blast radius)를 전수 조사해 양끝(생산자·소비처)을 동시 정합한다.
- 옛 main 의 DBMS 흐름(NEXT)·구조 노드 유지 방식이 올바른 기준이며, 본 기능은 그 의도를 refactor 의 id 통일 위에 복원한다.
- 분석 품질 검증은 단위 테스트가 아니라 실제 파이프라인을 돌려 그래프를 원문과 대조하는 방식으로 한다.
