# Feature Specification: MCP 레거시 검색 결과 정예화 (선정 게이트 + 계층화 상세 + 직렬화)

**Feature Branch**: `057-cluster-result-refinement`

**Created**: 2026-07-16

**Status**: Draft

**Input**: User description: "아키텍트 스킬(LLM)에 전달되는 cluster_retrieve 결과의 선정 품질 고도화 + 계층화 상세 + 직렬화 수정. 관련된 것만, 그러나 그것의 전문(원문 코드·규칙·예시·테이블 컬럼)을 전달한다."

## 배경 — 전부 실측된 문제 (2026-07-16)

질의 "주문 건의 배송 상태 조회와 배송 추적 이력"(shopmall)에 대한 실측:

1. **노이즈**: 22노드 중 유관 5~6개. 원인 사슬 — ① 앵커를 점수 불문 top-3 고정 선발
   (1위 0.895 vs 2위 0.765 의 점수 절벽 무시 → 가격이력·정산 오답 앵커 2개), ② 후보 12위
   전원이 support root 자격(그래프 연결 없이 직행 입장 + 각자 CALLS 1홉을 후보로 유입),
   ③ 오답 앵커의 테이블 이웃까지 동반. 무관 example 뭉치가 바이트의 46%.
2. **직렬화 부풀림**: MCP SDK 가 dict 결과를 escape(`\uXXXX`)+indent 텍스트화하고 구조화
   콘텐츠로 한 번 더 실음 — 원내용 67.3KB 가 CLI 에는 139.9KB 로 도착, 한도 초과로
   내용이 파일로 치환되어 스킬이 레거시 내용을 못 받는 사고의 방아쇠.
3. **필드 부적합**: 내부 전용 `search_text`·`element_id` 는 송출되는데, 사용자 필수 요구인
   **원문 코드**(그래프에 `code_text` 로 존재)와 **TABLE 컬럼 목록**(HAS_COLUMN 관계로 존재)
   은 응답에 없음.

사용자 결정(2026-07-16): "관련된 노드만 정확히 가져오되, 가져온 노드의 내용은 전량 —
원문 코드는 무조건 포함, search_text 는 불필요, 테이블은 설명+컬럼까지. 선정은 조잡한
고정 임계가 아니라 고도화된 방식으로. 프론트 표시에 영향을 주면 안 된다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 아키텍트 스킬이 "유관한 것의 전문"만 받는다 (Priority: P1)

설계 제안(Intent/Plan/DDD 스테이지)을 만드는 아키텍트 스킬이 레거시 그래프를 질의하면,
질의와 실제로 유관한 함수·테이블만, 그러나 각각의 전문(요약·원문 코드·규칙·예시·
읽고 쓰는 테이블·컬럼)을 받아 설계 근거로 쓴다. 무관한 도메인의 함수와 그 예시 뭉치가
컨텍스트를 오염시키지 않는다.

**Why this priority**: 이 결과가 설계 산출물의 근거이자 UI "레거시 근거" 칩의 출처다.
노이즈가 섞이면 근거 표시 자체가 거짓이 된다.

**Independent Test**: 검증 질의(배송 상태 조회·추적 이력)로 검색 API 를 직접 호출해
결과 노드 전수를 질의와 대조 — 무관 도메인(가격·정산·쿠폰·회원등급·장바구니) 함수 0개,
포함된 모든 함수에 원문 코드 존재, 포함된 모든 테이블에 컬럼 목록 존재.

**Acceptance Scenarios**:

1. **Given** 점수 1위와 2위 사이에 뚜렷한 절벽이 있는 질의, **When** 검색 실행,
   **Then** 절벽 아래 후보는 앵커가 되지 않고 그 이웃·테이블도 결과에 동반되지 않는다.
2. **Given** 상위권 점수가 촘촘한 복합 질의(정답 씨앗 여러 개), **When** 검색 실행,
   **Then** 상위권 후보들이 앵커로 유지되어 기존 골드셋 정답 재현율이 떨어지지 않는다.
3. **Given** 검색 결과의 FUNCTION 노드, **When** 아키텍트 스킬이 수신, **Then** 원문
   코드가 반드시 포함되고 내부 전용 필드(search_text 등)는 포함되지 않는다.
4. **Given** 검색 결과의 TABLE 노드, **When** 아키텍트 스킬이 수신, **Then** 논리명·
   물리명·설명과 컬럼 전량(이름·타입·PK 여부·논리명·설명)이 포함된다.

---

### User Story 2 - 결과가 한도를 넘지 않아 끝까지 도달한다 (Priority: P1)

검색 결과가 CLI 중계 한도를 넘지 않아, 파일 치환 없이 스킬과 프로버넌스 기록기(052)에
직접 도달한다. UI 칩(⛓ 레거시 근거 N)의 N 이 실제 유관 참조 수와 일치한다.

**Why this priority**: 현재 아키텍트 UI 에 근거가 0으로 표시되는 실사고의 직접 원인.

**Independent Test**: verify_052 e2e(제안 생성→intent 실행→저장 확인)에서
legacyReferences nodes>0, 파일폴백 미발동, 칩 스크린샷에 유관 노드만 표시.

**Acceptance Scenarios**:

1. **Given** 검증 질의의 결과, **When** MCP 로 전달, **Then** CLI 가 받는 텍스트 크기가
   원내용과 같은 자릿수(escape·indent·이중 전송으로 2배 부풀지 않음)다.
2. **Given** intent 실행 완료, **When** 제안 상세 조회, **Then** legacyReferences 에
   유관 노드들이 기록되고 UI 칩·팝오버가 이를 표시한다.
3. **Given** 그래도 한도를 넘는 극단 결과(초대형 함수 원문 등), **When** CLI 가 파일로
   치환, **Then** 052 파일폴백이 전량을 복원한다(안전망 존치).

---

### User Story 3 - Analyzer 검색 UI 는 무변화·무회귀 (Priority: P2)

Analyzer 프론트(그래프 탭 의미검색)는 계약 변화 없이 동작하며, 선정 품질 개선의 이득만
받는다.

**Why this priority**: 같은 검색 코어를 공유하므로 회귀 위험이 있는 유일한 기존 소비자.

**Independent Test**: 검색 UI 실행 — 스트림 진행·결과 뭉치 표시·캔버스 매칭이 기존과
동일 필드로 동작(실측: 프론트 소비 필드는 노드당 id·name·label·relevance·role 5개).

**Acceptance Scenarios**:

1. **Given** 프론트 의미검색, **When** 개선 배포 후 동일 질의, **Then** 스트림 이벤트
   형태·노드 필드가 기존 계약 그대로다(추가 필드는 무해, 제거·개명 없음).

---

### Edge Cases

- 후보 전체가 저점(절벽도 상위권도 없음): 최소 앵커 1개(최고점)는 항상 선발 — 결과 0건
  위장 금지, 기존 "빈 clusters = 정보" 계약 유지.
- 점수 동률·플랫 분포: 앵커 상한(기존 3) 유지 — 게이트는 줄이는 방향으로만 작동.
- `code_text` 가 빈 노드(예: 외부 심볼): 빈 값 그대로 표기(누락과 구분).
- 컬럼이 없는 TABLE(DDL 미수집): 빈 배열 + 기존 설명 필드로 표기.
- 동일 rule statement 가 한 함수에 중복: 1개로 병합(예시는 합집합, 순서 보존).
- 임베딩 없음/모델 불일치: 기존 SearchUnavailable 오류 표면화 그대로.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (선정 게이트 고도화)**: 시스템은 앵커를 **점수 구조에 적응**해 선발해야 한다
  — 1위와의 상대 격차가 큰 후보는 앵커에서 제외하고, 상위권이 촘촘하면 복수 앵커를
  유지한다(상한은 기존 3). 고정 개수·단일 절대 임계 같은 조잡한 규칙 단독 사용 금지.
  게이트 방식·상수는 골드셋 전수 A/B(`search/eval` 하네스)로 결정하고 그 근거를 spec
  산출물에 기록한다.
- **FR-002 (동반 입장 자격 재정의)**: 직행 입장(SEMANTIC_SUPPORT)과 1홉 확장의 뿌리
  (support root) 자격을 게이트와 연동해 재정의한다 — 낮은 순위 후보가 무조건 자기
  이웃을 끌고 들어오는 구조를 제거하되, 골드셋에서 확인된 "정답이 의미순위 4~12위에
  분산되는 복합 질의"의 재현율을 훼손하지 않아야 한다(재현율 우선, A/B 로 판정).
- **FR-003 (계층화 상세 — LLM 소비 프로파일)**: 아키텍트 스킬에 전달되는 결과는 계층화한다.
  - 앵커 FUNCTION: 식별자·이름·논리명·라벨·소속(파일)·요약·**원문 코드**·읽기/쓰기
    테이블·호출관계·관련도·**rule 전량(statement + example 전량, example 의 테이블 영향 포함)**.
  - evidence FUNCTION: 앵커와 동일하되 **rule/example 제외**, 대신 포함 근거(어떤 노드와
    어떤 관계로 연결되어 왔는지) 명시. **원문 코드는 포함**(사용자 필수 요구).
  - TABLE: 논리명·물리명·설명·**컬럼 전량**(이름·타입·PK 여부·논리명·설명)·포함 근거.
- **FR-004 (불필요 필드 제거·중복 제거)**: LLM 소비 프로파일에서 내부 전용 필드
  (search_text, element_id)를 제거한다. 동일 statement 의 rule 중복은 병합한다.
- **FR-005 (직렬화 수정)**: MCP 도구 응답은 **비이스케이프·비들여쓰기(compact) 텍스트
  1벌**로 전달되어야 한다 — 한글 escape 부풀림과 동일 내용 이중 전송을 제거해, CLI 가
  받는 크기가 원내용 크기와 같아야 한다.
- **FR-006 (REST 계약 불변)**: `/robo/search/semantic` 응답의 이벤트 형태·노드 필드는
  변경하지 않는다(프론트 소비 필드 id·name·label·relevance·role 실측 확인 완료).
  선정 품질 개선은 REST 에도 동일 적용되나 형태는 그대로다.
- **FR-007 (프로파일 선택 계약)**: LLM 소비 프로파일이 MCP 기본이 된다. 기존 원형
  전량(full)은 명시 옵션으로 존치한다(디버그·회귀 대조용). 기존 축약(summary,
  `_slim_clusters`)은 **삭제** — 호출자 전수 0 실측(2026-07-16), 목적(크기 절감)은
  tiered+compact 직렬화가 상위 호환으로 대체(사용자 확인, 데드코드 금지 원칙).
- **FR-008 (안전망 존치)**: 052 의 CLI 파일폴백(초대형 결과 전량 복원)은 안전망으로
  유지한다 — 본 스펙은 한도 초과의 상시 발생을 없애는 것이지 폴백을 대체하는 것이 아니다.

### Key Entities

- **앵커(anchor)**: 질의의 직접 정답 후보 — 게이트를 통과한 상위 노드. 전문 수록 대상.
- **evidence**: 앵커의 실행 문맥(호출관계 1홉)과 강한 의미 후보 — 요약+코드 수준 수록.
- **TABLE/COLUMN**: 앵커가 읽고 쓰는 테이블과 그 컬럼 스키마 — 설계 근거의 데이터 축.
- **rule/example**: 함수의 업무 규칙과 사례 — 앵커에만 전량 수록.
- **골드셋**: `search/eval` 의 질의→정답 함수 대조표 — 선정 변경의 유일한 회귀 심판.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001 (재현율 유지)**: 골드셋 전수 A/B 에서 정답 재현율이 기존 수치(shopmall
  30/30 포함) 이상 — 단 1건이라도 하락하면 게이트 상수를 재조정하거나 채택하지 않는다.
- **SC-002 (노이즈 소멸)**: 검증 질의(배송)에서 무관 도메인(가격·정산·쿠폰·회원등급·
  장바구니) 함수가 결과에 0개.
- **SC-003 (전문성)**: 결과의 모든 FUNCTION 에 원문 코드, 모든 TABLE 에 컬럼 목록 포함.
  내부 전용 필드 0개.
- **SC-004 (크기)**: 검증 질의에서 CLI 도달 텍스트가 원내용 대비 1.1배 이내(현재 2.1배).
  파일 치환 미발생.
- **SC-005 (끝까지 도달)**: verify_052 e2e 에서 legacyReferences 에 유관 노드 기록,
  아키텍트 UI 칩·팝오버 실물 스크린샷으로 확인.
- **SC-006 (프론트 무회귀)**: Analyzer 검색 UI 가 동일 질의에서 기존 계약 필드로 정상
  동작(실물 확인), 콘솔 오류 0.

## Assumptions

- 게이트의 구체 방식(상대 격차 폭, 절벽 검출 방법)과 상수는 골드셋 A/B 산출물로 확정한다
  — 본 스펙은 "적응형이어야 하고 재현율이 심판"이라는 계약만 고정한다.
- 원문 코드는 그래프에 이미 수집된 `code_text` 를 사용한다(신규 수집 없음). 빈 값 노드는
  빈 값 그대로 노출한다.
- 컬럼 스키마는 기존 HAS_COLUMN 그래프를 사용한다(신규 수집 없음).
- 052 파일폴백·프로버넌스 기록 계약(architect 측)은 본 스펙 범위 밖(무변경 소비자).
- 아키텍트 스킬의 소비 방식(마커·기록)은 변경하지 않는다 — 내용물 구성만 달라진다.
