# 02. 현재 설계와 책임 경계

## 1. 목표 파이프라인

```text
ANTLR parser AST/DDL/scan
  -> parser 구조 사실(CALL/RETURN/ASSIGNMENT/종료·분기 좌표와 표현)
  -> analyzer 구조 연결(RW, symbol resolution, table, source evidence)
  -> bottom-up callee semantic summary
  -> LLM: summary / table insight / branch별 Rule 선택·설명
  -> 결정론 검증·finding 격리
  -> trusted Rule에서 Example 전수 파생
  -> graph 저장·검색·후처리
```

결정론과 LLM의 경계는 “결정론을 많이 쓰기”가 아니라 **업무 의미를 이해해야 하는가**다.

## 2. 결정론 코드가 해도 되는 일

- AST/DDL가 제공한 줄·범위·중첩·구문 role을 읽고 분기 행 obligation으로 조립
- 원문 source와 물리 식별자·리터럴을 손실 없이 보존
- 심볼 해석에 근거한 사용자 정의 CALL 연결과 표준/외부 호출 분류
- 구조적으로 확인 가능한 table R/W 연결과 AST RETURN occurrence 소비
- bottom-up DAG/SCC와 실행 의존성 계산
- branch별 required output key 생성
- 해당 요청 evidence에 존재하는 짧은 condition/effect reference의 형식·소속 검사
- JSON/내부 DSL의 제한된 문법 검사
- accepted Rule의 참조를 정본 evidence에 연결하고 graph 관계를 파생
- accepted Rule에서 EXAMPLE 생성 및 전수 동등성 비교
- obligation = trusted + findings + unavailable 회계

여기서 Python 표기는 임의 언어 전체를 Python으로 번역하는 컴파일러가 아니다. 내부 DSL
wrapper와 참조를 기계 비교하기 위한 표기다. 코드는 source 언어의 업무 의미를 새로 해석하지
않으며, ontology/skill이 보증하지 않는 표현 변환을 만들지 않는다.

## 3. LLM이 해야 하는 일

- 현재 함수가 실제로 하는 업무의 의미 요약
- branch 좌표별로 evidence condition/effect 중 무엇이 cond/then인지 선택
- 사람이 읽을 수 있는 `nl` 설명
- 테이블 물리 정보와 사용 문맥으로부터 설명·논리적 의미를 제안
- callee summary를 이용해 caller의 의미를 보강
- 입력만으로 의미를 확정할 수 없으면 모른다고 표면화

LLM은 좌표·짧은 ID를 선택하지만, 그 선택의 **업무 의미 판단**은 LLM 책임이다. 코드는
누락된 선택을 임의로 채우지 않는다.

## 4. 폐기된 결정론 설계

다음은 다시 구현하지 않는다.

1. 위치별 값 추적과 객체 필드 상태 추적
2. 지역변수 초기값이나 런타임 값을 고정 사실처럼 전달
3. 상태코드 이름으로 성공/실패 의미 추론
4. 함수명·접두·고객 코드값으로 CALL/RW/Rule 의미 결정
5. arbitrary source expression을 언어별 대응표로 Python 의미식으로 변환
6. 분기표가 있다는 이유로 cond/then 업무 의미를 코드가 자동 결정
7. LLM 출력 누락을 source 기반 기본값으로 하이재킹

허용되는 값 정보는 source에 명시된 상수/리터럴과 callee의 **정확한 반환 표현 집합**뿐이다.
반환 표현 `STATUS_CODE`의 업무 의미는 별도 명세/상수 설명/충분한 문맥 없이는 추론하지 않는다.

## 4.1 구조 구문 생산자 계약 — 새 현재 권위

- ANTLR grammar가 구문을 식별할 수 있으면 `antlr-code-parser`의 언어별 listener가 AST JSON으로
  emit한다. analyzer에 언어별 정규식 parser를 두지 않는다.
- parser는 정확한 node type/role, start/end line, 구조 부모, 필요한 원문 표현을 보존한다.
- analyzer는 AST node를 routine/branch에 귀속하고 symbol/table/graph 계약과 연결한다.
- AST 계약이 활성화된 뒤 누락된 구조 node를 source 패턴으로 조용히 복원하지 않는다. parser
  contract failure로 좌표와 언어를 표면화한다.
- embedded SQL 문자열, 외부 문서, preprocessor 비활성 영역처럼 host-language AST가 의미를
  소유하지 않는 텍스트는 DDL parser·skill·lexing owner가 처리한다. “모든 regex 금지”가 아니라
  **grammar가 아는 구문을 analyzer가 중복 파싱하는 것**이 금지다.

### 현재 확인된 실제 결함

- 실제 C AST corpus에서 `RETURN` node는 0개다. 함수 원문에는 return이 있지만 Framework
  listener가 emit하지 않는다.
- C/Java/Python grammar에는 return rule/context가 이미 있다. listener 배선이 빠져 있다.
- PL/SQL listener는 이미 `RETURN`과 `ASSIGNMENT` node를 emit한다. 언어별 계약이 불균일하다.
- analyzer `branch_inventory.py`는 현재 `_termination_rows`, `_return_expressions`, `_calls`,
  `_assignment_pairs`, `_entry_statement_line`에서 첫 토큰·정규식·문장 종결자·괄호 개수를 사용해
  source를 재탐색한다.
- 현재 return expression 추출은 C/Java/Python/SQL의 완결된 한 줄에만 테스트돼 있다. multiline,
  inline return과 모든 지원 언어의 완전성은 보장되지 않는다.

따라서 “AST RETURN을 이미 확실히 받아 쓴다”는 설명은 틀리다. 현재는 AST **분기 범위**와 함수
원문을 결합해 return을 재추출하며, 이 legacy 경로는 parser AST 계약으로 교체해야 한다.

## 5. Rule 계약

현재 wire는 branch row별 고정 key 아래 `cond`, `then`, `extra`, `nl`을 가진다.

- row key 집합은 요청마다 required로 고정한다.
- `cond`는 `C...` / `!C...` 짧은 evidence reference 배열이다.
- `then`은 `E...` 짧은 evidence reference 배열이다.
- `extra`는 직접 evidence에 없는 권위 있는 DML/명시 오류 등 드문 의미 효과 후보다.
- `nl`은 사람이 읽는 의미 설명이다.
- Rule/Example/graph 관계는 trusted 선택에서 코드가 파생한다.

주의: 현재 Pydantic 정규식은 `C<number>`, `E<number>` 모양만 닫고 **해당 요청에 실제로
존재하는 reference enum까지 문법으로 닫지는 않는다**. 잘못된 번호는 grader가 거절한다.
문서에서 “배열이 완전히 closed”라고 부르면 오해다.

`extra`를 `then`과 합치거나 무조건 제거하지 않는다. 빈도가 낮아도 의미 손실이 되면 정확도
퇴보다. compact wire는 이 필드의 선택 차이를 해결한 뒤에만 채택한다.

## 6. Example 계약

- EXAMPLE은 LLM이 별도 생성하지 않는다.
- trusted Rule의 cond/then을 시스템이 Python형 내부 표기로 파생한다.
- 모든 trusted Rule에 대해 EXAMPLE 파생 여부와 내용 동등성을 전수 검사한다.
- rejected/unverified Rule에서 trusted EXAMPLE을 만들지 않는다.
- 표기 parser의 통과가 의미 정확도 증명은 아니다. Rule 선택이 원 evidence와 맞는지는 별도
  검증한다.

## 7. Summary 단일 문서 계약

`search_text` 별도 필드는 폐기됐다. 사람 표시·검색·callee bottom-up 전달은 canonical
`summary` 하나를 사용한다. 단, 한 문자열에 목적 없는 사실을 줄줄 복사하라는 뜻은 아니다.

summary가 담아야 할 최소 의미:

- 핵심 목적
- 결과를 바꾸는 중요한 조건/상태
- 주요 데이터 읽기·쓰기와 외부 효과
- 중요한 반환/오류 의미
- callee에서 확정된 의미 중 caller 해석에 필요한 것

물리 CALL/RW/RETURN 목록 전체는 이미 구조 데이터로 있으므로 summary에 중복 나열하지 않는다.
필요한 것만 자연스러운 의미 문장에 녹인다. 물리명은 원문을 보존하고, 상태값 의미는 증거 없이
추론하지 않는다.

현재 결함: `llm/prompts/common/summary_contract.md`는 purpose-only를 요구하면서 위 의미를
제외한다. 생산 코드가 별도 semantic renderer 없이 그 문자열 하나를 그대로 검색·bottom-up에
사용하므로 정보 열화 위험이 있다. TA-144가 해결 전이다.

## 8. 실행 의존성과 동시성

- summary 요청은 shared priority semaphore에서 최우선이다.
- 한 summary가 확정되면 해당 node를 즉시 publish하여 parent bottom-up과 후처리를 깨운다.
- Rule/Table은 전역 summary 완료를 기다리지 않고 자신의 입력이 준비되면 실행한다.
- concurrency 64는 유지한다.
- Rule은 큰 유한 작업을 먼저 처리하는 LPT priority를 쓰되 summary를 추월하지 않는다.
- 요청 순서만 바꿔 KV locality를 추정 최적화하지 않는다. 실제 cache hit 증거가 필요하다.
