## 4. “출력 반복”에 대한 정확한 결론

긴 호출을 전부 반복 출력 반복로 부르면 안 된다.

- 최신 run은 Rule deadline 없이 종료했다.
- 긴 호출은 출력 토큰 증가와 거의 선형으로 함께 증가한다.
- Rule raw JSON 955,455자 중 minified JSON은 572,576자다.
- 구조 공백 382,879자, 약 40.1%가 의미 없는 구조 표현 비용이다.
- `nl` 260,245자, cond JSON 64,070자, then 55,891자, extra 8,891자다.

즉 정상적으로 필요한 행별 의미 출력과 불필요한 JSON 공백 생성이 함께 있다. 반복 guard는
비정상 동일 토큰 루프를 막되, 단순히 max token에 닿았다는 이유만으로 전체 후보를 “출력 반복”라고
오판하지 않는다.

## 5. 반증되어 폐기된 성능 접근

1. **CSV cond/then**: Rule 출력은 줄었지만 trusted -54. 정확도 교환이라 폐기.
2. **positional tuple**: 희소 `extra` 의미를 잃을 수 있어 폐기.
3. **`extra`를 `then` union에 합침**: 모델 선택 경계가 무너져 대규모 invalid effect 발생.
4. **5-row/6-row 고정 축소**: 콜 수와 경합이 늘고 wall/quality가 악화.
5. **입력 크기만으로 분할**: 실제 지연은 출력 구조와 더 강하게 연결돼 불충분.
6. **prompt에 compact라고 부탁**: 강제가 아니어서 구조 공백을 제거하지 못함.
7. **sibling prefix-family 요청 정렬**: wall -27초지만 trusted -10, 단일 run 인과도 불명확.
8. **논리 input token 합계로 KV cache 판정**: cache 사용량과 다른 지표라 증명 불가.

## 6. 현재 유력 후보: compact regex grammar

현재 SGLang OpenAPI는 요청별 top-level `regex`를 지원한다. 서버 launch 설정을 바꾸지 않고
named fields와 배열을 유지하면서 구조 공백을 문법으로 금지하는 확인 호출를 수행했다.

| 실제 Rule probe | 기존 출력 | regex 출력 | 감소 | 의미 선택 |
|---|---:|---:|---:|---|
| 1 row | 79 | 47 | -40.5% | cond/then/extra 동일 |
| 7 rows | 1,315 | 623 | -52.6% | refs/extra 동일 |
| 8 rows | 1,276 | 951 | -25.5% | refs/extra 동일 |
| 8 rows, extra 존재 후보 | 876 | 541 | -38.2% | refs 동일, old extra 1 vs new 0 |

결론: 토큰 절감 효과는 강하지만 정확도 동등성은 아직 증명되지 않았다. 특히 old extra가 맞는지
new omission이 맞는지 source/evidence를 직접 판정해야 한다. “regex가 의미를 바꿨다”와
“기존 출력의 extra가 잘못이었다”를 구분하지 않고 채택/폐기하면 안 된다.

## 7. 다음 성능 연구 질문

1. whitespace-free regex가 `extra` 선택을 바꾸는 원인은 문법 제약, field order, decode path 중 무엇인가?
2. evidence-specific enum까지 닫으면 invalid ref와 생성 탐색을 함께 줄일 수 있는가?
3. `nl` 길이를 의미 손실 없이 bounded one-sentence template로 강제할 수 있는가?
4. row batch 기준을 입력 문자가 아니라 예상 output refs/rows/rare-extra 구조로 정할 수 있는가?
5. 요청별 regex가 response cache key, raw evidence, usage logging에 정확히 포함되는가?
6. 서버 로그의 radix-cache hit와 client 요청 순서를 직접 조인할 방법이 있는가?

공식 SGLang 문서/소스와 현재 배포 OpenAPI·실확인 호출를 모두 확인한다. 서버 설정 변경을 해결책으로
삼지 않는다.

## 8. 공식 SGLang 조사 결과 — 2026-08-05

- [SGLang Structured Outputs 공식 문서](https://sgl-project.github.io/advanced_features/structured_outputs.html)는
  JSON schema, regex, EBNF 중 요청당 하나를 사용할 수 있고, OpenAI 호환 API에서
  `extra_body={"regex": ...}`를 지원한다고 명시한다. XGrammar는 세 형식을 모두 지원하는 기본
  backend이며 성능·기능상 권장된다.
- 같은 공식 문서는 constraint가 **형식 준수**를 보장한다고 설명하지만, 더 나은 출력 품질을
  위해 prompt에도 원하는 형식을 명시하라고 한다. 이는 형식 적용와 의미 정확도가 별개라는
  현재 extra 차이 실측과 일치한다.
- SGLang의 현재 공식 문서는 GrammarManager가 grammar를 compile하고 재사용을 위해 cache하며,
  유일한 다음 토큰 경로는 jump-forward할 수 있다고 설명한다. 따라서 요청별 동적 regex도
  compile 비용과 cache cardinality를 실측해야 하지만, 구조 토큰을 강제로 제거하는 접근 자체는
  서버가 의도한 사용 방식이다.
- [공식 server arguments](https://github.com/sgl-project/sglang/blob/main/docs/advanced_features/server_arguments.md)는
  JSON 구조 공백을 전역으로 끄는 `--constrained-json-disable-any-whitespace`를 제공한다. 그러나
  이는 launch 설정이며 이번 범위에서 변경 금지다. 요청별 regex가 같은 효과를 필요한 Rule에만
  적용하는 현재의 in-scope 대안이다.

공식 자료만으로 compact regex의 **의미 동등성**은 증명되지 않는다. production 채택 여부는
현재 모델·현재 prompt·현재 evidence의 제한 replay와 직접 의미 대조가 결정한다.

## 8.1 딥리서치 결과 — 2026-08-05 (8개 질문 심층 분석, 원문은 사용자 보유)

확정 사실(1차 근거 포함, TA-146/147 판정 계약에 반영):

1. **요청 수준 공백 제거는 regex/EBNF로만 가능** — `constrained_json_whitespace_pattern`은
   xgrammar가 무시(sglang #8250), `any_whitespace=False`는 서버측 전용. json_schema 경로 불가.
2. **거대 단일 regex보다 EBNF+공유 규칙** — 참조 집합을 `cref ::= "C12"|...` 한 규칙으로 재사용.
   요청별 동적 문법은 매번 fresh compile(캐시 키=문법 문자열)이지만 sub-second라 decode 76초
   대비 무시 가능. 단 대형 문법은 grammar queue를 막을 수 있어 크기 관리 필수.
3. **extra 1→0은 constrained decoding의 분포 왜곡으로 설명 가능**(Park et al. NeurIPS 2024,
   DISC 2504.09135, JSONSchemaBench §6) — whitespace 제거·field 재정렬·enum 폐쇄·nl 상한을
   **동시에 바꾸지 말고 각각 1회 A/B로 분리**해야 원인이 갈린다.
4. **문자열 대형 enum 금지** — 고동시성 garbage(xgrammar #460, sglang #2414)가 우리 정수 ID
   전환 이력과 일치. 참조 폐쇄는 정수 ID+EBNF 공유 규칙으로만.
5. **nl 상한은 schema maxLength로 불가**(xgrammar #749 — pattern과 결합 시 조용히 무시),
   regex 수량자 `"[^"\\]{1,N}"`만 신뢰 가능. N은 실측 p95+여유, 종결문자 클래스로 마감.
6. **jump-forward 이득은 기대하지 않는다**(sglang #8954 미미, #2518 역행 보고) — 이득 주축은
   출력 토큰 자체 감소.
7. **Qwen3 thinking-off + xgrammar 구조화 실패 버그(sglang #6675)가 우리 설정과 정확히 겹침**
   — 배포 버전 확인이 문법 최적화 전체의 전제. `/get_server_info` 확인 호출로 버전 확인 필요.
8. tail 완화용 클라이언트 배치 크기 균질화는 정확도 중립이나 총 wall 불변(decode-bound) —
   후순위. TTFT 확인 호출가 유일한 무침습 radix 관측법 — 진단용.

채택 순서(각각 독립 1회 A/B, 합격선 trusted ≥4,016 & extra 건수 불변):
① whitespace-free EBNF ② nl regex 상한 ③ 정수 ID 참조 폐쇄 ④ 배치 크기 균질화.

2차 리서치 확정(2026-08-05, 원문은 사용자 보유):

- `{1,N}` 수량자는 **유니코드 코드포인트 단위**(공식 EBNF 사양) — 한글 N자는 그대로 N.
  단 구버전 xgrammar regex 변환기는 `{x,y}` 자체를 거부한 이력(0.1.20 docstring) —
  적용 전 `{1,5}` 초소형 확인 호출 1콜로 수락 확인(거부는 컴파일 단계 명시 에러라 안전).
- `ebnf` extra_body는 PR #2526, 늦어도 SGLang v0.4.3부터. 우리 dev build는 1콜 확인 호출로 판정.
- xgrammar EBNF = GBNF 기반+확장. 공유 규칙(`cref ::= "C12"|...`) 재사용은 사양상 정상,
  미정의 rule은 위치 찍힌 명시 에러. 문자 클래스에서 `\d` 축약형 거부 — `[0-9]`로 풀 것.
  **정정**: `MAX_REPETITION_THRESHOLD`는 llama.cpp 상수이지 xgrammar 한계가 아님.
  xgrammar rule 수/크기 하드 상수는 문서에 없음 — 실패 모드는 컴파일 시간·재귀 한계·거부.
- **#6675의 수정 버전은 존재하지 않음**(PR #6743 미병합). 발동 조건 = 서버가
  `--reasoning-parser`로 기동 + thinking off(`</think>` 미출현 → 지정한 형식이 적용되지 않음).
  "정상으로 보이는 출력"이 적용의 증거가 아닐 수 있으므로, 문법 A/B 전에 **형식 적용
  판별 확인 호출 1콜**(모델이 자발적으로 내지 않는 형태를 지정, 예 regex `XQZV-[0-9]{4}`)이
  최우선. 단 이 배포의 2026-08-03 실측(형식 밖 출력 5/5 차단, xgrammar 쉼표/공백 교착)은
  형식 지정이 실제 적용된다는 직접 증거다 — 교착은 형식 지정이 없으면 일어나지 않는다.
  재확인 확인 호출는 그래도 수행한다(설정 변경 가능성 배제).
- 고동시성 garbage(#460/#2414)는 enum 크기·alternation 수가 아니라 **배치/스케줄러 인프라
  버그 클래스**(마스크 오배정; 혼합 배치가 트리거). 안전한 alternation 규모의 문헌 경계는
  없음 — 검증은 실운영과 같은 혼합 배치·동시성 64에서 {32,128,512} 스윕으로만.
  EBNF 공유 규칙은 어느 경우든 문법 크기 최소화 가치가 있어 유지.

J단계 진입 확인 호출 체크리스트(서버 변경 0, 각 1콜): ① 형식 적용 확인 ② `ebnf` 수락
③ `{1,N}` 수량자 수락 ④ 한글 nl 상한이 정확히 N자에서 닫히는지.

## 8.2 딥리서치 질문↔답변 원장 (2026-08-05, 2회 왕복 — 답변 원문은 사용자 보유)

**1차 (8문항)** — 질문: ①형식 적용 디코딩의 토큰당 오버헤드·jump-forward 실효
②요청별 regex/EBNF의 compile 비용·캐시 ③문법 제약이 의미 선택(extra)을 바꾸는 메커니즘
④참조 enum 폐쇄의 득실 ⑤nl 길이 제한 방법 ⑥출력 구조 기반 배칭 ⑦cached_tokens=0
배포에서 KV 관측법 ⑧Qwen3+xgrammar 알려진 이슈.
답변 요지: 오버헤드 near-zero(<40µs/token)이나 대배치에서 비병렬 검증 패널티(Pre³ 논문
—40% 사례), jump-forward는 버전 의존·역행 보고(#8954/#2518)라 **이득 주축은 출력 토큰
자체 감소**. 캐시 키=문법 문자열이라 요청별 문법은 매번 fresh compile(0.12~0.3s급 — 우리
decode 76s 대비 무시 가능, 단 대형 문법의 grammar queue 주의). extra 변화는 분포 왜곡
(Park NeurIPS'24 GAD, DISC 2504.09135, JSONSchemaBench §6 OOD 사례)+field 순서 효과 —
**변경 축들을 동시에 바꾸지 말 것**. 문자열 대형 enum은 고동시성 garbage(#460/#2414)와
우리 실측이 일치 — 정수 ID+EBNF 공유 규칙 권장. nl은 json_schema maxLength 불가(xgrammar
무시, #749) — regex 수량자만 신뢰. 배칭 균질화는 tail만 완화(총 wall 불변). KV 관측은
TTFT 확인 호출가 유일한 무침습법(radix는 prefill만 가속). thinking-off 문법 미적용 버그
(#6675)가 우리 설정과 겹침 — 최우선 확인 권고. 요청 수준 공백 제거는 regex/ebnf만 가능
(`constrained_json_whitespace_pattern`은 무시 — #8250).

## 8.4 J단계 확인 호출 실측 (2026-08-05, 각 1콜 — 서버 설정 무변경)

1. **형식 적용 ✓**: regex `XQZV-[0-9]{4}` 강제 → `XQZV-2025` 생성. 이 배포에서 형식 적용
   작동 확정 — #6675(reasoning-parser 미적용) 우려 완전 배제.
2. **ebnf extra_body ✓**: `root ::= "PING"` → `PING`. 수락·강제 확인.
3. **`{1,N}` 수량자 ✓**: `[a-z]{1,5}` 수락, 5자 마감. 구버전 거부 이슈 없음.
4. **한글 + 계획 형태 ✓**: `"[^"]{1,8}"` → `"안녕"` 정상(quoted 부정 클래스가 한글 통과).
5. **계수 단위 = 코드포인트 확정**: `"[^"]{1,3}"`에서 한글 2자(=UTF-8 6바이트) 허용 —
   바이트 계수였다면 1자에서 닫혔어야 함. 리서치 답변과 일치.
6. **신규 제약(설계 금지 추가)**: 양성 유니코드 범위 클래스 `[가-힣]{1,5}`는 수량자만
   강제되고 문자 클래스가 강제되지 않음(출력 `**[AI`) — ASCII 클래스(`[A-Z]` → HELLO 강제)
   와 부정 클래스는 정상. **EBNF/regex 설계에서 양성 유니코드 범위 사용 금지** —
   nl 상한은 부정 클래스 `"[^"\\]{1,N}"`, 참조는 ASCII만 사용(현 계획과 일치, 무영향).
7. 요청 인코딩 주의: regex에 비ASCII를 넣을 경우 요청 body를 UTF-8 바이트로 명시 전송해야

## 8.5 J-3 A/B 실측 — 후보 ①(출력 공백 제거, EBNF) 2026-08-05

**설계**: A측은 마지막 cold의 저장 record(동시성 64, 재호출 없음). B측은 **같은 system/user
바이트**로 형식 지정만 EBNF로 바꿔 순차 호출. 추가로 **역실험 대조군 A_seq** — 형식은
원래(json_schema)대로 두고 부하만 B와 같은 순차로 맞춰, 차이의 원인이 형식인지 부하인지
가른다(principles §4). production 코드 무변경 → prompt byte identity 구조적 보장.

**표본**: 33 record / 160 행. `extra` 보유 record **9건 전량** + 행수 1~8 층화 각 3건
(선정 규칙을 스크립트에 고정 — 결과를 보고 바꿀 수 없음).

| 집합 | cond 오류 | ret 누락 | extra | nl 참조ID 노출 | 출력 토큰 | 지연 |
|---|---|---|---|---|---|---|
| A (기록, 동시성 64) | 7 | 2 | 9 | 18 | 16,801 | 2,203s |
| A_seq (대조, 순차) | 5 | 0 | 6 | 8 | 17,040 | 136s |
| **B (형식 지정, 순차)** | **1** | **0** | 1 | 19 | **10,291** | **92s** |

판정 기준은 프롬프트 안에 이미 있는 결정론 정답을 썼다 — 분기표 `rows[k].when`이 정답
경로이고 `direct`의 `ret` 효과는 `then`에 포함되어야 한다. 검증용 LLM 호출은 하지 않았다.

**확정된 사실**

1. **출력 토큰 -38.8%(vs 기록) / -39.6%(vs 동일 부하)**, 문자 -44.0%, 지연 -32.5%.
   공백 0(`canonical_equal` 33/33), 행 키 누락·추가 **0**.
2. **구조 정확도가 올라간다**: cond 오류 7→1, ret 누락 2→0. 부하만으로는 설명되지 않는다
   (같은 순차 조건의 A_seq도 5건 오류). **역실험으로 "저부하가 원인" 가설은 반증됨.**
3. **동시성 64 자체가 품질을 깎는다(신규 발견)**: 같은 형식·같은 프롬프트인데 동시성 64는
   순차 대비 cond 오류 5→7, 참조ID 노출 8→18, 미검증 extra 6→9. 리서치가 지목한
   "혼합 배치 마스크 오배정" 계열과 방향이 일치한다. K단계에서 별도로 다룰 사안.
4. **`extra` 감소는 신뢰 내용의 손실이 아니다**: 코퍼스의 extra 보유 9건을 원본 run의
   판정과 대조하니 **9건 전부 격리**(unverified 8 + rejected 1)였고 **인정된 것은 0건**이다.
   사유는 "이 행의 직접 source에서 증명할 수 없음"이 대부분이고, 실제 소스를 열어보니
   오류 메시지 문자열(`"..._i0002 처리중 ... Error"`)에서 테이블명을 읽어 insert로 단정한
   환각이었다. 따라서 B의 extra 1건은 **finding 8건 감소**를 뜻한다.
5. **합격선 "extra 건수 불변"은 현 기준선에서 노이즈를 보존하는 조건이 된다.** 이 기준은
   then-union 실험이 extra 의미를 대량 파괴한 사건에서 나왔는데, 현 baseline의 extra는
   100% 미인정이다. 기준을 "**인정된(trusted) extra 건수 불변**"으로 바꾸는 것이 원래
   의도에 맞는다 — 계약 변경이므로 사용자 판단 사항으로 남긴다.
6. **개선되지 않은 축**: `nl`이 내부 참조 ID를 사람 문장에 노출하는 문제
   (예: "조건 C868이 성립하지 않고 C865가 성립할 때 E1 호출"). B 19/160행,
   기록 A 18/160행으로 **production 대비 동등**이나, 저부하 A_seq은 8행이라 형식 지정이
   이 축을 개선하지는 않는다. 후보 ②(nl 상한)와 별도 축이며 같은 A/B에 섞지 않는다.

**남은 관문(04 §5)**: 전체 cold에서 trusted ≥4,016·obligation 4,100·unavailable 0(K단계),
전체 테스트 + prompt byte identity, wall 개선 확인. production 적용에는 호출별 문법을
요청에 싣는 경로가 필요하다(현재 `extra_body`는 config 단위 고정) — 합격 확정 후 spec 116.

## 9. AST 구조 사실 전환의 성능 측정 계약

RETURN/CALL/ASSIGNMENT/종료/조건 구문을 parser AST로 옮기는 TA-151은 우선 정확도·유지보수
수정이다. 빨라질 것이라고 추정하지 않는다. 전환 전후 다음을 같은 corpus에서 측정한다.

- parser wall, AST JSON 파일 수·총 bytes·node type별 수
- analyzer step2/step6/step7 wall과 중복 source lexing 시간
- Rule evidence bytes와 전체 input/output tokens
- RETURN/branch obligation의 missing/extra/wrong-owner
- 공식 cache-off cold wall과 trusted/findings/unavailable

AST node를 전부 prompt에 복사하면 입력 토큰이 늘 수 있으므로 금지한다. analyzer는 필요한 좌표와
짧은 evidence ref만 생성한다. AST 전환과 compact Rule wire를 한 A/B에 섞지 않고 원인을 분리한다.
