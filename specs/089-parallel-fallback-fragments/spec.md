# 089 — 폭주 폴백의 조각 분석을 병렬화

작성: 2026-07-23. 근거: run20 실측에서 **폭주 폴백 사슬이 step7 꼬리를 만들었다**.

## 원인 (로그로 확정)

`run_rules_fallback` 은 조각을 `for frag in fragments: await ...` 로 **직렬** 분석했다.
조각 4개면 콜 4번(각 p50 31초)이 순차로 쌓이고 그 뒤 병합 1콜이 붙는다.

run20 타임라인:

| 시각 | 사건 |
|---|---|
| 16:59:43 | 반복 폭주 감지 발동 (`Bank_005_CSB_Check` — **작은 함수**) |
| 17:01:50 | 폴백 병합 콜 완료 |
| 17:02:28 | 폴백 병합 콜 완료 = **step7 종료 시각과 일치** |

감지 → step7 종료까지 **165초**. 그동안 다른 노드는 거의 끝나 GPU 가 놀았다.

구조적 문제: 투입 우선순위가 "큰 함수·긴 사슬 먼저"라 **작은 함수가 맨 뒤에 배치**되는데,
폭주는 크기와 무관하게 터진다. 그래서 가드레일의 복구 경로가 하필 겹칠 일감이 없는
시점에 직렬로 돌아, **안정성 장치가 성능을 깎는** 형태가 됐다.

## 계약 (변경 후)

- 조각 분석을 `asyncio.gather` 로 동시에 돌린다. `gather` 는 **입력 순서를 보존**하므로
  병합 입력 리스트가 순차 실행과 동일하다 → **산출물 불변**.
- 부분 실패 정책 유지: 조각 하나가 실패하면 그 조각만 건너뛰고 나머지는 계속(FR-026).
- `BudgetExceededError` 는 `return_exceptions=True` 로 수거한 뒤 즉시 재전파(회로 차단기).
- 투입 순서(spec 082)는 건드리지 않는다 — 순서 재배치는 두 번 다 느려졌다(spec 085).
