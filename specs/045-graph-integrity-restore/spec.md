# Feature Specification: 분석 그래프 정합성 복원 — 헌법 위반 시정 + 소비자 계약 이름 정합

**Feature Branch**: `045-graph-integrity-restore`

**Created**: 2026-07-13

**Status**: Draft

**Input**: 2026-07-13 DRY/정합 전수조사 (`docs/작업보고내용/2026-07-13-analyzer-DRY조사.md`) 에서 **실제 Neo4j 쿼리·실제 artifact 파일로 실측 확정**된, "지금 실제로 틀리게 동작하는" 항목만 모은다. 구조 중복(동작 불변 리팩터)은 **spec 046** 으로 분리한다.

---

## 배경 — 왜 이 스펙인가

이 스펙은 **새 기능이 아니라 헌법(`.specify/memory/constitution.md`) 준수 복원**이다. 조사에서 확정된 결함이 대부분 헌법 원칙을 정면으로 위반하고 있었다.

| 헌법 조항 | 현재 위반 사실 (실측) |
|---|---|
| **Cost & Safety Constraints** — *"Each run is destructive by policy: it wipes the Neo4j graph (`DETACH DELETE`) … a run is a full rebuild"* | `wipe_graph` 가 `DataSource` 를 예외 보존하도록 바뀌어 full-rebuild 정책에서 이탈. 게다가 그 **자식**(`:Schema`/`:Table`/`:Column`)은 계속 삭제되어 **엣지 0개의 좀비 DataSource** 만 남는 반쪽 상태 |
| **IV. No Silent Failure** — *"Returning a quietly empty result is forbidden"* | 소스 파일 read 실패가 **로그 0건**으로 빈 결과를 반환 → 노드에 `code_text` 속성이 **아예 부재**한 채 run 이 "성공" 종료 |
| **III. Single Source of Truth** | `Table.logical_name` 이 저장 경로(`to_item`)에 없어 **Neo4j 에는 22개 전부 / artifact 에는 22개 전부 빈값** — 진실이 두 개 |

추가로, analyzer 가 저장하는 속성명과 소비자(프론트)가 읽는 이름이 어긋나 **화면에 데이터가 영구히 안 보이는** 계약 불일치가 있다.

**supersede 대상**: `specs/016-node-display-properties/spec.md` 의 **FR-004** (아래 FR-014 참조).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 분석을 다시 돌려도 그래프가 깨끗하고 예측 가능하다 (Priority: P1)

분석가가 `/analyze` 를 실행하면, 이전 run 의 잔재가 **하나도 남지 않은** 상태에서 새 그래프가 만들어진다. 절반만 남은 노드(껍데기 DataSource, 자식 잃은 부모)가 섞여 다음 분석·검색·화면을 오염시키지 않는다.

**Why this priority**: 헌법이 못박은 "매 run = full rebuild" 계약이다. 지금은 반쯤 지워진 상태가 남아 **다음 분석의 입력이 오염**된다. 그래프가 진실의 기준이므로 여기가 무너지면 아래 모든 것이 무의미하다.

**Independent Test**: 분석 1회 실행 후 그래프 전체 노드 수를 센다. 이전 run 의 노드가 0개여야 하고, 어떤 라벨도 "부모만 남고 자식이 없는" 상태가 아니어야 한다.

**Acceptance Scenarios**:

1. **Given** 이전 run 의 노드가 1,700개 이상 남아있는 그래프, **When** 새 분석을 시작, **Then** 초기화 직후 그래프의 노드 수는 **0**이다 (라벨 무관, 예외 없음).
2. **Given** 초기화 직후, **When** 분석이 진행, **Then** 새로 만들어지는 노드만 존재하며 옛 run 의 노드는 하나도 섞이지 않는다.
3. **Given** 분석 완료 후, **When** 그래프에서 임의의 부모 노드를 골라 자식 관계를 조회, **Then** "부모만 있고 자식이 통째로 없는" 껍데기 노드가 존재하지 않는다.

### User Story 2 - 소스를 못 읽으면 조용히 넘어가지 않고 알려준다 (Priority: P1)

분석기가 소스 파일을 읽지 못하면(파일 이동/삭제/경로 오류/인코딩 문제), 그 사실이 **로그로 표면화**된다. 지금처럼 "성공했습니다"라고 끝내놓고 화면의 코드 패널만 비어 있는 일이 없다.

**Why this priority**: 헌법 IV 정면 위반이다. 지금은 **"파일을 못 읽었다"와 "이 노드는 원래 코드가 없다"를 아무도 구분할 수 없다.** 조용한 데이터 손실은 검색 품질 저하(BM25 재료 소실)로도 번지는데, 그 사실조차 계측되지 않는다.

**Independent Test**: 소스 파일 하나를 일부러 지운 뒤 분석을 실행한다. 경고 로그가 최소 1건 남고, 완료 로그에 "원문 없는 노드 N개"가 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 노드가 참조하는 소스 파일이 존재하지 않는 상태, **When** 분석 실행, **Then** 그 파일 경로를 담은 경고 로그가 **최소 1건** 남는다.
2. **Given** 같은 상태, **When** AST 적재 단계가 끝남, **Then** 완료 로그에 **원문 누락 노드 수**가 숫자로 표시된다.
3. **Given** 소스를 읽지 못해 테이블 R/W 관계를 못 뽑은 파일이 있음, **When** 링킹 단계 완료, **Then** 그 파일이 건너뛰어졌다는 경고가 남는다 (지금은 아무 흔적 없이 관계가 0건이 된다).
4. **Given** LLM 분석 단계에서 일부 노드가 처리되지 못함, **When** 단계 완료, **Then** 완료 로그의 `분석됨 + 실패 + 건너뜀` 합계가 **전체 노드 수와 일치**한다 (지금은 어디에도 안 세어지는 노드가 있어 합계가 안 맞는다).

### User Story 3 - 화면에서 변수·상수·함수의 정보가 실제로 보인다 (Priority: P1)

사용자가 그래프에서 변수/상수/함수 노드를 클릭하면, 저장돼 있는 정보(타입·값·주석·파라미터)가 **화면에 실제로 표시**된다.

**Why this priority**: 데이터는 이미 그래프에 **정상 저장돼 있는데** 화면이 다른 이름으로 찾고 있어서 안 보인다. 즉 **분석 품질과 무관하게 제품이 비어 보인다.** 데모에서 바로 드러난다.

**Independent Test**: 변수 노드를 클릭해 "타입" 행에 값이 뜨는지, 상수 노드에 값이 뜨는지, Java 메서드에 파라미터·반환타입이 뜨는지 눈으로 확인한다.

**Acceptance Scenarios**:

1. **Given** 그래프에 타입 정보가 저장된 변수 노드, **When** 노드를 클릭, **Then** 상세 패널의 "타입" 행에 그 값이 표시된다 (현재: 영구 공백).
2. **Given** 값이 저장된 상수 노드(`#define MAX 100`), **When** 노드를 클릭, **Then** 그 값이 표시된다 (현재: 안 보임).
3. **Given** 주석/어노테이션이 저장된 함수·변수·타입 노드, **When** 노드를 클릭, **Then** 그 내용이 표시된다 (현재: 컨테이너 카드에서만 보임).
4. **Given** Java 메서드 노드, **When** 노드를 클릭, **Then** 파라미터·반환타입·소속 컴포넌트가 표시된다 (현재: 라벨 필터에서 누락돼 영구히 안 보임).

---

### User Story 4 - 산출물 파일이 그래프와 같은 사실을 말한다 (Priority: P2)

분석 결과 파일(artifact)을 열어보면 그래프에 저장된 것과 **같은 값**이 들어있고, 같은 내용이 여러 파일에 **중복 저장되지 않는다**.

**Why this priority**: artifact 는 검증의 기준선이다. 지금은 그래프에는 값이 있는데 artifact 에는 빈값이라 **검증 자체가 무의미한 사각지대**가 있고, 같은 원문이 두 파일에 통째로 중복돼 산출물이 원본 소스의 3.6배로 부푼다.

**Independent Test**: 분석 후 그래프의 테이블 논리명과 artifact 의 테이블 논리명을 대조한다. 그리고 두 artifact 파일에 같은 원문이 중복돼 있는지 바이트 단위로 센다.

**Acceptance Scenarios**:

1. **Given** 분석 완료, **When** 그래프의 테이블 논리명과 artifact 의 테이블 논리명을 대조, **Then** **완전히 일치**한다 (현재: 그래프 22개 보유 / artifact 22개 전부 빈값).
2. **Given** 분석 완료, **When** 산출물 파일들에서 코드 원문의 총 바이트를 집계, **Then** 같은 원문이 **두 번 저장되지 않는다** (현재: 842 KB 가 순수 중복).
3. **Given** 산출물 카테고리 정의, **When** 정의된 항목과 실제 만들어지는 항목을 대조, **Then** **아무도 만들지 않는 유령 항목이 0개**다 (현재: 3개).

---

### User Story 5 - 데이터 계보(lineage)가 엉뚱한 코드에 붙지 않는다 (Priority: P2)

카탈로그에서 받은 데이터 계보 정보를 코드에 연결할 때, 이름이 **부분적으로만 비슷한** 엉뚱한 코드에 붙지 않는다.

**Why this priority**: 조용한 실패보다 나쁜 **조용한 오답**이다. `a.sql` 이 `xxa.sql` 에 매칭돼 잘못된 관계가 그래프에 박히고, 아무도 그 사실을 모른다. 그래프가 거짓을 말하기 시작한다.

**Independent Test**: 이름이 서로의 접미사가 되는 두 파일(`a.sql`, `xxa.sql`)이 있는 상태에서 계보를 연결하고, 관계가 올바른 파일에만 붙는지 확인한다.

**Acceptance Scenarios**:

1. **Given** `a.sql` 과 `xxa.sql` 이 모두 존재, **When** 카탈로그 계보의 `a.sql` 을 연결, **Then** 관계가 `a.sql` 에만 붙고 `xxa.sql` 에는 붙지 않는다.
2. **Given** 계보의 이름이 여러 코드에 똑같이 해당될 수 있음, **When** 연결 시도, **Then** 관계를 **추측해서 붙이지 않고** 경고를 남긴 뒤 건너뛴다.

---

### Edge Cases

- **초기화 시 다른 서비스 데이터**: 같은 데이터베이스를 쓰는 다른 서비스(카탈로그의 데이터소스 등록, 아키텍트의 설계 그래프)의 데이터도 함께 삭제된다. 이는 헌법의 full-rebuild 정책상 **의도된 동작**이며, 해당 서비스는 분석 후 자기 데이터를 다시 등록·생성해야 한다 (Assumptions 참조).
- **소스 파일 전체를 못 읽는 경우**: 한 파일도 읽지 못하면 그 파일의 모든 노드가 원문 없이 만들어진다. 이 경우에도 run 은 완주하되, **원문 누락 노드 수가 0이 아님이 완료 로그에 명시**된다.
- **원문이 원래 없는 노드**: 파일·라인 정보 자체가 없는 노드(외부 호출 stub 등)는 원문 누락 카운터에서 **제외**한다 — "못 읽은 것"과 "원래 없는 것"을 섞지 않는다.
- **계보 이름이 아무 코드에도 안 맞는 경우**: 관계를 만들지 않고 조용히 넘어가되, 미해결 건수를 집계에 남긴다.

## Requirements *(mandatory)*

### Functional Requirements

#### 그래프 초기화 정책 (헌법 Cost & Safety 복원)

- **FR-001**: 분석 시작 시 그래프 초기화는 **라벨·소유자를 가리지 않고 전체 노드와 그 관계를 삭제**해야 한다. 어떤 노드 종류도 예외로 보존하지 않는다.
- **FR-002**: 초기화 로직의 설명(docstring)은 **사실만** 담아야 한다. 현재 문서에 적힌 *"카탈로그의 삭제 규칙도 같은 규칙"* 이라는 근거는 **사실이 아님이 확인**되었으므로(카탈로그는 "지목한 데이터소스와 그 자식을 지우는" 정반대 규칙이며, 문서가 지목한 경로 자체가 존재하지 않음) 제거해야 한다.
- **FR-003**: 초기화가 **같은 데이터베이스를 공유하는 다른 서비스의 데이터도 삭제한다**는 사실을 문서에 명시해야 한다 (숨은 부작용 금지).

#### 조용한 실패 제거 (헌법 IV 복원)

- **FR-004**: 소스 파일 읽기에 실패하면, 실패한 **파일 경로와 원인**을 담은 경고를 남겨야 한다. 조용히 빈 결과를 반환하는 것은 금지한다.
- **FR-005**: AST 적재 단계 완료 시, **파일·라인 정보가 있는데도 원문을 얻지 못한 노드의 수**를 완료 로그에 방출해야 한다. 이 값이 0이 아니면 불변식 위반 신호다.
- **FR-006**: 소스를 읽지 못해 테이블 R/W 관계 추출에서 건너뛴 파일은 **경고로 표면화**해야 한다 (현재는 흔적 없이 관계가 0건이 된다).
- **FR-007**: 소스 경로 해소 시, 신뢰할 수 있는 경로 정보가 없으면 **존재하지 않을 경로를 지어내지 말고** 경고를 남겨야 한다.
- **FR-008**: 코드 분석 단계 완료 시, **`분석됨 + 실패 + 건너뜀` 의 합이 전체 대상 노드 수와 일치**해야 한다. 어느 집계에도 잡히지 않고 사라지는 노드가 있어서는 안 된다.

#### 소비자 계약 이름 정합

- **FR-009**: 변수·상수 노드의 **타입 정보**는 저장된 이름 그대로 소비자에게 노출되어야 하며, 소비자는 그 이름으로 읽어야 한다. 저장 이름과 읽는 이름이 다르면 안 된다. (현재: 저장은 `var_type`, 상세 카드는 `variable_type` 으로 읽어 **영구 공백**. 같은 프론트 안의 다른 코드는 `var_type` 을 올바로 읽고 있어 **내부 모순** 상태.)
- **FR-010**: **상수의 값**은 상세 화면에 표시되어야 한다. (현재: 상수는 `value` 로 저장하는데 카드가 `init_value` 만 읽어 값이 안 보인다.)
- **FR-011**: 함수·변수·데이터타입 노드의 **주석·어노테이션**은 상세 화면에 표시되어야 한다. (현재: 컨테이너 카드에서만 표시.)
- **FR-012**: **메서드(METHOD)** 노드도 루틴으로 취급되어 파라미터·반환타입·소속 컴포넌트가 표시되어야 한다. (현재: 라벨 필터에서 누락되어 Java/C# 메서드는 영구히 안 보인다.)

#### 산출물 정합

- **FR-013**: 테이블의 **논리명**은 저장 경로에 포함되어 산출물과 그래프가 **같은 값**을 가져야 한다. (현재: 그래프에는 있고 산출물에는 전부 빈값 → 검증 사각지대.)
- **FR-014**: 코드 **원문**은 산출물에서 **한 번만** 저장되어야 한다. 분석 결과 산출물은 LLM 분석 결과를 담는 것이 책임이며 원문의 사본을 또 담지 않는다. (현재: 원문 842 KB 가 두 산출물에 그대로 중복.)
- **FR-015**: 산출물 카테고리 정의에는 **실제로 아무도 만들지 않는 항목이 없어야** 한다. (현재: 유령 항목 3개.)
- **FR-016**: ~~노드 저장 시 **빈값 미저장 규칙**은 모든 노드 종류에 동일하게 적용되어야 한다.~~
  → **🚫 철회 (2026-07-13, 구현 중 반증).** 테이블 노드가 이 규칙에서 "벗어나 있다"고 본 것은 **오진**이었다. 다른 노드는 `SET n += item` 이라 키가 빠지면 "미저장"이지만, 테이블은 속성을 **하나씩 명시 SET**(기존 DDL 설명을 보존하는 `coalesce` 구조)한다. 여기에 빈값 제거를 적용하면 키가 빠져 값이 null 이 되고 **기존 속성이 삭제**된다 → 규칙이 아니라 **파괴**다. 두 메커니즘은 **의도적으로 다르며**, 이 사실을 코드 주석에 못박는 것으로 갈음한다.

#### 데이터 계보 정확성

- **FR-017**: 카탈로그 계보의 이름을 코드에 연결할 때는 **경로 구분자 경계**를 존중해야 한다. 이름이 다른 이름의 단순 접미사라는 이유로 매칭해서는 안 된다.
- **FR-018**: 계보 이름이 **여러 코드에 해당**하면, 하나를 추측해 고르지 말고 **경고 후 건너뛴다.**

#### 스펙 정합 (supersede)

- **FR-019**: **`specs/016-node-display-properties/spec.md` 의 FR-004 를 대체한다.**
  - **옛 FR-004 (016)**: *"코드 노드에 `code_text`(본문 원문 슬라이스)를 step6에서 저장한다(step2 소스 무파싱 불변식 보존)."*
  - **새 규칙 (045 FR-019)**: 코드 원문은 **AST 적재 단계(step2)** 가 **파일·라인 범위를 가진 모든 노드**(코드노드·컨테이너·변수·상수·데이터타입)에 **단일 지점에서** 부여한다. **"AST 적재 단계는 소스를 읽지 않는다"는 불변식은 폐기한다.**
  - **폐기 근거**: 원문은 노드 종류와 무관하게 "파일·라인이 있으면 그 원문을 갖는다"는 하나의 규칙으로 충분하며, 종류별로 채우는 단계를 나누면 분기가 생긴다. 실제 소비처가 존재함이 확인되었다 — 상세 카드(파일/함수/변수/데이터타입/비코드/SQL구문)와 아키텍트의 추적성 조회가 모두 이 원문을 읽는다.
  - 016 문서는 **그대로 보존**한다(역사 기록). 이 스펙이 그 조항을 대체한다는 사실만 명시한다.

### Key Entities

- **그래프 노드**: 분석이 만들어내는 코드·데이터 구조의 단위. 각 노드는 자기 **원문**(파일·라인 범위가 있으면)과 표시용 속성(이름·타입·값·주석)을 갖는다.
- **산출물(artifact)**: 분석 결과를 검증하기 위한 파일 묶음. **구조 산출물**(원문 포함)과 **분석 결과 산출물**(LLM 산출물)의 책임이 분리되어야 한다.
- **데이터 계보(lineage)**: 카탈로그가 제공하는 "어떤 코드가 어떤 테이블을 읽고 쓰는가" 정보. 코드에 연결될 때 **정확한 대상**에만 붙어야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 분석 시작 시 초기화 직후 그래프에 **남아있는 노드가 0개**다 (라벨 무관, 예외 0).
- **SC-002**: 소스 파일을 하나 일부러 제거한 상태로 분석하면, 그 파일에 대한 **경고 로그가 최소 1건** 남는다 (현재: 0건).
- **SC-003**: AST 적재 완료 로그에 **원문 누락 노드 수**가 숫자로 나타난다. 정상 데이터셋에서는 이 값이 **0**이다.
- **SC-004**: 코드 분석 완료 로그에서 **`분석됨 + 실패 + 건너뜀` = 전체 대상 노드 수** 등식이 성립한다.
- **SC-005**: 변수·상수 상세 화면에서 **타입 행에 값이 표시되는 노드의 비율이 100%** 다 (타입이 저장된 노드 기준. 현재 0%).
- **SC-006**: Java 메서드 노드 상세 화면에서 **파라미터·반환타입이 표시**된다 (현재 미표시).
- **SC-007**: 그래프의 테이블 논리명과 산출물의 테이블 논리명이 **전 건 일치**한다 (현재: 22건 중 0건 일치).
- **SC-008**: 산출물 전체에서 **같은 코드 원문이 두 번 저장되지 않는다** — 원문 중복 바이트 **0** (현재 842,440 바이트).
- **SC-009**: 산출물 카테고리 정의 중 **아무도 만들지 않는 유령 항목이 0개**다 (현재 3개).
- **SC-010**: 이름이 서로의 접미사인 두 파일이 있을 때, 계보 관계가 **정확히 지목된 파일에만** 붙는다 (오귀속 0건).

## Assumptions

- **전체 삭제의 대가를 수용한다 (제품 결정, 2026-07-13)**: 초기화가 같은 데이터베이스의 다른 서비스 데이터(카탈로그의 데이터소스 등록, 아키텍트의 설계 그래프)도 삭제한다. 이는 헌법의 full-rebuild 정책과 일치하며, **분석 후 해당 서비스가 자기 데이터를 다시 만들어야 한다**는 운영 부담을 감수하기로 결정했다. 향후 문제가 실제로 발생하면 그때 소유권 기반 삭제(소유 마커 라벨)를 도입한다 — 그 설계는 spec 046 의 저장 계층 통합이 선행되면 한 줄로 가능하다.
- **`var_type` 이 정본이다**: 변수·상수의 타입 속성 이름은 저장 계층·그래프·프론트의 다른 코드가 이미 쓰고 있는 `var_type` 을 정본으로 하고, 이를 벗어난 소비자(상세 카드 2곳)를 정본에 맞춘다. 반대 방향(저장 이름을 바꿈)은 그래프 속성명 변경 → 다른 소비자 연쇄 수정이라 비용이 크고 이득이 없다.
- **원문의 집은 구조 산출물이다**: 코드 원문은 구조 산출물(`ast`)에만 두고, 분석 결과 산출물(`analysis`)은 LLM 산출물(요약·역할·논리명·Example Mapping)만 담는다.
- **산출물 기준선 재생성 필요**: FR-013/FR-014 는 산출물 바이트를 바꾸므로, 바이트 동일성 검증의 **기준선을 재생성**해야 한다. 이는 의도된 변경이다.
- **프론트 저장소 동반 수정**: FR-009~FR-012 는 소비자(프론트) 쪽 수정이 필요하다. 이 스펙은 기능(사용자가 무엇을 보는가) 단위이므로 백엔드·프론트를 한 장에 묶는다 (SpecKit 멀티서비스 규약).
- **비범위 — spec 046 으로 분리**: 저장 코드 32개 복붙 통합, 소스 슬라이싱 3벌 통합, 코드 분석 단계의 전략 하드분기 제거, 확장자·루틴 라벨·비용추적의 단일진실화, 죽은 코드 삭제. 이들은 **동작 불변 리팩터**라 검증 방식(바이트 동일성)이 달라 분리한다.
- **비범위 — 동시 분석 가드**: 진행 중인 분석이 있는데 새 분석을 시작하면 서로의 그래프를 지우지만, 실사용에서 발생하지 않는 시나리오로 판단하여 이번 범위에서 제외한다 (제품 결정, 2026-07-13).
