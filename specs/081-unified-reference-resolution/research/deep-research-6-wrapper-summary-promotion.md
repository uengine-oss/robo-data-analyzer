# 코드베이스별 "외부 참조 조회 관용구" 학습과 정답지 없는 채점 — 리서치 보고서

## TL;DR
- **§4의 발견이 옳다: 대부분은 LLM 없이 결정론적 "1홉 플로우 서머리 승격"으로 잡힌다.** 이것은 정적분석에서 이미 확립된 기법(CodeQL의 `summaryModel`/propagator, StubDroid의 자동 서머리, Infer의 bi-abduction 프레임)이며, "무가공 전달"은 CodeQL이 `value`(값 보존) 스텝으로 정확히 모델링한다. 캐시 조회·널 검사·조건분기는 값 자체를 바꾸지 않으므로 무가공 전달로 안전하게 볼 수 있다.
- **정답지 없는 채점(Q2)은 "비대칭 커버리지 지표"로 가능하되 그것만으로 FP=0을 보장하지 못한다.** 진짜 조회 API는 인자 문자열의 커버리지가 매우 높고 우연 일치 API(`put`/`log`)는 낮다는 가정은 합리적이나 공개 임계값 선례는 없다. FP=0 제약을 지키려면 **커버리지 지표는 후보 발굴용으로만 쓰고, 승인은 반드시 "본문에 표준 조회 API가 있고 키가 무가공 전달된다"는 구조적 결정론 검증으로** 해야 한다.
- **권고: LLM 없는 결정론 1홉 승격을 먼저 구현하라. 사내 래퍼 학습을 위한 LLM 에이전트는 "표준 API를 전혀 안 쓰는 자체 구현" 잔여에만 한정하라. 그 잔여가 실측상 미미하면 만들지 마라.**

## Key Findings

**1. "무가공 전달 래퍼 승격"은 존재하는 기법이며 이름이 여럿이다.**
- CodeQL: **flow summary / propagator / `summaryModel`**. GitHub model packs 문서는 "라이브러리 내 메서드가 taint source, sink, 또는 propagator(= flow summary로도 불림)인지 기술한다"고 명시한다. 무가공 전달은 `value`(value-preserving step), 가공 후 전달은 `taint`로 구분. 튜플이 정확히 `Argument[N] → ReturnValue/Argument[M]` 형태로 "인자 위치 → 인자/반환 위치" 흐름을 인코딩한다.
- StubDroid(Arzt & Bodden, ICSE 2016, pp.725–735): "taint 분석 문제를 위한 정밀하고 효율적인 라이브러리 모델을 추론하는 최초의 완전 자동 접근법(the first fully automated approach for inferring precise and efficient library models for taint-analysis problems)". IFDS/IDE 스타일 데이터플로우 서머리를 라이브러리로부터 자동 구성하며, Java collections API 서머리 사용 시 데이터플로우 분석 실행시간을 대폭(최대 약 80%) 단축.
- Infer/Pulse: **bi-abduction / function summary**. 함수를 독립적으로 요약하며, "함수가 손대지 않고 남기는 상태(frame)"가 무가공 전달의 이론적 대응물. 단 Infer 서머리는 메모리-형태(separation logic) 중심이라 taint식 인자→반환 표는 아니다.
- 학계 용어: "flow-through summary", "value-preserving summary", "identity/pass-through summary", "propagator". "API alias"라는 용어를 쓰는 도구는 발견되지 않았다.

**2. 조건분기·캐시·널검사를 거쳐도 "무가공 전달"로 볼 수 있다.** 값 보존(value-preserving)의 판정 기준은 "키 심볼이 표준 조회 호출로 도달하기까지 값이 재대입·문자열연산·부분추출을 겪지 않는가"이다. §4의 실물 예시(`cache.get(jndiName)` 먼저, `if` 안에서 `lookup(jndiName)`)는 `jndiName`이라는 파라미터 심볼이 그대로 `lookup`에 전달되므로 값 보존이 성립한다. 캐시·널검사는 제어흐름 분기일 뿐 데이터 값을 변형하지 않는다.

**3. 정답지 없는 채점의 핵심은 커버리지 비대칭이지만, 그것은 후보 신호이지 승인 근거가 아니다.** Seldon(Chibotaru 등, PLDI 2019)은 정답지 없이 106개 시드 어노테이션(sources 28 / sanitizers 30 / sinks 48)만으로 21만여 후보 API에서 6,896개 역할을 추론했고 "추정 정밀도 67%"라 보고했다 — 원문: "거의 7,000개의 API 역할을 210,000개 이상의 후보 API로부터 매우 적은 감독(300개 미만 어노테이션)으로, 높은 추정 정밀도(67%)로 학습했다". 이는 "높은 정밀도"라는 저자 표현에도 불구하고 FP 33%를 의미하며, 우리의 FP=0 제약에는 채점 신호로만 쓰고 승인은 결정론에 맡겨야 함을 보여준다.

**4. 반환값 후속사용(다운스트림) 확인은 검증된 결정론 신호다.** Solar/Elf(Yue Li 등)의 "self-inferencing property": 리플렉션 호출의 타겟을 "타겟 호출 인자들의 동적 타입과 반환값에 걸린 다운캐스트(있다면)에 근거해 자동 추론"한다(Elf, ECOOP 2014). Solar(TOSEM 2019)는 "self-inferencing property는 대부분의 Java 리플렉션 코드에 내재하나 이전엔 충분히 활용되지 않았다"고 명시한다. 우리 문제에 이식하면 "반환값이 특정 타입으로 캐스팅/역직렬화/실행되는가"를 조회 API 식별의 보강 신호로 쓸 수 있다.

## Details

### Q1. 결정론적 1홉 래퍼 승격이 얼마나 멀리 가는가 — 매우 멀리 간다

**존재 여부와 이름.** 이 기법은 정적분석의 주류 기능이다. 가장 직접적인 대응은 CodeQL의 **model generator**로, 라이브러리/프레임워크 코드를 분석해 flow-summary(propagator) 모델을 자동 생성하며 provenance 태그를 붙인다. CodeQL ExternalFlow 공식 문서는 provenance 형식을 "{origin}-{verification}"으로 정의하고, "'df-generated': 모델이 model generator 도구에 의해 생성됨"이라 명시한다. 등급은 `df-generated`(자동 생성) → `df-manual`(자동 생성 후 사람 검증) → `manual`(수기)이다. `summaryModel`은 "요소를 관통하는 흐름을 모델링"한다. StubDroid는 동일한 아이디어를 IFDS/IDE 서머리로 구현한 최초 사례다. 우리의 "① `ctx.lookup(x)`가 카탈로그에 있고 ② 래퍼 본문에 그 호출이 있고 ③ 키 인자가 파라미터와 동일 심볼·무가공"이라는 3조건은 정확히 **value-preserving summary(`Argument[0]` → 내부 lookup의 `Argument[0]`)의 결정론적 특수 케이스**다.

**정밀도와 실패 모드.**
- **몇 홉까지 안전한가**: 값 보존은 홉 수에 관계없이 "각 홉에서 값이 변형되지 않으면" 합성 가능하다(IFDS 서머리 합성의 기본 성질). 그러나 우리 제약("콜체인 무한 추적 금지")과 실무 안전성을 감안하면 **1~2홉으로 제한**하는 것이 타당하다. 홉이 늘수록 오버로드·동적디스패치 해소 실패로 인한 정밀도 저하 위험이 커진다. **공개 수치 없음**: 엔터프라이즈 Java에서 래퍼 위임 체인의 평균 깊이에 대한 공개 실증 연구는 발견되지 않았다. 가장 근접한 자료는 메서드 체이닝 통계(Nakamaru 등, MSR 2020)로, Java 메서드 호출의 약 4분의 1이 2개 이상 연쇄에 속한다는 것이나 이는 fluent 체이닝이지 위임 래퍼 깊이가 아니다.
- **조건분기·캐시·널검사**: 위 Key Finding 2 참조. 값 보존 판정은 "데이터 변형 없음"이지 "제어흐름 단순함"이 아니므로 통과한다. 단, **조건에 따라 다른 키를 반환**하면(예: `if(x) lookup(a) else lookup(b)`) 무가공이 아니다 — 이건 §3에서 이미 확정한 "값이 갈리면 포기"와 동일 규칙.
- **오버로드·상속·인터페이스 다중 구현**: 이것이 주된 실패 모드다. `getLocalHome`이 인터페이스이고 구현체가 여럿이거나, 동일 시그니처 오버로드가 여러 개면 어느 본문을 승격할지 모호하다. 안전한 정책은 **구현체/오버로드가 유일하게 결정될 때만 승격, 다중이면 전부 포기**(FP=0 우선).

**커버되지 않는 잔여의 성격.** 세 부류다: (a) 래퍼가 값을 **가공**해 전달(프리픽스 부착, 매핑 테이블 치환) — 이건 결정론으로도 LLM으로도 위험, 포기가 정석. (b) 표준 조회 API를 **안 쓰는 자체 구현**(직접 JDBC, 자체 JNDI 파싱) — 카탈로그에 앵커가 없어 1홉 승격 불가. (c) **설정으로 주입되는 조회기**(DI 컨테이너가 런타임에 조회기 구현을 바꿈) — 정적으로 타겟 미결정. 이 (b)(c)가 LLM이 유일하게 기여할 수 있는 영역이지만, 그 비중은 우리 실측(사내 래퍼 17건 전부가 표준 lookup을 무가공으로 감싸는 케이스)에서 **0에 가깝다**.

### Q2. 정답지 없는 채점

**커버리지/일관성 지표.** 연관규칙 마이닝의 support/confidence 프레임이 직접 대응한다. "이 API의 n번 인자 문자열 중 X%가 조각 키와 일치"는 confidence, "그런 호출 건수"는 support다. 다만 연관규칙 문헌은 confidence 임계값만으로 FP를 못 잡으며 통계적 유의성(p-value, FDR/FWER 보정)이 필요하다고 명시한다. **외부참조 조회 API에 대한 공개 임계값은 없다.** 우리가 실측할 값이다.

**비대칭성 신호의 실증.** 진짜 조회 API는 인자 커버리지가 거의 1.0, 우연 일치 API는 낮다는 가정은 Solar의 self-inferencing 및 스펙 마이닝 전반의 근거와 정합적이나, **정확히 이 수치를 보고한 선례는 없다**. 관련 방향의 확립된 교훈은 Le Goues·Weimer(TACAS 2009, "Specification Mining with Few False Positives")에서 온다 — 원문: "기존 스펙 마이너가 FP를 내는 이유는 프로그램 행위의 모든 측면에 동일한 가중치를 주기 때문이며 … 우리는 중복 코드, 드물게 테스트된 코드, 버전관리에서 잦은 교체를 겪는 코드에 낮은 신뢰를 부여한다". 그 결과 "동일한 수의 스펙을 원래 입력의 60%만으로 학습"할 수 있었다. (주의: "FP율 5%"라는 구체 수치는 원문에서 확정 인용되지 않으므로 근거 미확인으로 제외.) 이식 가능한 핵심 교훈은 "모든 관찰에 동일 가중치를 주지 말라"이다.

**역방향 커버리지.** "외부 파일 키 중 몇 %가 코드에서 인용되는가"는 dead-configuration 탐지의 표준 관점이다(예: Elixir Meandro의 "unused configuration option" 규칙). 진짜 키 자리는 인용률이 높고 스키마 필드명은 낮다는 방향성은 타당하지만, **정답지 없이 이것만으로 판정하면 반례가 존재한다**: 레거시에는 실제로 죽은 설정(dead config)이 흔해서 "인용 안 됨"이 "키가 아님"을 의미하지 않는다. 따라서 역방향 커버리지도 채점 보조 신호로만.

**반환값 후속사용.** Q1 Key Finding 4와 동일. 이것이 가장 강한 결정론 신호다 — `sqlMap.selectOne(id)`의 반환이 DTO로 캐스팅되고, `lookup(name)`의 반환이 `EJBLocalHome`으로 캐스팅되는 등 후속 사용이 조회 의미를 확증한다. 반면 `put("orderId", …)`는 반환을 안 쓰거나 boolean/void다.

**결론(Q2)**: 정답지 없는 "옳음 채점"은 **다신호 결합**으로만 가능하다 — (1) 인자 커버리지 비대칭, (2) 반환값 후속사용 패턴, (3) 역방향 인용률. 어느 하나도 단독 승인 근거가 못 된다. FP=0 제약 하에서 이 지표들은 **규칙 후보의 순위화·게이팅**에만 쓰고, 최종 승인은 "본문 내 표준 API + 무가공 전달"의 구조적 증명으로 한다.

### Q3. LLM이 필요한가 — 대부분 불필요

**순수 정적분석으로 규칙 학습한 선례.** StubDroid는 LLM 없이 라이브러리 본문에서 서머리를 자동 추출했고, CodeQL model generator의 `df-generated`도 순수 정적분석이다. Seldon은 학습을 쓰지만 LLM이 아니라 선형최적화다. 즉 **"래퍼가 표준 API를 무가공으로 감싼다"는 규칙 산출은 LLM 없이 이미 실증**되어 있다. 커버리지는 도구마다 다르나, 표준 API에 앵커가 있는 한 결정론이 지배적이다.

**LLM이 꼭 필요한 잔여.** Q1의 (b)(자체 구현), (c)(DI 주입 조회기)뿐이다. IRIS(Li 등, ICLR 2025, arXiv:2405.17238)는 CWE-Bench-Java 120건에서 CodeQL이 27건만 탐지한 데 비해 GPT-4로 55건(+28)을 탐지하고 평균 false discovery rate를 5%p 개선했으나, sink recall이 GPT-4에서 최고 87.11%로 **과대근사(over-approximation)** 경향을 보인다 — FP=0 제약에는 그대로 못 쓴다. 프로젝트 규모의 LLM 취약점 탐지 실증(LLMDFA, Wang 등, NeurIPS 2024, arXiv:2402.10754)은 미탐 사례의 원인을 **함수간 dataflow summary 누락**, 즉 프로젝트 고유 함수 요약 실패로 지목한다 — 정확히 우리 사내 래퍼 상황이다. 결론: LLM은 규칙 후보 **제안**에만, 승인은 결정론 검증기에.

**분업의 검증된 관행성.** "통계/학습으로 후보 발굴 + 결정론으로 승인"은 neuro-symbolic 정적분석의 표준 구조(IRIS, MoCQ, Seldon+검증기)다. 반례는 "에이전트가 직접 연결까지" 하는 구조인데, 이는 우리 사내 선례(환각으로 폐기)와 IRIS의 낮은 소스 정밀도가 함께 경고한다.

**LLM 입력 비교.** 실증된 정면 비교는 못 찾았으나, IRIS는 **메서드 시그니처 + few-shot CWE 예시**를 주고, 프로젝트 규모 연구는 **본문/문맥 부족이 미탐의 주원인**이라 지목한다. 따라서 우리 문맥에선 **래퍼 본문 + 호출부 표본 몇 개 + 조각 키 목록 일부**를 함께 주는 것이 시그니처만 주는 것보다 정밀도가 높을 것으로 판단(추정, 정면 비교 선례 없음).

### Q4. 파이프라인 배치와 비용
- **통합 vs 분리**: 관용구 학습을 스캔 에이전트에 통합하면 프롬프트 오염(테이블 스킬과 외부참조 스킬이 섞임)과 실패 전파 위험. **별도 에이전트로 분리**하면 실패 격리·토큰 예산 독립·프롬프트 단순화 이점. 링킹이 컨텍스트 조립 전에 끝나야 한다는 제약과도 부합(학습 단계는 링킹 전 1회).
- **코드베이스별 1회 학습·캐시**: CodeQL의 **model pack**이 정확히 이 관행이다 — 학습된 모델을 팩으로 저장·재사용. 같은 고객사 재분석 시 팩만 재적용하면 재학습 비용 회피. 우리 규칙(래퍼명+인자위치)을 JSON 스킬로 저장하는 현 구조와 동일 철학. **적용 가능**.

### Q5. 실패 모드
- **여러 겹 래퍼(A→B→C→lookup)**: 각 홉이 값 보존이면 이론상 합성 가능하나, 제약상 **1~2홉으로 컷**. 넘으면 규칙 미생성(재현율 희생, FP=0 유지).
- **조회·비조회 겸용 메서드**: 같은 메서드가 때론 키, 때론 일반 문자열을 받으면 위험. 판정: **해당 인자 위치로 오는 문자열의 커버리지가 1.0이 아니면 규칙 비활성화**(단 1건의 비키 인자라도 섞이면 FP 위험). 이는 §6 "FP 1건이면 즉시 비활성화"의 사전 게이트.
- **다른 모듈에서 깨지는 규칙**: 저장 시점에 **교차검증**하라 — 규칙을 학습한 모듈이 아닌 다른 모듈의 호출부 표본에 규칙을 적용해 커버리지가 급락하면(예: 동일 래퍼가 다른 모듈에선 비키 인자로도 쓰임) 규칙을 좁히거나 폐기. 이는 스펙 마이닝의 교차검증 관행에 대응.

### Q6. 투자 가치
- **표준 카탈로그 커버리지 공개 통계**: 없음. 우리 실측(149건 중 표준 136 / 사내 17, 표본 1)이 유일 근거이며 일반화 불가.
- **판정**: 사내 래퍼를 **완전히 포기하는 것은 비합리적**이다 — 실측 17건(약 11%)이 전부 사내 래퍼를 통과하고, 그 17건이 전부 §4 발견대로 "표준 lookup의 무가공 1홉 래핑"이기 때문이다. 그러나 **LLM 학습으로 풀 문제가 아니다**. 결론: **"결정론적 1홉 승격"은 반드시 만들어라(저비용·고정밀·FP=0 유지 가능). "LLM 기반 사내 래퍼 관용구 학습"은 만들지 마라** — 그것이 필요한 잔여((b)(c))는 실측상 0에 가깝고, LLM 정밀도(IRIS sink recall 87%지만 소스 과대근사, Seldon 67%)가 FP=0 제약과 충돌하며, 결정론 1홉이 이미 17건을 전부 잡기 때문이다. **"만들지 말라"가 이 항목의 답이다** — 단 대상은 LLM 학습 컴포넌트에 한정.

### Q7. 놓친 프레임
- **문제를 "코드 쪽 조회 관용구 학습"이 아니라 "라이브러리 서머리 자동 생성"으로 재정의하라.** 이것이 StubDroid/CodeQL model generator가 이미 푼 문제이고, 학습이 아니라 **본문 데이터플로우의 결정론적 요약**이다. 사내 래퍼는 "미모델링 라이브러리 함수"일 뿐이며, 그 본문이 우리 코드베이스 안에 있다는 점에서 오히려 더 쉽다(바이너리 서머리보다 소스가 유리).
- **양방향 정의-사용 매칭 프레임**: 조각 쪽에 SCIP `SymbolRole`(§3에서 확정) 역할 비트를 부여했듯, 코드 쪽에도 "조회 역할" 비트를 부여하고 **역할 대 역할**로 매칭하면, 필드명 우연 일치(`put`)는 애초에 조회 역할 비트가 없어 배제된다. 이는 "일치=연결" 순환을 끊는 구조적 해법이다.

## Recommendations (단계별 + 중단 임계값)

**1단계 — 결정론적 1홉 서머리 승격 구현 (즉시, 최우선).**
- 표준 조회 카탈로그(§3 확정)를 앵커로, 사내 메서드 본문에서 "카탈로그 호출 + 키 인자 무가공 전달(값 보존)" 3조건을 결정론으로 검사해 래퍼를 승격.
- 구현체/오버로드가 유일할 때만 승격, 다중이면 포기. 홉은 1~2로 제한.
- **제약 적용 가능성**: 순수 Python·서브프로세스 0·콜체인 1홉 제한·FP=0 전부 충족.
- **중단 임계값**: 실측 코퍼스에서 **FP 1건이라도 발생하면 해당 규칙 즉시 비활성화**(§6). 5개 코퍼스 전수에서 신규 연결의 정밀도 100%를 못 지키면 홉을 1로 더 좁힌다.

**2단계 — 다신호 채점기를 "규칙 후보 게이트"로 구현 (1단계 후).**
- (1) 인자 커버리지 비대칭, (2) 반환값 후속사용(캐스트/역직렬화/실행), (3) 역방향 인용률을 계산해 규칙 후보를 순위화·필터. 승인은 여전히 1단계의 구조적 증명.
- **중단 임계값**: 커버리지 지표만으로 승인하는 경로는 만들지 마라. 채점기가 결정론 승인과 불일치를 보이면(채점 통과했으나 구조 증명 실패) 항상 구조 증명을 신뢰.
- **교차검증 게이트**: 학습 모듈 외 다른 모듈 표본에서 커버리지 급락 시 규칙 폐기.

**3단계 — 잔여((b)(c)) 측정. LLM은 그 다음에 판단 (조건부).**
- 1·2단계 적용 후 남는 미연결 "적재 참조"를 실측. 이 잔여가 진짜 참조의 **5% 미만이면 LLM 컴포넌트를 만들지 마라**(Q6 결론).
- 5% 이상이고 대부분이 (b)(c)이면, 그때만 **로컬 GPU LLM으로 규칙 후보 제안**(래퍼 본문+호출부 표본+키 목록 입력) → 반드시 1·2단계 결정론 검증기 통과분만 채택.
- **중단 임계값**: LLM 제안 규칙이 실측 FP를 1건이라도 만들면 그 규칙 폐기. LLM 경로 전체의 순 추가 정밀 연결이 결정론 대비 유의미하지 않으면 LLM 경로 폐기.

## Caveats
- **표본 1 문제**: §4의 무가공 전달 관찰도, 우리 149/17 분포도 모두 표본 1 코퍼스다. 5개 코퍼스 전수 측정 전에는 어떤 임계값도 잠정. 특히 "잔여 5%" 컷은 실측으로 교체할 자리표시.
- **공개 수치 부재 항목(명시)**: (1) 엔터프라이즈 Java 래퍼 위임 체인 평균 깊이 — **공개 수치 없음**(가장 근접: MSR 2020 메서드 체이닝 ~25%, 그러나 위임 깊이 아님). (2) 프레임워크 API 호출이 사내 래퍼를 경유하는 비율 — **공개 수치 없음**. (3) 외부참조 조회 API 커버리지 비대칭의 구체 임계값 — **공개 선례 없음**. (4) 표준 카탈로그만으로의 커버리지 비율 — **공개 통계 없음**.
- **추정 표시**: LLM 입력 형태별 정밀도 우열은 정면 비교 선례가 없어 **(추정)**. Infer가 taint식 인자→반환 표를 직접 만드는지는 문서상 명확치 않아, bi-abduction의 frame 개념을 무가공 전달의 이론적 대응으로 해석한 것이며 직접 이식은 아님.
- **CodeQL model generator의 본문분석/ML 여부**: `df-generated` 결정론 모델 생성기는 공식 문서로 확인되나, 본문을 ML/LLM으로 분석해 propagator를 추론하는 별도 컴포넌트("automodel")의 존재는 단일 공개 출처로 확정하지 못함.
- **인용에서 제외한 미확인 수치**: Le Goues·Weimer의 "FP율 5%" 구체 수치, LLMDFA "미탐 44건 중 42건" 구체 건수는 원문 단일 출처로 확정되지 않아 본문에서 제외했다. IRIS 소스 정밀도 "70%대"는 원문이 sink recall 87.11%와 FDR 5%p 개선을 보고하되 소스 스펙의 명시 정밀도 수치는 별도 검증 대상이므로 "과대근사 경향"으로 서술했다.
- IRIS 및 Seldon(67%)의 정밀도는 **FP=0 제약과 정면충돌**하는 수치이므로, 이들 학습 기법은 승인기가 아니라 후보 발굴기로만 인용됨.
