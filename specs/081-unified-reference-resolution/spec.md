## 0. FP 0 의 롤모델은 SAST 계열이 아니다

이 spec 이 "실측 FP 1건이면 즉시 롤백" 을 택한 이유는 취향이 아니라 **도구 계열의 최적화
방향이 갈리기 때문**이다.

- **과대근사 계열(부적합)**: CodeQL·Infer 류 SAST 는 soundness 를 위해 과대근사한다.
  대규모 프로젝트 NPD 탐지에서 **오탐률 95% 이상**이 보고된다(arXiv 2601.18844).
  재현율을 위해 정밀도를 내주는 설계이므로 우리 계약과 정면으로 어긋난다.
- **정밀도 우선 계열(우리 롤모델)**: OpenRewrite/Moderne LST 는 타입 귀속 기반으로
  *"100% accurate method matching — No false positives from similar-looking code"* 를 표방하고,
  IDE 프레임워크 지원(IntelliJ Spring facet · MyBatis 플러그인)은 **사용자에게 보여주는
  결과**라 정밀도를 극도로 중시한다.

**즉 "안 이어도 되지만 틀리게 이으면 안 된다"는 우리 요구는 IDE·리팩터링 도구의 요구와
같고, 취약점 탐지기의 요구와는 반대다.** 미연결을 성능 저하로 읽지 않는 이유가 여기 있다.

## 1. 목표

코드 단위(메서드/함수/프로시저)가 외부 아티팩트를 참조하면 그래프로 잇는다.
**의미 판단은 하지 않는다 — 잘 쪼개고 잘 연결하는 것이 전부다.**

## 2. 절대 계약

- **결정론만.** 리터럴로 확정될 때만 연결. LLM 은 이 경로에 관여하지 않는다.
- **틀린 연결 0 > recall.** 실측 FP 가 1건이라도 나오면 그 규칙만 즉시 비활성화하고 기록한다.
- **콜체인 추적 금지.** 값이 없는 지점(파라미터만 받는 함수)은 앵커가 아니다.
- 기존 연결(ofbiz 119 · ukesa 115 · swing 4 · 링킹 gold 8케이스)이 **하나도 줄지 않을 것.**

## 3. 구조 — 사전 + 사실의 조인

언어별 분기를 링킹 로직에 넣지 않는다. 양쪽이 각자 문자열을 내놓고 한 번 조인한다.

```
참조 대상 사전 (target_index)          코드 문자열 사실 (symbol_values + 본문 리터럴)
  chunk_key   조각 이름표                 · 루틴 본문의 따옴표 리터럴
  file_name   파일 이름                   · 상수를 폴딩해 얻은 확정 값
  file_path   경로 접미                   · (후속) 관용구 인자 — FOPEN/BULK INSERT/fopen
                       \        /
                        조회 1회
                           ↓
              exact → file(강등) → 미연결
```

언어마다 다른 것은 **"확정 문자열을 어떻게 뽑는가"** 뿐이며, 그것은 데이터(규칙표)로 외부화한다.

## 4. 참조 대상 사전 계약

| 종류 | 무엇 | 대상 노드 |
|---|---|---|
| `chunk_key` | `EXTERNAL_CHUNK.keys` | EXTERNAL_CHUNK |
| `file_name` | 파일 이름 (`.` 포함 필수) | PROJECT_FILE |
| `file_path` | 경로의 모든 접미 (`a/b/c.xml`, `b/c.xml`, `c.xml`) | PROJECT_FILE |

- `derived_document` 청크는 대상이 아니다(078 계약 유지).
- 자기 자신 파일로의 연결은 만들지 않는다.

## 5. 조회 알고리즘 (결정론)

입력 문자열 `v` (최대 240자):

1. **경로형**: `v` 에 `/` 또는 `\` 가 있으면 정규화(`\`→`/`, 선행 `./` 제거) 후 `file_path` 조회.
   유일하면 **파일 연결(exact)**. 복수면 미연결.
2. **토막 후보**: `v` 자체 + **키 문자셋 밖 문자 뒤에서 시작하는 접미들** 중
   `is_reference_key` 를 통과하는 것만, **긴 것부터** 순서대로.
   - 키 문자셋은 `span_common._KEY_PATTERN` 하나가 단일 진실이다. 프레임워크 지식을 쓰지 않는다.
   - **공백이 있는 값은 분해하지 않는다.** 식별자·경로에 공백은 없고, 공백이 있는 값은 사람이
     읽는 문장이다. 실측 근거는 §5-2.
3. 각 후보를 `chunk_key` → `file_name` 순으로 조회하고 **첫 성공에서 멈춘다**:
   - 청크 1개 → **조각 연결**
   - 청크 2개 이상 → **미연결** (더 짧은 후보로 내려가지 않는다)
   - 파일 이름 1개 → **파일 연결**

### 5-1. 롤백한 규칙 — 파일 강등 (실측 FP)

같은 파일 안에서 키가 겹치면 그 **파일**로 강등 연결하는 규칙을 넣었다가 **롤백했다.**

- **실측**: ofbiz-order-standalone 에서 강등 엣지 **127건** 발생. 내용은 `orderId`·`statusId`·
  `amount`·`quantity`·`partyId` 등 **흔한 필드명**이었고, 자바 5개 파일이 `entitymodel.xml`
  하나로 127개 엣지를 만들었다.
- **판정**: 흔한 단어의 우연한 일치는 참조가 아니다. 신호를 묻는 그래프 오염이며
  `FP 0 > recall` 위반이다.
- **조치**: 규칙 제거. 대상이 유일하지 않으면 **미연결**이 정답이다.
  `ReferTo.resolution` 속성도 함께 제거했다(강등이 없으면 구분할 값이 없으므로 죽은 스키마).
- **비용**: loan-ejb-app 의 세션 7건은 같은 XML 안에서 정의·언급으로 키가 겹치므로
  **여전히 미연결**로 남는다. 엔티티 7건은 유일하므로 연결된다.

### 5-2. 좁힌 규칙 — 공백 있는 값은 분해 금지 (실측 FP)

- **실측**: ofbiz `OrderServices.java` 에서 오연결 **6건**. 리터럴 `" for order "` 를 다듬은
  `for order` 를 공백 경계로 잘라 끝 토막 `order` 가 엔티티 키 `order` 와 일치했다.
- **판정**: 문장 조각의 끝 단어는 참조가 아니다. FP.
- **조치**: 통째 롤백 대신 경계를 좁혔다 — **값에 공백이 있으면 구분자 분해를 하지 않는다.**
  식별자(`java:comp/env/ejb/X`)·경로(`%s/subscribers.dat`)에는 공백이 없다.
- **효과**: 오연결 6건 제거, 정상 연결 28건(별명 17 · 파일 11) 전부 유지.
  `tests/.../test_target_index.py` 로 고정.

### 5-3-1. 키 확정률 — 리서치 1b §2 와의 대조

리서치 1b 는 Li/Tan/Xue(TOSEM 2019, DOI 10.1145/3295739)를 인용해 **리플렉션 콜사이트의
49% 만 문자열 상수**라고 보고했다. 같은 지표를 우리 제품 경로로 실측했다.

| 코퍼스 | 해석기 호출부 | 리터럴 | 상수폴딩 | 확정 계 | 동적 | **확정률** |
|---|---:|---:|---:|---:|---:|---:|
| loan-ejb-app | 38 | 6 | 29 | 35 | 3 | 92.1% |
| ofbiz-order-standalone | 112 | 110 | 0 | 110 | 2 | 98.2% |
| ukesa | 287 | 287 | 0 | 287 | 0 | 100.0% |
| **합계** | **437** | **403** | **29** | **432** | **5** | **98.9%** |

**49% 대 98.9% 는 우리가 더 잘해서가 아니라 세는 대상이 다르기 때문이다.**

- 리플렉션 연구는 **모든 리플렉션 콜사이트**를 센다 — 설정파일·명령행·네트워크에서 이름이
  들어오는 것까지 포함한다(진입 메서드는 55.3%가 Unknown).
- 우리는 **카탈로그에 등록된 자원 조회 호출부만** 센다. 그 API 들은 관용적으로 키가 리터럴이다.
  게다가 사용자 지시로 **동적은 애초에 후보에서 제외**한다(§9).

**결론: 98.9% 를 "동적 문제를 풀었다"는 뜻으로 읽으면 안 된다. 문제를 정의에서 제외한
결과이며, 리서치 1b 의 49% 는 우리가 제외한 영역의 크기를 알려주는 값이다.**
loan 의 `상수폴딩 29` 는 `symbol_values` 가 실제로 값을 만들어낸 건수이고, 나머지 두
코퍼스가 0인 것은 그 코드베이스가 리터럴을 직접 쓰기 때문이다 — **코퍼스별 편차가 크므로
이 비율을 일반 상수로 쓰지 않는다.**

### 5-4. 선행 결함 — 자바 AST 가 초기화식을 버리고 있었다 (antlr-code-parser)

`CONSTANT_FIELD`/`FIELD` 에 `initValue` 가 없어 `Constant.value` 가 항상 빈 값이었고, 이 spec 의
상수 폴딩이 전부 무효였다. C/PL/SQL/PostgreSQL/Python 리스너는 모두 방출하고 **자바만 누락**.
`JavaAstListener.enterFieldDeclaration` 에서 선언자가 1개일 때만 `initValue` 를 싣도록 수정.
바이트 골든은 자바 1개 노드에 `initValue` 필드만 추가됨을 필드 단위로 확인한 뒤 갱신(다른 4개
언어 골든 바이트 동일). 파서 테스트 107/107.
**부수효과**: 같은 코퍼스에서 `references` 7 → 745, `init_by` 0 → 15.

### 5-5. 미해결로 남긴 관측 (이 spec 범위 밖)

- `SKIP_DIRS` 에 `out` 이 있어 `data/out/` 같은 **송신 인터페이스 디렉터리가 통째로 미수집**된다
  (`in` 은 수집됨). 제품 전역 영향이라 임의 변경하지 않고 기록만 한다.
- 전체 파이프라인 실행에서 `link_residual_patterns_step` 이 `ModelCallLimitExceeded
  (residual, max_calls=15)` 로 1회 실패했다. 연결 단계와 무관한 LLM 보강 단계이며 인과 미확정.

## 6. 코드 문자열 사실 계약

- **본문 리터럴**: 주석/삼중따옴표 제외(기존 `key_index`).
- **상수 폴딩**: `a + b + …` 의 **모든 피연산자가 확정 문자열일 때만** 단일 값 산출.
  하나라도 비상수/미해결이면 **즉시 None**. 재귀 깊이 상한 4.
- **색인 범위**: 같은 owner 우선, 없으면 프로젝트 전역. 전역에서 **같은 이름이 서로 다른 값**을
  가지면 그 이름은 **폐기**(모호).
- **한정 참조** `Class.NAME` 인식. 마지막 마디로 조회한다.
- **불변 확인**: `Constant` 는 정의상 상수. `Variable` 은 `final/const/immutable` 표지가 있을 때만.
  루틴 본문에서 재대입되면 그 루틴에서는 사용하지 않는다(기존 규칙 유지).

### 6-1. 선언부는 호출부가 아니다 (실측 결함, 2026-07-23 수정)

승격된 사내 래퍼는 **자기 선언부가 자기 이름의 호출처럼 보인다.**

```java
public EJBLocalHome getLocalHome(String jndiName) throws NamingException {   // ← 여기가 호출로 잡혔다
    home = (EJBLocalHome) context.lookup(jndiName);
```

`getLocalHome` 이 승격돼 카탈로그에 들어간 뒤, 그 선언부가 `getLocalHome(` 패턴에 걸려
arg0 = `String jndiName` 을 키 인자로 뽑고 있었다.

- **자바에서는 무해했다** — `String jndiName` 은 식별자가 아니라 값이 확정되지 않는다.
- **그러나 파라미터가 맨이름인 언어(파이썬 `def load(name):`)에서는 그 이름의 상수가 있으면
  값이 확정돼 오연결이 난다.** 잠재 FP 이므로 고쳤다.
- **조치**: `call_sites(..., own_name)` 이 자기 이름의 **첫 등장**을 건너뛴다. 루틴 노드의
  범위는 선언부에서 시작하므로 첫 등장이 곧 선언부이고, 본문의 재귀 호출은 뒤에 오므로
  살아남는다. 언어별 코드 0.
- **효과(실측)**: 동적포기 loan 6→3 · ofbiz 6→2, **연결 건수는 28/34/113 그대로**(재현율 손실 0).

## 7. 그래프 계약 변경

- **노드 타입 추가 0, 관계 타입 추가 0.**
- `REFER_TO` 의 대상이 `EXTERNAL_CHUNK` **또는** `PROJECT_FILE` 로 확장된다.
- ~~`REFER_TO` 에 속성 `resolution` 추가~~ — **폐기.** §5-1 에서 파일 강등 규칙을 롤백하자
  구분할 값이 없어져 죽은 스키마가 됐다. 속성을 만들지 않는다.
- 미해결 참조는 **그래프에 넣지 않는다.** 실행 로그/보고에 건수만 남긴다
  (`dynamic_key_sites` · `orphan_chunks` · `promoted_wrappers`).

## 9. 범위 밖 (명시적 미연결)

런타임 조립 · 외부입력 · 리플렉션 · 다홉 파라미터 전달 · 조건분기로 갈라지는 값 ·
가변 상수 · PDF/HWP/Office.

### 9-1. swing_system 조립 경로 17건 — **의도적 미연결로 종결**

```c
snprintf(filepath, sizeof(filepath), "%s/subscribers.dat", g_db.data_dir);
fopen(filepath, "r");
```

파일명은 고정이고 파일이 실재한다. 그러나 디렉터리가 변수(`g_db.data_dir`)이고, 전달 방향이
지금까지 다룬 `파라미터 → 호출` 이 아니라 **`호출 출력 → 변수 → 호출`** 이다.

**판정: 잇지 않는다. 사용자 지시 "동적으로 만들어지는 키는 아예 보지 않는다" 와 정면으로
충돌하기 때문이다.** 부분 상수(`%s/subscribers.dat` 의 고정 부분만 떼어 쓰기)로 우회하면
"동적을 조금은 본다" 가 되어 계약이 무너진다. 이 17건은 **결함이 아니라 계약의 결과**다.
재검토가 필요하면 계약 자체를 먼저 바꿔야 한다.

### 9-2. ★ 발견 — 우리는 방향 하나만 모델링하고 있다 (미착수, 결정 필요)

ofbiz 고아조각 17건을 원문으로 전수 확인한 결과 **죽은 설정이 아니었다.**

```xml
<service name="massChangeApproved"
         engine="java"
         location="org.apache.ofbiz.order.order.OrderServices"   ← 클래스 FQN
         invoke="massChangeApproved"                             ← 메서드 이름
         auth="true"/>
```

설정이 **자기를 구현하는 코드를 정확히 지목**한다. 081 이 모델링하는 `코드 → 설정`
(코드가 키로 설정 내용을 가져다 씀)의 **정반대 방향**이며, 이 관계가 없으면 그 코드가
무엇인지 설명할 컨텍스트가 통째로 빠진다.

이름 일치로는 못 잡는다 — 실제로 어긋난 사례가 있다:

```xml
<service name="changeOrderStatus" … invoke="setOrderStatus"/>   ← 서비스명 ≠ 메서드명
```

**성격**: `location` 은 클래스 FQN, `invoke` 는 메서드 이름으로 **둘 다 정확한 식별자**다.
추정이 없으므로 **FP 0 을 지키기가 오히려 지금 하는 일보다 쉽다.** 같은 형태가 널리 쓰인다
— Spring `<bean class="…">`, web.xml `<servlet-class>`, EJB `<ejb-class>`, Struts
`<action type="…">`. loan 의 고아 `web.xml#LoanServlet` 도 같은 부류다.

**미착수 이유**: 관계 방향이 늘어나면 그래프 계약이 바뀐다(§7 "관계 타입 추가 0" 과 충돌
여부, `REFER_TO` 를 양방향으로 쓸지 새 타입을 둘지). **사용자 결정 사항이다.**

**되짚어야 할 수치**: 이 방향을 모델링하면 지금 "고아"로 세는 38건 중 상당수가 고아가
아니게 된다. 즉 **§5-3 의 고아조각 수치는 "아무도 안 쓴다"가 아니라 "우리가 안 보는
방향으로 쓰인다"를 포함한 값이다.** 보고할 때 이 전제를 반드시 함께 말해야 한다.

## 10. 리서치 1b 대조 (2026-07-23)

`deep-research-1b-custom-access-pattern-discovery.md` 는 2026-07-22 발행이나 저장소에 늦게
들어와 081 작업 중에는 보지 못했다. 사후 대조 결과 **설계를 바꿀 근거는 없었다.** 항목별로:

| 리서치 1b 의 권고 | 우리 설계 | 판정 |
|---|---|---|
| **sink-reachability 역전파** — 표준 DB 진입점을 sink 로 두고 콜그래프를 역방향 전파 | **I/O 프리미티브 앵커 + 위로 승격** — 런타임 I/O 프리미티브를 앵커로 두고 본문 검사로 래퍼를 승격 | **같은 아이디어의 다른 구현.** 방향(밑바닥 진입점에서 위로)이 동일하다. 차이는 전파 매체 — 1b 는 콜그래프, 우리는 본문. **우리가 콜그래프를 못 쓰는 이유는 자바 콜그래프에 값 위치 호출이 통째로 빠져 있고(`specs/093-...`) `Calls` 엣지에 인자가 없기 때문**이다. 콜그래프가 고쳐지면 1b 방식으로 옮길 수 있다 |
| **계산된 이름은 UNVERIFIED 로 남기고 selective prediction 으로 평가** | **동적은 아예 안 본다** (사용자 지시) | **결론은 같고 회계가 다르다.** 둘 다 "억지 해석 금지". 1b 는 미확인을 risk-coverage 곡선의 좌표로 관리하자 하고, 우리는 `dynamic_key_sites` 건수로만 남긴다. **1b 의 "미확인율은 벌점이 아니라 사람 검토 예산 지표" 라는 프레임은 채택할 만하나, 우리는 사람 검토 큐 자체가 없으므로 지금은 불필요하다** |

### 10-1. 채택하지 않은 것과 그 이유

- **LLM 좁은 이진 검증 + 자기일관성(SEA·SURE)**: 1b 의 핵심 권고지만 채택하지 않는다.
  리서치 6호가 "LLM 기반 사내 래퍼 학습은 만들지 말라"고 명시했고, **결정론 1홉 승격이
  실측 5종을 사람 입력 0으로 이미 전부 잡았다.** LLM 이 기여할 잔여((b) 자체구현·
  (c) DI 주입 조회기)는 우리 실측에서 0에 가깝다. 비용 대비 이득이 없다.
- **models-as-data YAML 사전 축적**: 형식은 우리 `DECLARED_RESOLVERS` 와 같은 발상이다.
  다만 **고객별 사전을 파일로 축적하는 것은 아직 불필요**하다 — 사내 래퍼가 매 실행
  결정론으로 재발견되므로 저장할 이유가 없고, 저장하면 코드베이스와 어긋날 위험만 생긴다.
- **명세 마이닝(빈발 패턴) 랭킹**: "빈발=정상" 가정은 1b 스스로 오탐 유발로 분류했다.
  FP 0 계약에서 랭킹 신호는 쓸 자리가 없다.

**정리: 리서치 1b 는 우리 설계를 뒤집지 않는다. 오히려 (1) 앵커 방향이 독립적으로 같은
결론에 도달했다는 확인과, (2) 자바 콜그래프가 고쳐지면 sink-reachability 로 갈아탈 수
있다는 이행 경로를 준다.**
