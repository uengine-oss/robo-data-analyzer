## User Scenarios & Testing *(mandatory)*

### User Story 1 - 책임을 즉시 찾는 저장소 (Priority: P1)

Analyzer를 처음 보는 유지보수자는 폴더와 파일 이름만으로 실행 흐름, LLM 자산, 그래프 저장,
검색, API, 테스트의 위치와 책임을 예측하고 한 경로로 찾아갈 수 있다.

**Why this priority**: 현재 기능은 동작하지만 같은 성격의 코드가 여러 최상위 폴더와 `shared`에
흩어져 있어 수정 범위와 영향도를 파악하는 비용이 크다.

**Independent Test**: 승인된 책임 지도와 실제 전체 트리를 비교하고, 옛 경로·옛 이름의 남은
참조가 0이며 각 책임의 활성 구현이 한 곳뿐인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 현재 Analyzer 기능 목록과 승인된 책임 지도, **When** 유지보수자가 임의 기능의
   구현·설정·테스트를 찾으면, **Then** 모호한 중복 경로 없이 한 책임 경계에서 모두 찾는다.
2. **Given** 이동 전 공개 진입점과 서비스 계약, **When** 새 구조에서 같은 동작을 실행하면,
   **Then** 호출자는 옛 내부 경로를 알 필요 없이 같은 결과를 받는다.

### User Story 2 - 분석 결과 무회귀 (Priority: P1)

운영자는 구조가 바뀐 뒤에도 동일 입력이 동일한 분석 그래프와 검색·MCP 결과를 만들며, 실패가
빈 성공으로 숨지 않는다고 신뢰할 수 있다.

**Why this priority**: 구조 개선이 분석 의미, 프롬프트 바이트 계약, 외부 서비스 계약을 바꾸면
리팩토링의 이점보다 회귀 위험이 커진다.

**Independent Test**: 이동 전 기준선과 이동 후 단위·계약·골드·재분석·REST/MCP/UI 결과를
대조해 정해진 허용 범위 밖의 차이가 0인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기준 프로젝트와 고정 정답지, **When** 새 구조로 전체 분석을 다시 실행하면,
   **Then** 필수 관계·의미 품질·검색 재현율이 승인된 기준선 이상이다.
2. **Given** 입력 누락이나 단계 실패, **When** 분석을 실행하면, **Then** 원인과 단계가 기록되고
   호출자에게 실패가 전달되며 빈 성공으로 완료되지 않는다.
3. **Given** 동일한 공통 프롬프트를 쓰는 병렬 분석, **When** 프롬프트 자산을 검사하면,
   **Then** 공유 바이트 계약이 모두 유지된다.

### User Story 3 - 전 파일 유지보수성 감사 (Priority: P2)

리뷰어는 리팩토링이 우연히 이동한 파일만 정리한 것이 아니라 전체 저장소를 동일 원칙으로
검사했고, 모든 파일의 판정과 검증 근거가 남았음을 확인할 수 있다.

**Why this priority**: 일부 파일만 정리하면 중복 판단, 침묵 실패, 죽은 코드와 잘못된 계약이
새 구조 안에 그대로 숨는다.

**Independent Test**: 작업 시작 시 동결한 전체 추적 파일 목록과 감사대장의 행을 대조해
미분류 파일이 0이고 각 행에 판정과 근거가 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 동결된 전체 파일 목록, **When** 감사대장을 집계하면, **Then** 각 파일은
   `수정`, `삭제`, `위반 없음` 중 정확히 하나로 분류되고 전체 수와 합계가 일치한다.
2. **Given** 수정 또는 삭제 판정, **When** 근거를 역추적하면, **Then** 생산자·소비자·계약과
   실행 검증이 연결되어 표본이나 추측에 의존하지 않는다.

### Edge Cases

- 역사 보존이 필요한 기존 spec과 baseline 파일은 내용 변경을 강제하지 않고 `위반 없음(역사 원문)`으로
  판정하되, 활성 코드·설정이 옛 경로를 참조하는지는 별도로 검사한다.
- 동적 import, 문자열 경로, 환경변수, CI·배포·외부 goal-verify 러너처럼 정적 import 검색에
  잡히지 않는 소비자를 포함한다.
- 같은 이름의 파일이 여러 책임에서 필요해 보이면 실제 호출 방향과 변경 이유를 대조하고,
  장기 호환 사본 대신 명시적 공개 경계를 둔다.
- 구조 이동 중 실패하면 직전 검증 슬라이스로 되돌릴 수 있어야 하며, 분석 데이터나 사용자 WIP를
  무단 삭제하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 저장소는 승인된 v10 책임 지도를 단일 목표 구조로 사용해야 한다.
- **FR-002**: 실행 흐름, LLM 자산, 그래프 저장, 검색, API와 테스트는 각각 한눈에 예측 가능한
  책임 경계와 이름을 가져야 한다.
- **FR-003**: 옛 구조와 새 구조의 활성 구현을 장기 이중 유지해서는 안 되며, 이동 완료 후 옛
  경로와 옛 이름의 활성 참조는 0이어야 한다.
- **FR-004**: 모든 추적 파일은 유지보수성·응집도, DRY/SSOT, 명명, 의존성·계약, 실패·운영성,
  성능·보안, 범용성·수명주기, 문서·검증 관점으로 판정되어야 한다.
- **FR-005**: 전체 파일 감사대장은 경로, 책임, 생산자·소비자, 발견, 판정, 수정 또는 삭제 근거,
  검증 증거를 보존해야 한다.
- **FR-006**: 파일 이동은 이력을 보존하고 호출자·설정·테스트·문서·스크립트·CI·배포 참조를
  같은 세로 슬라이스에서 갱신해야 한다.
- **FR-007**: 공개 실행 진입점, 입력 AST 계약, Neo4j 그래프 계약, Catalog 연동, REST/MCP 계약은
  명시적으로 변경 승인된 항목 외에는 동일해야 한다.
- **FR-008**: 결정 가능한 동작은 결정론적으로 유지하고, LLM 프롬프트와 구조화 출력 계약은 기존
  캐시·호환성 제약을 지켜야 한다.
- **FR-009**: 실패는 원인과 단계가 관측 가능해야 하며 조용한 빈 성공으로 바뀌어서는 안 된다.
- **FR-010**: 단위, 계약, 골드, 전체 재분석, REST/MCP/UI, 외부 러너 검증을 모두 통과하기 전에는
  완료로 표시해서는 안 된다.
- **FR-011**: README와 헌장은 실제 최종 구조와 단일 진실 위치를 설명해야 하며 실행 가능한 문서
  명령을 가져야 한다.
- **FR-012**: 역사 spec과 기준선은 보존하고, 생성물·비밀정보·실소비 없는 복제물은 근거 없이
  새 구조로 이동하지 않아야 한다.

### Key Entities

- **책임 지도**: 기능 책임과 목표 디렉터리, 공개 경계, 허용 의존 방향의 단일 정답표.
- **이동 지도**: 각 현재 경로와 최종 경로, 소비자, 이동 순서, 검증 슬라이스의 대응표.
- **파일 감사 기록**: 파일별 책임·소비자·원칙 판정·조치·검증 증거.
- **회귀 기준선**: 구조 변경 전후 의미 결과와 서비스 계약을 비교하는 고정 정답과 실행 증거.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 동결한 전체 추적 파일 수와 감사대장 행 수가 정확히 일치하고 미분류 파일이 0개다.
- **SC-002**: 옛 활성 경로·옛 이름·중복 구현 참조를 전수 검색한 결과가 0개다.
- **SC-003**: 모든 필수 단위·계약 검사가 통과하고, 검색 골드 기준은 29/30 이상을 유지한다.
- **SC-004**: 기준 프로젝트 전체 재분석에서 오류 0건이며 승인 기준선 밖의 그래프·의미 차이가 0건이다.
- **SC-005**: REST, MCP, 중앙 UI와 Architect 근거 연결의 핵심 시나리오가 모두 통과한다.
- **SC-006**: 공통 프롬프트 바이트 동일성 검사와 저장소 문서의 실행 명령이 모두 성공한다.
- **SC-007**: 리팩토링 완료 후 새 유지보수자가 책임 지도만으로 임의의 활성 기능 구현과 테스트를
  중복 후보 없이 찾을 수 있다.

## Assumptions

- 이 R1 당시 승인된 v10 구조와 개명·합침·삭제 후보표는 당시 handoff가 단일 진실이었다.
  해당 handoff 경로는 폐기됐으며 현재 구조는 spec 062와 `D:/work/robo/세서비스-최종트리.md`를 따른다.
- 현재 `main`의 커밋 `4a1bb126...`이 구조 변경 전 기준선이다.
- `module_test`는 현재 작업트리에 존재하지 않으므로 이번 구현의 삭제 대상이 아니다.
- 내부 경로 이동 자체는 외부 공개 계약 변경으로 간주하지 않지만, 외부 러너와 배포 참조는 실제
  소비자이므로 같은 작업에서 갱신한다.
