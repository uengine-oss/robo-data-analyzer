# 103 — summary·search_text 계약 정렬

> 2026-07-24 · 상태: 반입 완료(run104 콜드런 + run105 재확인) · 선행 spec 041(summary 다이어트) · 101 · 102

## 1. 문제 — 계약이 층마다 다르게 굳어 있었다

산출물 품질을 `logs/llm-prompts` 입출력 원문으로 조사한 결과, **세 개의 계약 불일치**가
품질 저하의 직접 원인이었다. 추정이 아니라 같은 호출의 입력·출력을 나란히 놓고 확인했다.

### 1-1. summary — "1~3줄" 계약이 네 곳에서 "한 문장"으로 좁혀졌다

| 층 | 실제 문구 | 결과 |
|---|---|---|
| 스키마 `SummaryOutput.summary` | `마커 없는 1~3줄` | — |
| `framework/code_summary.yaml` | `summary` **한 문장** | 좁힘 |
| `common/summary_contract.md` | **한 문장**으로 설명한다 (좋은 예시도 1문장) | 좁힘 |
| `framework/_common.yaml` | 목적·주요 효과 **한 문장**만 유지 | 좁힘 |
| `summary_quality.py` | 줄 **2개 이상 = `multiple_lines` 위반** → 재작성 | 되돌림 |
| `quality/summary_rewrite.yaml` | 재작성도 **한 문장**으로 | 되돌림 |

실측(run103): **416/416 전부 1줄, 길이 중앙값 47자.** 재작성 게이트 62회 발동.

spec 041 다이어트의 목적은 **RULE 중복 금지**(조건·수치·코드값을 요약에 넣지 마라)였는데,
그 제약이 **길이** 제약으로 옮겨 붙어 업무 내용까지 함께 깎였다. 길이와 조건 서술은 직교한다.

### 1-2. search_text — 이름으로 비웠다

`code_summary.yaml`: "단순 위임 함수는 `""`".

실측(run103): 공백 **97/416**. 그중 **35건이 규칙 2개 이상**을 보유했고 거의 전부
이름이 `*_call_*` 이었다. 분할 #1 은 이름을 보고 "위임"이라 판단해 비웠는데, **같은 함수에서
분할 #3 은 규칙 5개를 뽑았다.** 검색과 근거가 서로 다른 함수를 가리키는 분할 간 모순이다.

### 1-3. 리터럴 진법 — 지침은 있는데 안 지켜졌다

`Bank_054_CSB_Check` 의 `( 1 <= ll_conv_acnt && ll_conv_acnt <= 010 )` 을 `1~10` 으로 옮겼다.
C 에서 `010` 은 8진수 8이다.

입력 원문 확인 결과 **분기 목록에 `010` 이 그대로 실렸고, §6 진법 지침도 프롬프트에 있었다.**
즉 정보 부재도, 절단도 아니다. 같은 §6 안에서 **❌/✅ 쌍이 있는 항목(여집합 분기·바깥 조건
보존)은 전부 지켜졌고, 쌍이 없는 진법 항목만 지켜지지 않았다.** 지침 형식의 문제였다.

## 2. 결정

### 2-1. 길이 계약을 스키마에 맞춘다 — 단, 상한은 문장 수로 건다

- 프롬프트 4곳: `한 문장` → **`1~3문장`**
- `summary_contract.md`: "금지되는 것은 길이가 아니라 조건 서술이다"를 명시하고,
  **내용 유실형 나쁜 예시**(`"배송비를 산정한다."`)를 추가했다. 좋은 예시는 2문장으로 교체.
- `summary_quality.py`: `multiple_lines` 상한 `1` → **`3`**(스키마와 동일).
  이 게이트가 막을 것은 조건 서술이지 분량이 아니다.
- `quality/summary_rewrite.yaml`: 재작성 임무를 **"조건만 걷어내기"** 로 한정.
  대상·산출물·연동 모듈까지 줄여 없애는 것을 나쁜 예시로 못 박았다.

**★ 줄 수만으로는 상한이 원리적으로 샌다.** 모델은 1~3문장을 **줄바꿈 없이 한 줄로** 쓰므로
줄 기준으로는 언제나 1줄이고, 몇 문장을 쓰든 절단이 걸리지 않는다. 그래서
`_normalize_diet_summary` 가 줄 절단에 더해 **문장 절단**도 한다.

단, 이 절단은 **현재 방어망일 뿐 교정 실적이 없다.** run105 실측에서 함수 노드 416건 중
3문장 초과는 **0건**이다(1문장 160 · 2문장 251 · 3문장 5 · 최대 169자). 도입 근거로 처음
지목했던 "한 줄 1,027자" 사례는 재측정 결과 **함수가 아니라 FILE·모듈 요약**이었고, 모듈은
`[핵심] 한 줄 + 본문` 이라는 **별개 계약**이라 길어도 정상이다(모듈 23건 중앙값 452자).
모듈 요약은 이 검증자를 타지 않으므로 영향받지 않는다.

문장 경계는 `(?<!\d)[.!?](?=\s|$)` — 종결부호 뒤가 공백이나 문장 끝일 때만. 숫자 뒤 마침표
(`3,000.50` · `v1.2`)는 소수점·판번호라 경계가 아니다. **언어 분기 없음**(한국어 `~다.` 도
마침표로 끝나므로 같은 규칙이 적용된다).

### 2-2. search_text 공백은 본문으로만 판정한다

- 판정 기준을 **이름 → 본문**으로 바꾸고 ❌/✅ 쌍을 붙였다.
  `❌ 이름이 ..._call_... 이라서 본문에 조건 분기가 5개인데도 ""`
  `✅ 본문이 인자 세팅 후 호출 한 줄뿐이라 ""`
- 분할 간 모순을 직접 금지: "규칙이 나올 만한 분기가 보이면 `search_text` 도 반드시 채운다."
- 스키마 `description` 도 같은 문구로 정렬(모델이 스키마 설명도 읽는다).
- framework·dbms 두 전략에 동일 적용.

### 2-3. 진법 지침에 ❌/✅ 쌍을 준다

판정을 요구하지 않고 **표기를 그대로 옮기라**고만 한다(진법 판정은 모델이 틀릴 수 있다).

```
❌ `x <= 010` 을 "10 이하" 로 (앞 `0` 을 지워 값을 바꿔 읽음)
✅ `x <= 010` 을 "`010` 이하" 로 (원문 표기 그대로)
❌ `0x1F`·`1_000`·`'007'` 을 "31"·"1000"·"7" 로 / ✅ 그대로.
```

자가 점검 절(앵커 직후 재확인)에 5번째 항목 **"값 표기를 바꾸지 않았나"** 를 추가했다 —
모델이 근거 분기를 다시 읽는 바로 그 자리다.

### 4-3. 남은 이탈

- **조건 서술 잔존 59/416(14%)** — 요약이 길어지며 조건 표현이 일부 복귀했다.

  모듈명(`zapamcom10200`) 같은 식별자를 정책 숫자로 잡는 경우가 섞여 있어, 다음 과제는
  **잔존 59건을 진짜 조건 서술과 오탐으로 가르는 것**이다.
- **search_text 부당 결손 6건** — `Check_Sum32` · `ngmf_strcat` 은 유틸리티라 타당할 수 있고,
