# Feature Specification: 테이블 논리명 품질 향상 + 스키마 화면 표시 배선

**Feature Branch**: `038-table-logical-name-display-quality`

**Created**: 2026-06-29

**Status**: Draft

**Input**: User description: "테이블 논리명이 너무 짧다(품질) + 스키마 화면에 논리명이 안 나온다(미표시). spec 025(table-logical-name)의 미완 부분 완성."

## 배경 (실측 — 2026-06-29 전수확인)

- spec 025로 테이블 `logical_name` 이 LLM 으로 생성·Neo4j 저장된다. 현재 framework DB 의 7개 테이블 **전부 논리명 보유, 빈값 0건**. analyzer.log 도 8개 테이블 `enrich_table_description` start→done 정상. **즉 LLM·프롬프트·analyzer 저장은 정상 — 본 작업은 LLM 결함 수정이 아니다.**
- **문제 ① (품질 — 논리명이 너무 짧음)**: 산출 논리명이 도메인을 충분히 설명하지 못한다. 실측: `계정 정보`(4자), `공통코드 상세`(6자), `제휴카드 정보`(6자) — 프롬프트 자기 기준("통상 8~20자")에도 못 미치고, 비전문가가 무슨 테이블인지 알기 어렵다. 같은 테이블의 `description` 본문은 충분히 설명적("공통코드 상세 마스터 — 인증 결과·결제 수단·은행/카드사 코드 매핑")인데 논리명만 빈약하다.
- **문제 ② (미표시 — 논리명이 화면에 안 나옴)**: 스키마(ERD) 화면의 테이블 노드 제목이 **항상 물리명**(`zngm_comm_cd_dtl`)으로만 나온다. 저장된 논리명이 화면까지 오는 길 **3곳에서 버려진다**:
  - (a) catalog `getTables` 응답이 `logical_name` 을 안 내려줌.
  - (b) frontend 의 스키마 테이블 타입에 `logical_name` 필드 자체가 없음.
  - (c) frontend 테이블 노드 제목 로직이 **옛 전제**("테이블엔 깔끔한 논리명 데이터가 없다")로 무조건 물리명을 쓴다.
  - → spec 025 **FR-004**("화면은 테이블을 논리명으로 표시, 물리명 병기")가 스키마 화면에 배선되지 않았다.

이 기능은 (1) 논리명 **생성 품질**을 높여 도메인을 충분히 설명하는 표시명을 만들고(여전히 물리명·코드토큰 금지·근거부족 시 빈값=날조금지 원칙 유지), (2) 그 논리명을 **catalog→화면까지 배선**해 스키마 화면이 테이블을 논리명으로 표시(물리명 병기)하게 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스키마 화면에서 테이블을 논리명으로 본다 (Priority: P1)

비전문가 사용자가 스키마(ERD) 화면을 열면, 테이블 노드 제목이 물리명(`zngm_comm_cd_dtl`)이 아니라 사람이 읽을 논리명("공통코드 상세 마스터")으로 보이고, 물리명도 함께(작게) 병기된다. 컬럼의 논리/물리 토글과 일관되게 동작한다.

**Why this priority**: 직접적 가독성 개선이자 spec 025 FR-004 의 미완 완성. 데이터(논리명)는 이미 DB 에 있는데 화면이 안 보여줘 가치가 0 인 상태. 이 스토리만으로도 사용자가 즉시 가치를 본다(MVP).

**Independent Test**: 재분석 없이 현재 DB 그대로, catalog+frontend 만 고쳐 스키마 화면을 열어 테이블 제목이 논리명으로 바뀌고 물리명이 병기되는지 확인(Playwright 스샷 + catalog 응답에 `logical_name` 포함 확인).

**Acceptance Scenarios**:

1. **Given** 논리명이 저장된 테이블, **When** 스키마 화면에서 그 테이블 노드를 봄, **Then** 제목이 논리명으로 표시되고 물리명이 병기된다.
2. **Given** 논리명이 비어 있는 테이블(근거 부족), **When** 스키마 화면, **Then** 물리명으로 표시된다(빈 논리명을 제목으로 쓰지 않음 — 폴백).
3. **Given** 논리/물리 표시 토글, **When** 물리명 모드로 전환, **Then** 테이블 제목·컬럼이 일관된 기준(물리 우선)으로 바뀐다.

---

### User Story 2 - 테이블 논리명이 충분히 설명적이다 (Priority: P1)

재분석을 마치면 각 테이블의 논리명이 도메인을 충분히 설명하는 표현이 된다 — `계정 정보`(빈약) 대신 `주문 계정 정보`, `공통코드 상세`(빈약) 대신 `공통코드 상세 마스터` 처럼. 단 물리명·코드토큰을 그대로 쓰지 않고, 근거가 부족하면 빈 논리명을 유지한다(날조 금지).

**Why this priority**: 가독성의 핵심. 표시(US1)가 돼도 논리명 자체가 빈약하면 사용자가 여전히 이해 못 한다. 표시와 품질은 함께 가야 가치가 완성된다.

**Independent Test**: 재분석 후 논리명 샘플을 `description` 본문·원문 코드와 대조 — 도메인 설명력이 늘었는지, 물리명/코드토큰이 안 섞였는지, 근거 없는 테이블에 빈값이 유지되는지.

**Acceptance Scenarios**:

1. **Given** code summary 근거가 충분한 테이블, **When** 재분석, **Then** 논리명이 도메인을 분간 가능한 명사구로 나온다(단순 1~2어절 빈약 표현 회피).
2. **Given** 도메인 코드·식별자, **When** 논리명 생성, **Then** 물리명·코드토큰을 그대로 쓰지 않는다(읽을 표현으로 풀어씀).
3. **Given** 근거 부족한 테이블, **When** 재분석, **Then** 빈 논리명을 유지한다(억지로 길게 날조하지 않음).

---

### Edge Cases

- 논리명 비어 있음(근거 부족) → 화면은 물리명 폴백, 저장은 빈값 유지(날조 금지).
- 논리명을 "길게" 요구하다 물리명/코드토큰을 욱여넣거나 없는 내용을 추가 → 금지(설명력 향상이 정확성·날조금지보다 우선하지 않음).
- catalog 응답에 `logical_name` 추가(계약 변경) → 소비처(frontend)가 옛 응답(필드 없음)에도 깨지지 않아야(옵셔널 필드, 폴백 물리명).
- DBMS·framework 양 전략에서 논리명 규칙·표시 동일(전략무관).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 테이블 논리명을 **도메인을 충분히 설명하는 명사구**로 생성해야 한다(단어 1~2개의 빈약한 표현을 지양하되, 정확성·날조금지를 위배하지 않는 범위 — 통상 하한을 현재보다 높임).
- **FR-002**: 논리명은 **물리명·코드토큰을 그대로 쓰지 않고**, 근거가 부족하면 **빈 논리명을 유지**한다(날조 금지 — spec 025 FR-002/FR-003 유지).
- **FR-003**: 논리명 생성 규칙 변경은 **전략무관**(DBMS·framework 공통)이어야 한다.
- **FR-004**: catalog 의 테이블 조회 응답은 테이블 **논리명을 포함**해야 한다(현재 미포함 → 추가).
- **FR-005**: frontend 의 스키마 테이블 표현은 catalog 가 내려준 **논리명을 보유**해야 한다(타입에 필드 부재 → 추가, 옵셔널).
- **FR-006**: 스키마 화면의 테이블 노드 제목은 **논리명이 있으면 논리명으로 표시하고 물리명을 병기**하며, **논리명이 없으면 물리명으로 폴백**한다.
- **FR-007**: 테이블 제목 표시는 컬럼의 **논리/물리 표시 토글과 일관**되게 동작한다(같은 기준으로 스왑).
- **FR-008**: 논리명 생성 지침 변경은 **반복 측정 비용을 늘리지 않아야** 한다(테이블당 1회 호출 구조·공통 골격 유지 — 캐시 친화, spec 025 FR-008 계승).
- **FR-009**: 본 작업은 **컬럼 논리명(spec 028)·`description`·`analyzed_description` 본문을 변경하지 않는다**(범위 격리).

### Key Entities *(include if data involved)*

- **테이블 노드**: 물리명 + **논리명(품질 향상 대상)** + 문단 설명. 논리명은 분석이 산출, 빈값 미저장.
- **테이블 조회 응답(계약)**: catalog → frontend 로 내려가는 테이블 메타. **논리명 필드 신규 포함**.
- **스키마 화면 테이블 노드**: 제목 = 논리명 우선 + 물리명 병기(폴백 물리명).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 재분석 후 근거 충분한 테이블의 논리명이 **현재보다 설명적**(샘플 대조 — 단어 1~2개 빈약표현 비율 감소). 빈 논리명 0건 저장(근거 있는 테이블 기준).
- **SC-002**: 논리명에 **물리명·코드토큰 그대로 노출 0건**(샘플 대조).
- **SC-003**: 스키마 화면에서 논리명 보유 테이블이 **논리명으로 표시**되고 물리명이 병기된다(Playwright 스샷 확인).
- **SC-004**: 논리명 없는 테이블은 **물리명으로 정상 폴백**(빈 제목·깨짐 0건).
- **SC-005**: catalog 응답에 **`logical_name` 포함**, 옛 소비 경로 회귀 0(스키마 화면·기타 테이블 소비처 정상).

## Dependencies & Contract (서비스 경계)

이 기능은 단일 capability 이나 구현이 3 서비스에 걸친다. 서비스 간 **공유 계약 = 테이블 조회 응답의 `logical_name` 필드**(producer=catalog, consumer=frontend). 이 spec.md 가 그 계약의 단일 출처다.

| 표면 | 서비스(레포) | 변경 | 계약 영향 |
|---|---|---|---|
| 논리명 생성 품질 | analyzer | 논리명 생성 지침·예시 보강(전략무관) | 내부만 — 계약 불변 |
| 테이블 조회 응답 | catalog | 응답에 `logical_name` 추가 | **계약 변경** (옵셔널 필드) |
| 스키마 화면 표시 | frontend | 응답의 `logical_name` 소비 → 제목 논리명+물리명, 없으면 물리명 폴백 | 계약 소비 |

- **graceful 폴백**: catalog 가 `logical_name` 을 아직 안 내려주는(구버전) 응답에도 frontend 는 물리명으로 정상 동작해야 한다(필드 옵셔널, 폴백 물리명).
- analyzer 품질 개선(US2)은 **재분석 후** 반영된다(현재 DB 의 옛 논리명에는 소급 안 됨). 표시 배선(US1)은 **현재 DB 그대로** 즉시 동작한다 — 두 스토리는 독립.

## Assumptions

- 논리명 생성 메커니즘(테이블당 1회 LLM 호출)은 그대로 두고 **지침·예시만 보강**한다(규칙 재정의 아님 — spec 025 Assumption 계승).
- catalog 응답에 옵셔널 필드 추가는 기존 소비처를 깨지 않는다(필드 미사용 소비처는 무영향, 신규 소비처만 읽음).
- 측정 데이터는 RWIS(zapamcom, framework). DBMS 전략도 동일 규칙으로 대비(라이브 실증은 별도).
- 테이블 설명 오염(DDL 프로비넌스 줄 — 별 TODO item B)·코드식별자 누출(spec 037)은 **이 스펙 밖**.
- 논리명은 임베딩 검색(별도 프로젝트) 입력이 아니므로(검색 입력 = summary/analyzed_description) 문체 변경의 검색 영향은 낮다.
