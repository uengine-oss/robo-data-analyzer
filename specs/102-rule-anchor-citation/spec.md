# spec 102 — 규칙 근거 인용(anchor) + 결정론 인용 검증 — **미착수 설계**

> spec 101 이 실측으로 막힌 지점을 푸는 유일한 설계다. **아직 실행하지 않았다.**
> 실행에는 콜드런 1회와 gold set 재감사가 필요하고, 그 결정은 사용자 몫이다(§5).

## 1. 왜 필요한가 — spec 101 이 남긴 잔여 결함의 성질

spec 101 은 근거성 게이트를 빌드해 반입했고(측정 전용), 검사 7종을 gold set 에 걸어
**최대 재현 22/29(76%)** 를 실측했다. 임계 25/29(85%)는 어떤 조합에서도 나오지 않았다.

끝까지 안 잡힌 7건은 전부 같은 성질이다:

| 항목 | 결함 |
|---|---|
| b320 규칙문 | 인접 분기(C9/s0032)의 로직을 P/s1149 분기 설명에 이식 |
| b320 `when` | 코드와 반대로 서술(비-P 인데 대체조회 수행) |
| b400 | 무조건 대입 필드들을 "~에 따라"라며 조건처럼 서술 |
| 10101 | `Y→146633 / else→114` 를 정확히 뒤집음 |
| d010 | `'XXXX'` 세팅을 그 값이 없는 경로에 귀속 |
| c000 | `then` 이 callee 내부 동작을 서술(라우터인데) |
| 10090 | 잔여 1건 |

**코드값도 분기 참조도 옳고 의미 대응만 틀렸다.** 판정하려면 "이 값이 어느 변수의 값인가 /
이 규칙이 어느 분기를 말하는가"라는 **결속**이 필요한데, `code_rules_examples` 프롬프트가
given/when/then 에서 변수·메서드 토큰을 지우라고 지시하므로 산출물에 결속이 없다.
게이트를 아무리 정교하게 만들어도 없는 신호는 못 읽는다 — **입력 계약의 문제다.**

## 2. 설계 — "인용하게 하고, 인용을 검증한다"

LLM 에게 의미 판단을 더 요구하지 않는다. **자기가 쓴 규칙이 코드 어디에 근거하는지 지목**하게
하고, 그 지목이 맞는지는 결정론이 검증한다. 표준 citation-verification 패턴이다.

### 2.1 스키마 (`RuleItem` 에 필드 1개 추가)

```
RuleItem {
  statement: "<조건>이면 <결과>"
  anchor:    { start: int, end: int }   # ← 신설. code_body 기준 1-based 줄범위
  examples:  [ ... ]
}
```

- 줄범위 하나만 요구한다. 심볼 목록을 요구하면 프롬프트의 "변수 토큰 금지" 원칙과 충돌하고
  출력도 부푼다. **줄번호는 도메인어가 아니므로 그 원칙과 충돌하지 않는다.**
- `ExampleItem` 에는 넣지 않는다 — 사례는 규칙의 앵커를 물려받는다(출력 폭주 억제).

### 2.2 결정론 검증 (게이트에 검사 3종 추가)

`pipeline/quality_gates/grounding.py` 에 얹는다. 모두 인용 검증일 뿐 의미 판단이 아니다.

| 검사 | 판정 |
|---|---|
| `anchor_exists` | `anchor` 가 `control_subtree` 의 어떤 분기 범위와도 겹치지 않음 → 지어낸 인용 |
| `anchor_values` | 규칙이 인용한 코드값이 **그 앵커 범위의 활성 코드**에 없음 → spec 101 의 `value_set` 이 추정으로 하던 일을 확정으로 |
| `anchor_effect` | 규칙의 `then` 이 주장한 결과값·반환이 앵커 범위에서 만들어지지 않음 |

spec 101 이 `best_match`(조건값 최대 겹침)로 **추정**하던 근거 분기가 여기서는 **확정**된다.
추정 실패가 그대로 오탐이던 `guard`·`branch_scope` 의 노이즈가 구조적으로 사라진다.

### 2.3 왜 이게 잔여 7건을 잡나

- b320·d010·10101: 규칙이 인용한 범위와 그 규칙이 쓴 값/결과가 어긋난다 → `anchor_values` /
  `anchor_effect` 가 확정 판정.
- b400: 앵커가 무조건 대입 구간을 가리키는데 statement 는 조건을 주장 → 그 범위에 분기 노드가
  없음으로 판정 가능.
- c000: 라우터의 앵커는 CASE 범위인데 `then` 이 서술한 값은 callee 본문에만 있음 → `anchor_effect`.

## 3. 제약 준수

- **범용**: 줄범위는 언어 무관. 검증은 `control_subtree` + 활성 소스만 쓴다. 어댑터 추가 0.
- **8단계 흐름 불변**: step7 산출 뒤 게이트가 얹히는 구조 그대로.
- **결정론 산출 6종 불변**: rules 스키마 변경은 코드본문·요약·READS·WRITES·CALLS·REFERENCES
  어디에도 닿지 않는다.
- 게이트는 여전히 **측정 전용**으로 시작한다.

## 4. 위험

| 위험 | 대응 |
|---|---|
| 출력 폭주(필드 추가 = 새 나열 지점) | 규칙당 정수 2개뿐. `ExampleItem` 에는 미적용 |
| 앵커 자체가 환각 | 그게 이 설계의 요점 — 환각한 앵커는 `anchor_exists` 가 즉시 잡는다 |
| 토큰·지연 증가 | 규칙당 ~10 토큰. 속도 축은 종결됐고 이 크기는 측정 오차 이하 |
| 모델이 앵커를 대충 찍음 | 앵커 품질 자체가 측정 대상이 된다(그 자체로 새 신호) |

## 5. **착수 전 사용자 결정이 필요한 이유** — 이 spec 이 미착수인 이유

실행하려면 두 가지가 필요하고, 둘 다 되돌릴 수 없다.

1. **콜드런 1회**(≈650초, 공유 서버). 프롬프트가 바뀌므로 LLM 응답 캐시도 전부 미적중이다.
2. **gold set 재감사.** 현재 gold(환각 29·누락 25)는 **현 프롬프트의 산출물**을 대조해 만든
   것이다. 프롬프트가 바뀌면 그 29건은 더 이상 같은 규칙을 가리키지 않아 **임계 자체가 무효**가
   된다. spec 101 의 §01-23~25 실측과도 직접 비교 불가해진다.

즉 "임계를 넘기려면 재추출이 필요한데, 재추출은 임계를 넘긴 뒤에만 허용된다"는 순환에 들어간다
(`docs/핸드오프/analyzer-성능/01 §01-25`). **이 순환을 끊는 것은 임계를 다시 세우는 결정이며,
그건 제품 합격선이라 사용자만 정할 수 있다.**

## 6. 착수 시 순서

1. gold set 을 현 상태로 동결·백업(`fn_00..23.json` 은 이미 세션 밖에 있다 — 저장소로 옮길 것).
2. `RuleItem.anchor` 추가 + 프롬프트에 앵커 지시 1줄. 나머지 지침 불변(바이트 diff 최소화).
3. 콜드런 1회 → 결정론 6종·완주 수 회귀 확인.
4. 앵커 품질 자체를 먼저 측정(`anchor_exists` 위반율). 위반율이 높으면 여기서 중단하고 기록.
5. 새 산출물로 gold set 재감사(24함수 층화 표본, 감사+적대적 검증 2단).
6. 새 임계로 게이트 3종 판정 → 통과분만 승격.
