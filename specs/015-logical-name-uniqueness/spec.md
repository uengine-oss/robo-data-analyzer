# Feature Specification: 논리명(logical_name) 고유성 유도 지침 — 두 전략(framework·dbms) 공통

**Feature Branch**: `015-logical-name-uniqueness`

**Created**: 2026-06-17

**Status**: Draft (합의 전 — 코드/프롬프트 착수 금지)

**Input**: 사용자 피드백(스크린샷, Navigator 논리명 보기) — "논리명으로 보면 같은 이름 중복이 있다. 이름이 고유성을 가지도록 **유도**해야 한다. **지침을 수정**해야 할 것 같다. **범용적으로 예시와 지침을 추가**하라. **모든 전략 둘 다**(framework·dbms)."

> 대상 = analyzer가 LLM으로 생성하는 `logical_name`(프론트 [navigator.ts:98] `properties['logical_name']` = "논리명" 토글 표시값). 관련 기존 스펙: [009-function-analysis](../009-function-analysis/spec.md)(함수 summary/logical_name) · [010-postprocessing-summaries](../010-postprocessing-summaries/spec.md)(모듈 summary/logical_name) · [002-strategy-pipeline-assembly](../002-strategy-pipeline-assembly/spec.md)(전략 분기). 헌법 원칙: 결정론 우선 · 단일진실 · KV캐시 친화 · 출력스키마 절제 · 계약경계.

## 사실 확정 (2026-06-17, 코드 직접 확인 — 추측 아님)

`logical_name` 생성 지점 = **4곳(2 전략 × {함수, 모듈})**:

| 지점 | 파일 | 현재 고유성 지침 | 형제 맥락 가용성 |
|---|---|---|---|
| FW 함수 | `prompts/framework/function_summary.yaml` `[1] logical_name`(48-124, 형제차별표 1.4: 77-94) | **있음** — "같은 모듈 안 형제와 한 글자라도 다르게" + 9쌍 차별표 | per-function 3분할 호출 → **형제 이름 목록을 컨텍스트로 안 받음** |
| DBMS 함수 | `prompts/dbms/function_batch.yaml` `system §2`(30-35) | **없음** — "코드토큰 박지마"만 | **배치 = 같은 부모 형제 노드를 한 콜에 함께 봄(맥락 보유!)** |
| FW 모듈 | `prompts/framework/module_summary.yaml` `[2] logical_name`(30-34) | **없음** | 멤버 함수 summary 종합 |
| DBMS 패키지 | `prompts/dbms/module_summary.yaml` `[2] logical_name`(30-34) | **없음** | 멤버 프로시저 summary 종합 |

**근본 진단(왜 중복이 나나):**
1. **비대칭** — FW 함수에만 형제 변별 지침이 있고, 나머지 3 지점(DBMS 함수·양 전략 모듈)은 지침이 **없다**.
2. **범위 한정** — FW 함수 지침조차 "같은 모듈 안"으로만 한정 → **모듈 경계를 넘는 중복**(스크린샷처럼 다른 모듈의 동일 논리명)은 대상이 아님.
3. **구조적 한계** — 프롬프트는 호출마다 stateless → 전체 이름 목록을 못 봐서 **지침만으로는 전역 고유성을 "보장"할 수 없고 "유도"만** 가능. 단, DBMS 함수는 배치라 **한 콜 안 형제끼리는 충분히 변별 가능**(현재 미활용).

**KV 캐시 제약(헌법):** DBMS `function_batch.yaml`의 `system`은 모든 배치 콜에 byte-identical(헤더 3행), FW는 `_common.yaml` `system` 단일진실([[kv-cache]]). 지침 텍스트는 **정적**이라 추가해도 콜 간 동일성은 유지되나 **prefix가 바뀌므로 `cli_scripts/check_byte_identical.py --update`로 골든 재기준** 필요.

## 결정된 설계 (단일 진실)

**★사용자 결정(2026-06-17)**: **방법 = 프롬프트 지침만.** 생성되는 순간부터 고유성을 갖도록 "**절대 동일 문자열 금지**"를 강하게 유도한다. **결정론 후처리(축 B)는 미채택** — 이름은 LLM이 만들 때부터 안 겹치게 "노력"하도록 지침으로 강제한다.

> 정직한 한계(왜곡 없이 명시): 지침만으로는 **한 콜이 함께 보는 형제(특히 DBMS 배치)** 끼리는 동일 문자열을 **강제 차단** 가능하지만, 서로 다른 호출/모듈이라 **상대를 못 보는 경우**는 "최대한 회피(노력)"가 한계다. 그래도 차별 축 2+ 강제로 우연한 전역 중복 확률을 크게 낮춘다.

### A. 프롬프트 지침(유도) — 4 지점 정합 (이번 스펙의 본체·유일 수단)
1. **DBMS 함수(`function_batch.yaml`)** — 신규 절 추가: 배치가 형제를 한 콜에 보므로 "이 배치 내 노드들끼리 `logical_name` **전체 문자열 동일 금지**, 차별 축 2+ 동시 노출"을 명시. FW 함수의 1.4 표를 DBMS 어휘(SELECT/INSERT/MERGE/커서…)로 **번역한 형제차별 예시표**를 둔다.
2. **FW 함수(`function_summary.yaml`)** — 기존 [1] 범위를 "같은 모듈 안" → "**옆 형제 + (가능하면) 모듈 전역 맥락**에서 변별"로 확장. (전역 형제 이름 주입은 축 B 결정에 따름.)
3. **FW/DBMS 모듈(`module_summary.yaml` ×2)** — [2]에 고유성 지침 신설: 단순 "~조회 패키지/모듈" 금지, **대상 데이터 + 핵심 행위 + 범위(일/시간/광역 등)** 중 2축 이상을 한 줄에 드러내 형제 모듈과 변별.
4. **범용 예시(도메인 중립)** — 특정 도메인(결제/용수) 의존 없이 어디서나 쓰는 ❌짧은 광역 / ✅차별 축 2+ 쌍을 각 지점에 둔다. (아래 "범용 예시 풀".)

### B. 결정론적 고유화 후처리 — ❌ 미채택 (사용자 결정)
생성 후 dedup으로 기계적으로 유일화하는 방식은 **안 쓴다**. 사용자 의도 = "지침으로 생성될 때부터 고유하게". 따라서 본 스펙은 **순수 프롬프트 지침**으로만 해결하고, 후처리 코드는 추가하지 않는다. (※ 추후 잔여 중복이 문제되면 별도 스펙에서 재검토 가능 — 이번엔 범위 밖.)

## User Scenarios & Testing *(mandatory)*

### US1 - DBMS 형제 함수 변별 (P1)
같은 패키지의 형제 프로시저 노드들이 서로 다른 `logical_name`을 받는다(배치 맥락 활용).
- **Test**: PL/SQL 패키지 1개 분석 → 한 부모 아래 형제 노드들의 logical_name 전체 문자열 중복 0.

### US2 - 모듈/패키지 논리명 변별 (P1)
형제 모듈/패키지들이 "~데이터 조회 패키지"처럼 뭉뚱그려지지 않고 대상+행위+범위로 갈린다.
- **Test**: 여러 모듈 분석 → 모듈 logical_name 완전중복 0, 각 이름에 변별 축 2+.

### US3 - 범용성 (P2)
지침·예시가 특정 도메인에 묶이지 않아 임의 코드베이스(자바/C/PLSQL)에서 동작한다.
- **Test**: 도메인이 다른 2개 코드베이스에서 중복률이 기준선 대비 감소.

### Edge Cases
- **진짜 동일 기능 형제**(오버로드/래퍼)는 의미가 같을 수 있음 → 강제 변별이 **환각**(없는 차이 지어냄) 유발 금지. 지침은 "본문에 실제 있는 차별 축만"(헌법 추측금지) 우선, 그래도 같으면 축 B(결정론 한정자)로 처리.
- **고유성 범위** — 지침이 강제할 수 있는 건 "한 콜이 함께 보는 형제"(DBMS 배치=강제 가능). 모듈/호출을 넘는 전역 중복은 상대를 못 보므로 **차별 축 2+ 강제로 최대한 회피(노력)**까지. (후처리 없음이므로 전역 100% 보장 아님 — 사용자 수용.)
- **KV 캐시** — system/Common 변경 시 `check_byte_identical --update` 누락하면 캐시미스. 지침은 정적 텍스트로만(동적 주입은 축 B의 형제목록 옵션에서만).
- **출력 스키마 불변**(헌법) — `logical_name` 필드명/타입(`SummaryOutput.logical_name`, `ModuleSummaryOutput.logical_name`, `BatchAnalysisOutput.nodes[].logical_name`)은 그대로. 값만 더 고유해짐.

## Requirements *(mandatory)*

- **FR-001**: 두 전략(framework·dbms) **함수** logical_name 생성 지점에 "**생성 시점부터 형제와 전체 문자열 동일 절대 금지 + 차별 축 2+**" 지침을 둔다. **DBMS 배치는 형제를 한 콜에 함께 보므로 "이 배치 내 동일 문자열 0"을 강제 규칙으로** 명시.
- **FR-002**: 두 전략 **모듈/패키지** logical_name 생성 지점에 형제 변별 지침을 신설한다(단순 광역 표현 금지, 대상+행위+범위 중 2축 이상 노출, 형제 모듈과 동일 문자열 금지).
- **FR-003**: 각 지점에 **도메인 중립 범용 예시**(❌짧은 광역 / ✅차별 축 2+)를 추가한다.
- **FR-004**: 출력 스키마(필드명·타입)와 **계약 경계는 불변** — 프론트 `logical_name` 소비(navigator.ts:98)·Neo4j 노드 프로퍼티 키는 그대로. 값 품질만 향상.
- **FR-005**: system/Common 프롬프트 변경 시 KV 캐시 골든을 `check_byte_identical --update`로 재기준(헌법 KV캐시 친화).
- **FR-006**: ❌ 결정론 후처리 dedup 미채택(사용자 결정). 고유성은 **오직 생성 시점 지침으로만** 달성한다.

## Success Criteria *(mandatory)*
- **SC-001**: **DBMS 한 배치(같은 부모 형제 묶음) 내 logical_name 완전중복 0** — 지침으로 강제 가능한 영역.
- **SC-002**: 전체 분석 산출에서 logical_name **완전중복률이 변경 전 기준선 대비 대폭 감소**(목표 0에 수렴, 측정으로 확인). 형제 함수/모듈 각 이름에 변별 축 2+.
- **SC-003**: 지침·예시가 도메인 중립이라 임의 코드베이스(자바/C/PLSQL)에서 동일 적용.
- **SC-004**: 출력 스키마·계약·프론트 소비 불변(회귀 0). KV 캐시 골든 재기준 완료(캐시미스 0). 후처리 코드 추가 0(순수 프롬프트 변경).

## Plan (구현 순서 — 합의 후)
1. ✅ (결정 완료) 방법=지침만, 후처리 미채택. 범위=형제 강제+전역 최대회피.
2. DBMS `function_batch.yaml` 형제 변별 절+예시 신설(배치 내 동일 문자열 0 강제) → FW `function_summary.yaml` 범위 강화("같은 모듈 안"→형제+광역) → 양 `module_summary.yaml` 고유성 지침 신설(범용 예시 동일 풀 사용).
3. `check_byte_identical.py --update` 골든 재기준(KV 캐시).
4. 실제 파이프라인 실행 → 생성된 logical_name 중복률 측정([[principle-verify]] 실행검증, 기준선 대비) → 프론트 논리명 보기에서 회귀 0 확인.
