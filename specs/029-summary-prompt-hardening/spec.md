# Feature Specification: code_summary 프롬프트 환각·쓰기누락 방지 강화

**Feature Branch**: `029-summary-prompt-hardening`

**Created**: 2026-06-26

**Status**: Draft

**Input**: User description: "code_summary 프롬프트(dbms·framework 두 전략)의 summary 생성 지침을 강화해 LLM 환각·쓰기누락을 방지한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 노드 summary가 코드 동작을 환각 없이 정확히 묘사 (Priority: P1)

다운스트림 소비처(설계 그래프 계약 소비처·자연어 코드 검색)는 각 코드노드의 `summary`만 보고 그 노드가 "무엇을 어느 축으로 처리하는지"를 파악한다. 부모(또는 호출 함수) 노드의 summary가 하위 노드(자식 구문/하위 함수)가 이미 정확히 요약한 처리 축·대상을 무시하고 **다른 도메인 개념으로 환각**하면, 소비처는 그 노드를 다른 노드와 혼동하거나 잘못 분류한다.

**Why this priority**: 환각된 summary는 "조용한 오류"다 — 형식은 멀쩡해 보이나 의미가 달라, 검색이 엉뚱한 노드를 1위로 올리고 설계 소비처가 노드를 오분류한다. 실제로 "광역 합계" 노드가 "유역별 수종"으로 환각돼 다른 노드와 구별 불가가 된 사례가 있다. 모든 다운스트림 정확도의 토대다.

**Independent Test**: 하위 노드가 특정 처리 축("광역 합계용 태그별")으로 정확히 요약된 부모 노드를 재분석해, 부모 summary가 그 축을 계승하는지(다른 개념으로 둔갑하지 않는지) 확인.

**Acceptance Scenarios**:

1. **Given** 하위 노드가 "광역 합계용 태그별"로 정확히 요약된 부모 MERGE 노드, **When** 부모 summary를 생성, **Then** 부모 [핵심]이 "광역 합계"를 계승하고 "유역별 수종" 등 다른 축으로 치환하지 않는다.
2. **Given** 단서가 충돌하는 노드(이름은 A, 하위 요약은 B), **When** summary 생성, **Then** 코드 동작·하위 [핵심]을 우선해 가장 정확한 의미로 종합한다.

---

### User Story 2 - 쓰기 노드 summary가 쓰기 동작·대상을 드러냄 (Priority: P2)

쓰기 노드(INSERT/UPDATE/MERGE/DELETE)는 데이터 흐름의 종착점이다. 검색·설계 소비처는 "이 노드가 무엇을 어디에 기록/반영하는가"로 쓰기 흐름을 식별한다. `INSERT INTO T ... SELECT ...` 같은 복합문에서 SELECT 절이 본문 대부분이라, summary가 읽기·의도("조회해 준비", "조인한다")만 쓰고 **최종 쓰기를 누락**하면, 쓰기 노드가 읽기 노드처럼 보여 흐름 식별이 실패한다.

**Why this priority**: 쓰기 누락은 검색에서 그 노드(예: 로그 기록 INSERT)를 질의와 매칭 실패하게 만든다. 측정상 쓰기 노드의 8%가 [핵심]에 쓰기를 누락했고, 그 8%가 검색 실패 케이스와 일치했다.

**Independent Test**: writes가 있는 노드를 재분석해, [핵심]에 쓰기 동작(기록/반영/갱신/삽입)과 대상이 포함되는지 확인.

**Acceptance Scenarios**:

1. **Given** `INSERT INTO LOG_TB ... SELECT ...` 노드, **When** summary 생성, **Then** [핵심]에 "변경 이력을 로그 테이블에 기록" 같은 쓰기 동작·대상이 포함된다(읽기로 끝나지 않음).

---

### User Story 3 - 대상은 의미어로, 입력→출력을 종합, 예시는 범용 (Priority: P3)

summary는 사람이 읽는 글이므로, 쓰기 대상도 테이블명(예: `RDD01DD_TB`)을 그대로 노출하지 않고 의미어("일보")로 표현해야 한다. 또한 "어느 입력 테이블에서 읽어 → 어느 대상 테이블에 쓰는지"를 한 문장에 종합해야 흐름이 명확하다. 프롬프트 예시는 특정 도메인(K-water 유역·일보)에 과적합되면 다른 PL/SQL·응용코드에 부적절하므로 범용이어야 한다.

**Why this priority**: 정확도의 토대(P1·P2)는 아니지만, summary 품질·일관성·전략 무관 범용성을 높인다.

**Independent Test**: 재분석 summary에 코드 테이블명이 그대로 노출되지 않고, 입력→출력이 한 문장에 종합되는지 확인. 프롬프트 예시에 특정 도메인 고유명사가 없는지 확인.

**Acceptance Scenarios**:

1. **Given** 쓰기 노드, **When** summary 생성, **Then** 대상이 "RDD01DD_TB"가 아니라 "일보" 같은 의미어로 표현된다.

### Edge Cases

- 단서가 서로 충돌(노드 이름 vs 하위 요약)할 때 → 코드 동작·하위 [핵심]을 우선.
- 하위 요약 자체가 부정확할 때 → 코드 동작(GROUP BY 키·조인 기준·실제 R/W)을 진실로 우선.
- writes가 없는 노드(순수 SELECT·제어·위임) → 쓰기 동작 지침 비적용(읽기/위임 그대로).
- 전략별 그래프 구조 차이 → dbms는 "부모-자식(PARENT_OF 구문 트리)", framework는 "호출 함수-하위 함수(callee)" 용어로 같은 원칙을 각각 표현(상호 충돌 없이).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: summary 생성 지침은 부모(호출 함수) summary가 하위 노드(자식 구문/하위 함수) [핵심]이 명시한 **처리 축·대상·기준을 충실히 계승**하고, 근거 없이 다른 개념으로 치환(환각)하지 않도록 명시해야 한다.
- **FR-002**: 주어진 모든 컨텍스트 단서(하위 [핵심]·reads/writes 테이블·참조 심볼·이름·module_intent)를 무시·치환·누락하지 말고 반영하며, 단서 충돌 시 **코드 동작·하위 [핵심]을 우선**하도록 명시해야 한다.
- **FR-003**: 쓰기 노드(writes 있는 INSERT/UPDATE/MERGE/DELETE)의 [핵심]은 **쓰기 동작 + 대상**을 반드시 포함하고, SELECT/USING 절이 본문 대부분이어도 노드 본질을 쓰기로 잡도록 명시해야 한다.
- **FR-004**: 쓰기 대상은 테이블명을 그대로 노출하지 않고 **의미어**로 표현하도록 명시해야 한다.
- **FR-005**: 가능한 경우 summary가 **입력 테이블 → 출력 테이블**(어디서 읽어 어디에 쓰는지)을 종합하도록 안내해야 한다.
- **FR-006**: 프롬프트 예시는 특정 도메인에 과적합되지 않는 **범용 표현**이어야 한다.
- **FR-007**: 위 지침은 **dbms·framework 두 전략 모두**에 동일 원칙으로 반영하되, 전략별 그래프 구조에 맞는 용어(dbms=자식, framework=하위 함수)를 쓰고 **같은 프롬프트 내·전략 간 상호 충돌이 없어야** 한다.
- **FR-008**: 분할2(테이블 insights)·분할3(비즈니스 규칙)은 자체 환각 방지 지침이 있어 본 강화의 직접 범위 외이나, 공유 `_common`에 들어가는 지침은 세 분할 모두에 전파됨을 전제로 충돌이 없어야 한다.

### Key Entities *(include if feature involves data)*

- **코드노드 summary**: `[핵심]` 한 줄(노드의 비즈니스 의미) + 내용. 다운스트림이 노드를 이해하는 단일 출처.
- **하위 [핵심]**: 자식 구문(dbms)/하위 함수(framework)가 이미 요약한 처리 축·대상 — 부모가 계승해야 할 권위 정보.
- **쓰기 노드**: writes 관계가 있는 INSERT/UPDATE/MERGE/DELETE 노드 — 쓰기 동작·대상이 [핵심]에 드러나야 함.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 정정 후 재분석에서, 하위 노드가 정확히 요약한 처리 축이 부모 summary로 계승된다(환각 사례 0 — 예: "광역 합계" 노드가 "광역 합계"로 회복).
- **SC-002**: 쓰기 노드의 [핵심] 쓰기 동작 누락률이 0%다(정정 전 8%).
- **SC-003**: 도메인 고유명사를 제거한 범용 예시로 재분석해도 SC-001이 동일하게 성립한다(지침이 근본 효과이며 예시 의존이 아님).
- **SC-004**: summary를 소비하는 자연어 코드 검색의 요약질의(summary 스타일 질의) 정확도가 회복된다(정정 전 8/10 → 정정 후 10/10).

## Assumptions

- 분석 LLM(사내 qwen 또는 동급)이 강화된 프롬프트 지침을 따른다. 단 LLM 비결정성으로 케이스별 미세 변동은 잔존할 수 있다.
- 분할2(테이블)·분할3(비즈니스 규칙)은 기존 환각 방지(R/W 권위·"막무가내=환각"·하위호출 끌어올림 금지)가 충분하다고 가정해 본 강화의 직접 대상에서 제외한다.
- `_common`은 dbms/framework 각 전략의 3분할이 공유하므로, 거기에 넣는 지침은 세 분할에 전파된다.
- summary 품질이 다운스트림(설계 계약·코드 검색) 정확도와 직결된다는 전제(이번 측정으로 실증됨).
