# Feature Specification: 컬럼 논리명(logical_name) 생성

**Feature Branch**: `028-column-logical-name`

**Created**: 2026-06-26

**Status**: Draft

**Input**: User description: "COLUMN 노드에도 짧은 업무 표시명(논리명)을 LLM이 생성해 저장 — 테이블(spec 025-table-logical-name) 미러. 어느 전략(framework·dbms)이든 동일."

## 배경 (Context)

분석기는 테이블·컬럼의 비즈니스 의미를 산출해 설계 그래프에 싣는다. **테이블**은 spec 025로 **논리명(`logical_name`, 짧은 업무 표시명)** + 문장형 설명을 둘 다 갖는다. 그런데 **컬럼**은 문장형 의미(`analyzed_description`)만 있고 **논리명이 없어**, 화면에서 컬럼만 "논리명 없음"으로 비대칭하게 보인다. 본 기능은 테이블과 동일하게 **컬럼에도 짧은 업무 논리명을 LLM이 생성**해 저장한다.

**전략 불변(중요)**: framework·dbms **어느 전략이든 컬럼 논리명은 동일하게** 산출·저장되어야 한다(한 전략 전용 동작 금지).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 컬럼에 논리명 표시 (Priority: P1)

설계 그래프를 보는 사용자가 컬럼 노드를 보면, 테이블처럼 **짧은 업무 논리명**(예: 컬럼 `ord_dt` → "주문일자")이 함께 보여야 한다. 현재는 문장형 설명만 있고 논리명이 없어, 테이블과 일관성이 깨지고 한눈에 들어오는 업무명이 없다.

**Why this priority**: 테이블만 논리명이 있는 비대칭이 사용자 눈에 바로 띈다(이미 보고됨). 컬럼 논리명은 데이터 카탈로그·설계 화면의 가독성·일관성의 핵심.

**Independent Test**: 분석을 돌린 뒤 컬럼 노드에 `logical_name`이 채워지고, 그 값이 코드 식별자가 아니라 짧은 업무명인지 확인하면 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 의미 있는 컬럼들을 가진 소스를 분석, **When** 분석이 완료되면, **Then** 각 컬럼 노드에 짧은 업무 논리명(`logical_name`)이 저장된다.
2. **Given** 동일 소스를 **framework / dbms 각각**의 전략으로 분석, **When** 완료되면, **Then** 두 경우 모두 컬럼 논리명이 **동일한 방식**으로 채워진다(전략 차이로 빠지지 않음).
3. **Given** LLM이 어떤 컬럼의 논리명을 만들지 못한 경우, **When** 저장하면, **Then** **빈 논리명은 저장하지 않는다**(테이블 025와 동일 규칙).
4. **Given** 컬럼 `ord_dt`, **When** 논리명을 생성하면, **Then** "주문일자" 같은 **업무명**이지 `ord_dt`/코드 식별자/DDL 타입이 아니다.

### Edge Cases

- LLM이 컬럼명을 그대로 반복하거나(동어반복) DDL 타입을 논리명으로 내놓는 경우 → 그런 값은 의미 없는 논리명이므로 저장 품질 기준(업무명·코드식별자 아님)을 따른다.
- 한 컬럼이 여러 코드노드 관점에서 분석돼 논리명 후보가 여러 개 나오는 경우 → 일관된 단일 논리명으로 수렴(테이블 logical_name 수렴 방식과 동일).
- DDL에만 있고 코드에서 안 쓰이는 컬럼 → 논리명 후보가 없을 수 있으며, 그 경우 빈 논리명 미저장(설명 부재와 동일 취급).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 분석기는 각 **컬럼**에 대해 **짧은 업무 논리명(`logical_name`)**을 LLM으로 생성해야 한다(MUST). 테이블 논리명(spec 025)과 동일한 성격 — 코드 식별자·DDL 타입·동어반복이 아닌 업무 표시명.
- **FR-002**: 컬럼 논리명은 **framework·dbms 두 전략 모두에서 동일하게** 산출·저장되어야 한다(MUST). 전략별로 다르게 동작하거나 한쪽에서만 채워져선 안 된다.
- **FR-003**: **빈 논리명은 저장하지 않는다**(MUST) — 테이블 025의 "빈값 미저장" 규칙과 동일.
- **FR-004**: 컬럼 논리명은 그래프의 **COLUMN 노드 속성**으로 저장되어, 소비처(화면·카탈로그)가 테이블 논리명과 동일하게 읽을 수 있어야 한다(MUST).
- **FR-005**: 본 기능은 **컬럼 논리명 추가에 한정**되며, 기존 컬럼 속성(`name`/`description`/`analyzed_description`/타입 등)의 의미·생성·저장을 바꾸지 않아야 한다(MUST, 무회귀).
- **FR-006**: 검증은 실제 분석을 돌려 컬럼 노드에 논리명이 채워지는지 확인하는 방식이어야 한다(MUST) — 두 전략 각각 1회.

### Key Entities *(include if feature involves data)*

- **컬럼 의미 산출 단위**: 분석기가 한 컬럼에 대해 LLM으로 산출하는 의미. 현재는 `name`(컬럼명) + `description`(문장형 의미). 여기에 **`logical_name`(짧은 업무 논리명)**을 추가.
- **COLUMN 노드**: 그래프의 컬럼. 현재 속성에 `analyzed_description`은 있으나 `logical_name` 없음 → **`logical_name` 추가**(테이블 노드는 이미 보유).
- **컬럼 의미 생성 지시(프롬프트)**: 전략별로 분리되어 있으나, **두 전략 모두** 컬럼 논리명을 요청하도록 **동일하게** 갖춰져야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 분석 후, 업무 의미가 있는 컬럼의 **논리명 채움 비율이 테이블 논리명 채움 비율과 동급**(예: 의미 있는 컬럼의 대다수에 논리명 존재). 옛 상태(컬럼 논리명 0%)에서 개선.
- **SC-002**: **framework·dbms 각 전략으로 분석한 결과 모두** 컬럼 논리명이 채워짐(어느 전략에서도 0% 아님).
- **SC-003**: 저장된 컬럼 논리명 중 **빈 문자열 0건**, 그리고 표본 검수 시 코드 식별자·DDL 타입 그대로인 값 비율이 낮음(업무명 품질).
- **SC-004**: 기존 컬럼 속성(name/description/analyzed_description/타입) **회귀 0**(값·존재 불변).

## Assumptions

- 테이블 논리명(spec 025)의 생성·수렴·"빈값 미저장" 방식이 **검증된 패턴**이며, 컬럼 논리명은 이를 **미러링**한다(새 메커니즘 발명 아님).
- 컬럼 논리명의 1차 소비처는 **표시(화면·카탈로그)** — 짧은 업무명. 식별/조인 등에는 기존 `id`/`name`을 계속 쓴다.
- 본 작업은 **생산자(analyzer) 한정** — 소비처(architect/frontend/catalog)는 테이블 논리명을 이미 읽으므로, 컬럼 논리명도 동일 키로 노출되면 추가 소비처 변경 없이 표시 가능(소비처 표시 확장은 별도).
- 전략별 프롬프트는 둘 다 수정하되 **요청 내용은 동일**(전략 불변 보장).
