# Feature Specification: DBMS CALL 노드 → 호출 대상 링킹 계약 정정

**Feature Branch**: `023-call-target-linking`

**Created**: 2026-06-24

**Status**: Implemented (라이브 검증 완료)

**Input**: User description: "DBMS CALL 노드를 호출 대상에 직접 연결하고, 프로시저/모듈 단위 호출관계는 저장하지 않고 hop-over로 파생한다."

## 한 줄 요약

DBMS 분석에서 호출 관계의 **저장 진실**을 "프로시저↔프로시저"에서 "CALL 노드 → 호출 대상"으로 바로잡는다. 프로시저·모듈 단위 호출관계는 **저장하지 않고**, 그릴/계산할 때 CALL 노드를 소유 루틴·모듈로 거슬러 파생(hop-over)한다.

## Clarifications

### Session 2026-06-24

- Q: 컴포넌트·건강·분석순서용 프로시저↔프로시저 파생 시 CALL 노드를 어디까지 거슬러 해소하고, 스코프·자기재귀는? → A: 포함 체인 **최상위 루트 루틴**까지 해소, **internal 스코프만**, 자기재귀는 **"중첩 CALL이 거슬러 올라가 만난 재귀(DBMS)"는 자기루프로 만들지 않고** "루틴이 직접 자기참조(Framework)"는 보존 — 정정 이전 산출과 동등(parity).
- Q: 호출을 프로시저 단위로 보는 백엔드 소비처마다 해소 로직을 따로 두나? → A: **결정론 단일 해소기 하나**로 모든 소비처가 공유(중복 구현 0).
- Q: 같은 대상을 한 프로시저가 여러 번 부를 때 저장 다중성은? → A: **호출 지점(CALL 노드) 단위로 각각 저장**(저장 단계 합치기 없음). 프로시저·모듈 단위 합치기는 **파생 단계에서만**.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - CALL 노드가 호출 대상과 직접 이어진다 (Priority: P1)

설계그래프를 보는 사람이 DBMS 코드를 분석하면, 각 호출 구문(CALL 노드)이 자기가 실제로 부르는 대상(분석된 PROCEDURE/FUNCTION/TRIGGER 또는 외부 stub)과 엣지로 이어져, "어느 호출문이 무엇을 부르는가"가 호출 지점 단위로 추적된다.

**Why this priority**: 결함의 핵심 정정. 지금까지는 호출 구문이 대상과 안 이어지고 프로시저 루트끼리만 이어져 1차 사실이 그래프에 없었다.

**Independent Test**: DBMS 샘플 분석 후 그래프 덤프에서 ① 모든 internal 호출 엣지의 출발점이 CALL 종류 노드 ② 도착점이 호출 대상 정의 노드 ③ 출발점이 프로시저 루트인 호출 엣지 0건임을 원문과 대조.

**Acceptance Scenarios**:

1. **Given** 프로시저 A가 프로시저 B를 부르는 PL/SQL, **When** DBMS 분석 완료, **Then** `A의 CALL 노드 → B` 엣지가 있고 `A → B`(루트→루트) 직접 엣지는 없다.
2. **Given** 분석 범위 밖 프로시저 X 호출, **When** 분석, **Then** `:FUNCTION:EXTERNAL` stub(X) 생성 + 호출 엣지 출발점은 그 호출의 CALL 노드.
3. **Given** 자기 자신을 부르는 재귀 호출, **When** 분석, **Then** `CALL 노드 → 자기 프로시저` 엣지 정상 생성(자기루프 아님).

---

### User Story 2 - 프로시저·모듈 호출관계는 저장 없이 파생 (Priority: P1)

호출을 프로시저·모듈 단위로 봐야 하는 소비처(컴포넌트 군집, 건강 지표, DBMS 분석 순서, 프론트 보기모드)는 저장된 프로시저↔프로시저 엣지에 의존하지 않고, CALL 노드를 소유 루틴·모듈로 거슬러 해소(hop-over)해 그때그때 도출한다. 결과는 정정 이전과 동등하다.

**Why this priority**: 저장 진실을 바꾸면 프로시저 단위를 가정하던 소비처가 조용히 깨진다(회귀). 같은 우선순위로 함께 보장해야 정정이 회귀 없이 성립한다.

**Independent Test**: 정정 전/후 동일 DBMS 샘플로 컴포넌트 구성과 건강 지표(fan_in/fan_out/순환)·분석 순서가 동등함을 비교(특히 컴포넌트 0개 붕괴 없음).

**Acceptance Scenarios**:

1. **Given** 내부 호출이 충분한 DBMS 프로젝트, **When** 분석, **Then** 컴포넌트(호출 군집)가 정정 이전과 동등하게 형성(빈 결과 붕괴 없음).
2. **Given** 다른 프로시저를 여러 번 부르는 프로시저, **When** 건강 메트릭 계산, **Then** fan_out 등 호출 차수가 프로시저 단위로 올바르게 집계.
3. **Given** 호출 의존이 있는 DBMS 코드, **When** 분석 순서(바텀업 라운드·순환) 결정, **Then** 프로시저 단위 의존 위에서 정정 이전과 동등한 순서 산출.

---

### User Story 3 - 무변경 영역의 동작이 보존된다 (Priority: P2)

stdlib/빌트인 호출 제외, FRAMEWORK 전략의 함수↔함수 호출, 프론트 보기·탐색은 이번 정정의 영향을 받지 않고 기존대로 동작한다.

**Why this priority**: 변경 경계를 명확히 못 박아야 불필요한 회귀·과수정을 막는다.

**Independent Test**: ① FRAMEWORK 호출 엣지가 정정 전과 동일 ② DBMS 결과에 빌트인 접두 호출 엣지 0건 ③ 프론트 보기모드(모듈간·건강·협력군집·영역구조)가 정상 렌더, 일반 탐색기는 원본 표시.

**Acceptance Scenarios**:

1. **Given** FRAMEWORK 코드베이스, **When** 분석, **Then** 호출 엣지는 함수↔함수 직접 형태 그대로.
2. **Given** `DBMS_OUTPUT.PUT_LINE` 같은 빌트인 호출, **When** DBMS 분석, **Then** 그 호출에 대한 엣지·대상 노드 미생성.
3. **Given** 정정된 그래프, **When** 프론트 보기모드 진입, **Then** 빈화면·오류 없이 hop-over 관계 렌더; 일반 탐색기는 CALL 노드 포함 원본 표시.

---

### Edge Cases

- 한 프로시저가 같은 대상을 여러 번 호출 → 호출 지점마다 별도 CALL 노드 → 호출 지점 수만큼 엣지(저장 단위). 프로시저·모듈 단위로 볼 때 파생에서 1개로 집계.
- CALL 노드의 소유 루틴을 거슬러 못 찾으면(부모 체인 끊김) → 프로시저·모듈 파생에서 빠지되 조용히 묻지 말고 집계 가능하게(silent fail 금지).
- 같은 단순명 대상 루틴이 여러 개 → 기존 해소 규칙(같은 모듈 우선)으로 대상 정의 노드 결정.
- external stub 대상이 여러 호출 지점에서 참조 → stub 1개로 dedup, 각 호출 지점 CALL 노드에서 그 stub으로 엣지가 모임.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: DBMS 분석은 internal 호출에 대해 출발점이 그 호출의 CALL 노드, 도착점이 호출 대상 정의 노드(PROCEDURE/FUNCTION/TRIGGER)인 호출 엣지를 저장해야 한다.
- **FR-002**: DBMS 분석은 프로시저↔프로시저(루트→루트) 직접 호출 엣지를 저장하지 않아야 한다.
- **FR-003**: DBMS 분석은 모듈↔모듈 직접 호출 엣지를 저장하지 않아야 한다.
- **FR-004**: external 콜리는 stub 노드(외부 함수/모듈/스키마)로 생성·연결하되, 호출 엣지의 출발점은 그 호출의 CALL 노드여야 한다.
- **FR-005**: stdlib/빌트인(`DBMS_`/`UTL_`/`SYS_`/`ORA_`/`OWA_`/`STANDARD` 접두) 호출은 호출 엣지·대상 노드를 만들지 않아야 한다(기존 동작 보존).
- **FR-006**: 프로시저 단위 호출관계가 필요한 소비처(컴포넌트 군집화)는 저장된 프로시저↔프로시저 엣지에 의존하지 않고, CALL 노드를 포함 체인 최상위 루트 루틴으로 해소하고 internal 스코프만 써서 프로시저↔프로시저 관계를 파생한다. 중첩 CALL이 거슬러 올라가 만난 재귀는 자기루프로 만들지 않는다.
- **FR-007**: 프로시저 단위 호출 차수·순환 등 건강 지표는 FR-006과 동일한 해소 규칙으로 도출한 관계 위에서 계산되어, 정정 이전과 동등한 값을 산출해야 한다.
- **FR-008**: 재귀 호출(프로시저가 자기 자신 호출)은 `CALL 노드 → 자기 프로시저` 엣지로 정상 표현되어야 한다(저장 단계에서 누락 금지).
- **FR-009**: FRAMEWORK 전략의 호출 링킹(함수↔함수 직접)은 이번 변경의 영향을 받지 않아야 한다.
- **FR-010**: 프론트 보기모드(모듈간·건강·협력군집·영역구조)는 정정된 그래프에서 hop-over 관계를 정정 이전과 동등하게 렌더해야 하며, 일반 탐색기는 원본(CALL 노드 포함)을 그대로 표시해야 한다.
- **FR-011**: 소유 루틴 해소에 실패한 호출 등 파생 과정의 누락은 조용히 묻히지 않고 집계/관측 가능해야 한다.
- **FR-012**: CALL 노드를 소유 루틴/모듈로 거슬러 해소하는 로직은 결정론 단일 해소기로 두고 모든 백엔드 소비처가 공유해야 한다(같은 규칙 중복 구현 금지).
- **FR-013**: DBMS 코드 분석 순서(바텀업 라운드·순환 식별)도 저장된 프로시저↔프로시저 엣지에 의존하지 않고 FR-012의 단일 해소기로 도출한 관계 위에서 결정되어, 정정 이전과 동등한 분석 순서를 산출해야 한다.

### Key Entities *(include if feature involves data)*

- **CALL 노드**: PL/SQL 호출 구문 노드. PARENT_OF로 소유 루틴에 이미 연결됨. 정정 후 호출 엣지의 출발점.
- **호출 대상**: 호출되는 정의 노드 — internal(분석된 PROCEDURE/FUNCTION/TRIGGER) 또는 external stub.
- **호출 엣지(CALLS)**: 호출 관계(internal/external). 정정 후 DBMS에서 `CALL 노드 → 대상`. 관계 타입명은 불변, 끝점 의미만 정정. 정체성 = (출발 id, 도착 id).
- **파생 프로시저↔프로시저 / 모듈↔모듈 관계**: 저장되지 않는 도출물. CALL 노드를 소유 루틴·모듈로 거슬러 해소해 그릴/계산할 때 생성.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: DBMS 결과 그래프에서 출발점이 프로시저 루트인 호출 엣지가 **0건**이다.
- **SC-002**: DBMS 결과 그래프에서 internal 호출 엣지의 **100%**가 CALL 종류 노드에서 출발한다.
- **SC-003**: 정정 전/후 동일 DBMS 샘플에서 컴포넌트 개수·멤버 구성이 **동등**(0개 붕괴 없음)하다.
- **SC-004**: 정정 전/후 동일 DBMS 샘플에서 프로시저별 fan_in/fan_out/순환 포함 여부가 **동등**하다.
- **SC-005**: DBMS 결과에 stdlib/빌트인 접두 호출 대상·엣지가 **0건**이다.
- **SC-006**: FRAMEWORK 샘플의 호출 엣지 집합이 정정 전과 **동일**하다.
- **SC-007**: 프론트 보기모드(4종)가 정정된 그래프에서 빈화면·오류 없이 hop-over 관계를 렌더한다.

## Cross-Service Contract Impact

이 정정은 헌법의 ↓출력 계약(robo-architect/프론트행 Neo4j 그래프 스키마) 중 **CALLS 엣지의 끝점 의미**를 바꾼다(프로시저↔프로시저 → CALL 노드→대상). 관계 타입명·관계 타입 자체는 불변(단일 진실).

- **robo-data-frontend**: 영향 검토 완료 → **무변경**. 보기모드는 끝점을 소유 모듈·루틴으로 해소(모듈간·건강·협력군집·영역구조)하므로 끝점 의미 변경에 강건하고, 일반 탐색기는 원본 그대로 표시가 정상(CALL 노드 노출 = 의도, hop-over는 보기모드 전용). 프론트 코드 변경·후속 스펙 모두 불필요.
- **무영향**: antlr-code-parser 입력 계약(CALL 노드는 이미 antlr 산출), catalog 서비스 계약.

## Assumptions

- DBMS의 CALL 노드는 antlr 산출물에 이미 존재하며 그래프 노드로 저장되고 소유 루틴과 부모-자식 관계로 연결됨(현 동작 전제).
- 프로시저·모듈 단위로 호출을 보고/계산하는 모든 소비처는 동일한 hop-over 해소 규칙을 단일 해소기로 공유한다.
- 호출 차수·군집화·분석순서는 기존 정책대로 internal 호출 위주로 산정한다.
- 각 실행은 전체 재빌드(그래프 wipe 후 재생성)이며 증분 갱신이 아니다.
