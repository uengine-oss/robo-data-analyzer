# Feature Specification: 용어 정체화 — framework 중심 노드/타입/로그 용어 제거

**Feature Branch**: `019-terminology-realign`

**Created**: 2026-06-18

**Status**: Draft

**Input**: framework 중심 용어를 노드 라벨·분석단위 용어·로그에서 걷어내 "각 노드는 자기 진짜 종류로" 보이게 한다. 017(식별자 통일)·018(관계명 통합)에 이은 같은 종류 framework 부채 정리의 3물결.

> **★★최종 확정 모델 (2026-06-19) — 본 문서 내 "MODULE/FUNCTION 역할 병기·유지" 표현은 전부 이걸로 대체(폐기됨)**:
> 노드 라벨 = **실제 antlr 타입 하나(단일)** — `:FILE`/`:CLASS`/`:METHOD`/`:SELECT`/`:PROCEDURE`/`:PACKAGE`… (DBMS·framework 공통, DBMS는 서브라벨 0 = 원칙). **역할 레이블(FUNCTION/MODULE)은 Neo4j 저장 전면 폐기**(속성으로도 안 둠 — 타입이 곧 진실). 역할(호출가능/그릇)은 **소비처가 타입에서 파생**(METHOD/PROCEDURE/FUNCTION/TRIGGER→호출가능, FILE/CLASS/INTERFACE/RECORD→그릇). 예외: 외부 호출 stub만 `:FUNCTION:EXTERNAL`/`:MODULE:EXTERNAL`(타입 미상 fallback). [상세=메모리 [[manual]] §9 노드라벨]

## 개요 *(맥락)*

분석기는 소스코드를 그래프(노드+관계)로 만들고, 화면·카탈로그·설계연계가 소비한다. 그런데 framework(Java/C/Python) 관점의 용어가 **DBMS(PL/SQL)에까지 강제**돼, 비개발자가 그래프·화면·로그를 볼 때 "실제와 다른 종류"로 표시되는 부채가 누적됐다. 두 차례 정리했고(017 식별자 `function_id`→`id` 단일화, 018 관계명 `HAS_FUNCTION`→`HAS_MEMBER` 통합), 본 기능은 그 **3번째 물결 = 노드 종류·분석단위 용어·출력(로그)** 의 정체화다.

확정된 framework 부채(코드/로그 전수 확인):

1. **그릇(컨테이너) 종류가 `MODULE` 하나로 뭉뚱그려짐**: 폴더·파일·클래스를 담는 "그릇"이 모두 `MODULE`로 표시돼 진짜 종류(파일/클래스)가 가려진다. 특히 DBMS `.sql` 파일은 그릇 종류가 비어 `MODULE`만 남아 **"파일"이라는 정체가 사라진다**. "MODULE"은 사실 **"컨테이너 역할"**이지 노드의 실제 종류가 아니다.
2. **분석 단위가 전부 "함수(function)"로 불림**: 프로시저·SQL 구문(SELECT/IF)·구조(선언부) 등 모든 분석 단위가 코드·내부에서 "function"으로 명명돼, DBMS 구문까지 "함수"로 읽힌다.
3. **로그·실시간 스트림이 framework 위주로 출력**: 분석 진행 로그/이벤트가 DBMS 구문(SELECT/IF)도 일괄 "FUNCTION"으로 내보내 실제 종류가 안 보인다.

**설계 원칙(확정)**: "각 노드는 **자기 진짜 종류**를 라벨로 갖는다 — 폴더=패키지, 파일=파일, 클래스=클래스, DBMS .sql=파일, 나머지는 파서가 준 실제 타입(SELECT/IF/PROCEDURE…). 'MODULE' 같은 **역할** 용어는 부가 표시일 뿐 실제 종류를 가리지 않는다." 종류의 출처는 이미 있는 언어별 종류 도출 규칙(온톨로지)이다. (017·018과 동일 방향 — 같은 뜻은 같게, framework 전용 강제는 제거.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 그릇 노드가 "정체대로" 보인다 (Priority: P1)

사용자가 그래프·화면·네비게이터에서 담는 그릇을 볼 때 **실제 종류대로** 보인다 — 폴더는 패키지, 파일은 파일, 클래스는 클래스. DBMS `.sql` 파일도 "파일"로 보인다. 더 이상 모든 그릇이 "MODULE"로 뭉뚱그려지지 않는다.

**Why this priority**: 비개발자가 그래프를 이해하려면 종류 표시가 실제와 맞아야 한다. 현재 DBMS 파일이 "MODULE"로 떠 "이게 무슨 모듈이지?" 혼란을 준다(사용자 직접 지적).

**Independent Test**: DBMS 프로젝트와 Java 프로젝트를 각각 분석한 뒤, 화면/네비게이터에서 .sql 파일이 "파일", Java 클래스가 "클래스"로 표시되고, "MODULE" 단독 표시가 사라졌는지 확인한다. 네비게이터의 그릇 목록(모듈 섹션)이 여전히 정상 채워지는지(회귀 0) 확인한다.

**Acceptance Scenarios**:

1. **Given** DBMS `.sql` 파일, **When** 분석 후 화면을 보면, **Then** 그 그릇이 "파일(FILE)"로 표시된다("MODULE" 아님).
2. **Given** Java 클래스, **When** 분석 후 화면을 보면, **Then** "클래스(CLASS)"로 표시된다.
3. **Given** 그릇 노드들, **When** 네비게이터의 그릇 목록을 보면, **Then** 종류가 바뀌어도 목록이 빠짐없이 채워진다(회귀 0 — 소비처가 타입 집합으로 그릇 식별).

---

### User Story 2 - 로그·진행 표시가 실제 종류를 보여준다 (Priority: P1)

사용자(또는 운영자)가 분석 진행 로그·실시간 스트림을 볼 때, 각 노드가 **실제 종류**(SELECT/IF/PROCEDURE/파일…)로 표시된다. DBMS 구문이 일괄 "FUNCTION"으로 뭉뚱그려지지 않는다.

**Why this priority**: 로그가 framework 위주라 "내 DBMS 코드가 제대로 분석되는지" 알 수 없다(사용자 직접 지적). 분석 진행을 신뢰하려면 출력이 실제와 맞아야 한다.

**Independent Test**: DBMS 분석을 실행하고 진행 로그/스트림 이벤트를 보면, 노드 이벤트의 종류가 실제 타입(:SELECT/:IF/:PROCEDURE/:FILE 등)으로 찍히는지 — "FUNCTION" 고정 표기가 사라졌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** DBMS SELECT 구문 노드, **When** 분석 진행 로그/스트림을 보면, **Then** 종류가 "SELECT"로 표시된다("FUNCTION" 아님).
2. **Given** 분석 산출 그래프, **When** 영속된 노드 라벨을 보면, **Then** 로그 표시와 실제 라벨이 일치한다(표시-영속 불일치 0).

---

### User Story 3 - 분석 단위 용어가 종류 중립적이다 (Priority: P2)

코드·내부 명명에서 분석 단위를 가리키는 용어가 **종류 중립**이 되어, 프로시저·구문·구조를 모두 포괄한다. "function/함수"라는 framework 단어가 DBMS 구문·구조까지 가리키지 않는다.

**Why this priority**: 유지보수·가독성 부채 — 코드를 읽는 사람이 "function"을 보면 framework 함수로 오해한다. 단 사용자 직접 노출보다 내부 명명이라 P2.

**Independent Test**: 분석 단위를 표현하는 핵심 타입/상태/단계 명칭이 종류 중립 용어로 바뀌고, framework 전용 "function" 잔재가 (의도된 진짜 함수 외에) 분석단위 명명에서 0 인지 전수 확인한다.

**Acceptance Scenarios**:

1. **Given** 분석 단위(프로시저·구문·구조), **When** 코드/명명을 보면, **Then** 종류 중립 용어로 일관되게 불린다.
2. **Given** 변경 후, **When** 소비처(화면·카탈로그·연계)를 보면, **Then** 동작 회귀 0.

### Edge Cases

- **DBMS 파일에 프로시저 여러 개**: 파일은 "파일"로, 그 안 프로시저는 각자 종류로 — 그릇-멤버 관계는 018대로 유지.
- **외부 호출 stub(분석 범위 밖 콜리의 소유 컨테이너)**: 종류 미상이라 "컨테이너 역할"만 부여(실제 종류 라벨 없음) — 정상 허용.
- **그릇 종류 라벨이 바뀌어 소비처가 옛 'MODULE' 가정을 깨는 경우**: 소비처를 **타입 집합으로 그릇 식별**하도록 전수 정합한다(회귀 0). 옛 'MODULE' 가정 잔재 0.
- **표시와 영속의 불일치**: 로그/스트림 표시 종류 = 실제 영속 라벨과 항상 일치(둘 다 실제 종류).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 그릇(컨테이너) 노드는 **실제 종류**를 자기 라벨로 가져야 한다 — 폴더=패키지, 파일=파일, 클래스=클래스, DBMS `.sql`=파일. 단일 "MODULE" 라벨로 종류를 덮어쓰지 않는다.
- **FR-002**: 역할 레이블(FUNCTION/MODULE)은 **Neo4j 에 저장하지 않는다**(폐기). 역할(호출가능/그릇)은 소비처가 **노드 타입에서 파생**한다(타입→역할 단일 맵). 소비처가 "그릇 전체"·"호출가능 전체"를 찾던 방식은 역할 라벨 대신 **타입 집합**으로 식별하도록 전수 정합한다(회귀 0).
- **FR-003**: 그릇 종류는 **기존 언어별 종류 도출 규칙(온톨로지)**에서 가져온다(새 매핑 발명 금지). 도출된 종류가 없을 때(예: DBMS 파일)는 "파일"을 기본으로 한다.
- **FR-004**: 분석 진행 **로그·실시간 스트림**의 노드 표시 종류는 **실제 종류**(SELECT/IF/PROCEDURE/파일…)여야 하며, 고정 "FUNCTION" 표기를 쓰지 않는다.
- **FR-005**: 로그/스트림에 표시되는 종류는 **그래프에 영속되는 실제 라벨과 일치**해야 한다(표시-영속 불일치 0).
- **FR-006**: 분석 단위(프로시저·구문·구조를 포괄)를 가리키는 **내부 용어·명명**은 종류 중립이어야 한다 — framework 전용 "function/함수"가 분석단위 전체를 가리키지 않는다. **중립 용어 = `CodeNode`**(사용자 결정 2026-06-18): dataclass `Function`→`CodeNode`, state `functions`→`code_nodes`, step `analyze_function`→`analyze_node`(또는 동급), `upsert_functions`→`upsert_code_nodes`, `function_*` 식별자 → 종류중립. ★단 **실제 "함수/프로시저" 루틴**을 구체적으로 가리키는 곳(라벨 `:FUNCTION`/`:PROCEDURE`, 루틴 판별)은 그대로 — 그건 진짜 함수 의미라 옳다.
- **FR-007**: 본 변경으로 기존 소비처(화면·카탈로그·설계연계)가 깨지지 않아야 한다(**회귀 0**). 라벨/용어 변경 시 **모든 소비처를 전수 정합**하고 옛 가정(예: 그릇=항상 "MODULE") 잔재를 제거한다.
- **FR-008**: 라벨·종류 변경은 **생산자(분석기)와 소비처(화면 등)를 원자적으로 동시 정합**한다 — 한쪽만 바꿔 그릇 목록이 비는 등의 일시 회귀를 만들지 않는다.
- **FR-009**: 017의 식별자 `id` 단일화·018의 관계 통합·구조노드·NEXT 등 기존 정합 결과는 **유지**한다(되돌리지 않음).
- **FR-010**: 매 분석은 기존 정책대로 **파괴적 전체 재빌드**로 동작하며 본 변경이 이를 바꾸지 않는다.

### Key Entities *(그래프 = 노드 + 관계)*

- **그릇(컨테이너) 노드**: 실제 종류 단일 라벨 — `PACKAGE`(폴더/패키지) · `FILE`(파일: C/Python/DBMS) · `CLASS`(클래스: Java 등). 역할 라벨(MODULE) 없음 — 그릇 여부는 소비처가 타입으로 판정.
- **분석 단위 노드**: 루틴(프로시저/함수/메서드/트리거) · 구문(SELECT/IF/LOOP…) · 구조(DECLARE/TRY/TRIGGER_BLOCK) — 모두 종류 중립 용어로 포괄, 각자 실제 타입 라벨.
- **데이터 타입 노드**: `DATA_TYPE`(struct/union/enum) — 그릇 아님(별개).
- **출력(로그/스트림) 표시 종류**: 노드의 실제 종류와 일치.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 분석 후 화면/네비게이터에서 DBMS `.sql`=파일, Java=클래스로 표시되고 "MODULE" 단독 표기가 0 이다(외부 stub 제외).
- **SC-002**: 그릇 종류 변경 후에도 네비게이터의 그릇 목록 등 기존 소비처가 빠짐없이 동작한다(회귀 0건).
- **SC-003**: DBMS 분석 진행 로그/스트림에서 노드 종류가 실제 타입으로 표시되며 고정 "FUNCTION" 표기가 0 이다.
- **SC-004**: 로그/스트림 표시 종류와 그래프 영속 라벨이 100% 일치한다.
- **SC-005**: 분석 단위 명명에서 framework 전용 "function" 잔재가 (의도된 실제 함수 외) 0 이며, 소비처 회귀 0건.

## Assumptions

- 대상 = `robo-data-analyzer`(생산자) + 소비처 catalog·frontend·architect(연계).
- 그릇 종류 도출은 기존 온톨로지(`shared/lang/ontology_roles.yaml`)를 단일 출처로 재사용한다(신규 매핑 없음).
- 매 분석은 파괴적 전체 재빌드 정책 유지.
- 017 id 단일화·018 관계/구조/NEXT 정합은 올바른 결과이므로 유지한다.
- "MODULE→실제 종류"는 frontend 라벨 처리(분류·카드 라우팅·네비게이터·라벨 순서)와 **함께** 가야 하며, 반응형 부분 수정은 회귀를 만든다(원자 정합).
- 검증은 단위테스트가 아니라 실제 파이프라인을 돌려 그래프·로그를 원문과 대조한다(분석 실행·커밋은 사용자 OK 후).
- 018 의 US4(MODULE→FILE/CLASS)는 본 스펙으로 흡수한다(018은 US1-3 완료 + US5 룰만 잔여).
