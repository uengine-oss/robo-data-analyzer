# Feature Specification: 테이블 논리명 부여 + 설명·요약 비즈니스 품질

**Feature Branch**: `025-table-logical-name`

**Created**: 2026-06-26

**Status**: Draft

**Input**: User description: "테이블에 logical_name(짧은 도메인 표시명) 부여 + node summary/테이블 설명을 더 비즈니스 로직답게(식별자·값·코드 보존, 날조 금지)."

## 배경 (실측)

- 코드노드는 `logical_name`(짧은 도메인 표시명, 100% 보유)을 갖는데 **테이블은 없음** — `name`(물리명 RDD01DD_TB)·`analyzed_description`(문단)만. 프론트는 테이블을 물리명으로만 표시.
- node summary 생성 규칙은 "비즈니스 의미·SQL키워드 금지·값/코드 보존·추측 금지"를 **이미 명시**하나, 프롬프트 **예시가 DB 기계어**("수량(VAL)·카운트(CNT) 컬럼 UPDATE, 신규 행 INSERT")라 출력이 기계어로 샌다("MERGE 일치 행 존재 시 수량 컬럼만 갱신").

이 기능은 (1) 테이블에 짧은 논리명을 부여해 사람이 읽을 표시명을 주고, (2) 요약·설명을 더 비즈니스-이벤트 중심으로 다듬는다 — **단 식별자·값·상태코드는 보존하고, 없는 내용은 만들지 않는다.**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 테이블이 사람이 읽을 논리명을 갖는다 (Priority: P1)

분석을 마치면 각 테이블은 물리명(RDD01DD_TB)과 별개로 짧은 도메인 표시명("일 용수공급량 일보")을 가진다. 사용자가 그래프·화면에서 테이블을 보면 무슨 테이블인지 물리명을 몰라도 이름만으로 안다.

**Why this priority**: 가독성의 직접 개선. 코드노드는 이미 논리명이 있는데 테이블만 없어 비대칭. 물리명만으론 비전문가가 못 읽는다.

**Independent Test**: 재분석 후 테이블에 논리명이 채워졌는지, 그 논리명이 물리명과 다른 사람이 읽을 표현인지, 화면에 표시되는지.

**Acceptance Scenarios**:

1. **Given** 코드가 사용하는 테이블, **When** 분석 완료, **Then** 그 테이블은 짧은 논리명(도메인 표시명)을 갖는다.
2. **Given** 테이블 논리명, **When** 화면에서 테이블 노드를 봄, **Then** 논리명이 표시되고 물리명도 병기된다.
3. **Given** 논리명을 만들 근거가 부족한 테이블, **When** 분석, **Then** 빈 논리명은 저장하지 않는다(없는 이름 날조 금지).

### User Story 2 - 요약·설명이 더 비즈니스 로직답다 (Priority: P2)

노드 요약과 테이블 설명이 DB 기계어(행/컬럼 UPDATE/INSERT)보다 업무 이벤트 중심으로 읽힌다. 단 의미 있는 식별자·값·상태코드(태그 유형 M/Q/S/D/P, SW/IN/OUT, 상태값)는 그대로 보존되고, 입력에 없는 내용은 추가되지 않는다.

**Why this priority**: 가독성·이해도 향상. 단 P2 — 핵심 정보(값/코드) 보존과 날조 금지가 우선이고, 문체 개선은 그 다음. 또 요약은 다른 시스템(검색) 입력이라 신중.

**Independent Test**: 재분석 후 요약 샘플을 원문 코드와 대조 — 업무 표현이 늘었는지, 값/코드가 유지됐는지, 없는 내용이 추가되지 않았는지.

**Acceptance Scenarios**:

1. **Given** 쓰기 노드, **When** 요약 생성, **Then** "기존 행 갱신/신규 삽입" 같은 기계어보다 업무 이벤트("기존 집계 갱신·신규 반영")로 표현하되 값·코드는 보존된다.
2. **Given** 도메인 코드값(M/Q/S/D/P 등)이 있는 노드, **When** 요약, **Then** 그 코드값이 요약에 보존된다.
3. **Given** 입력에 없는 책임·테이블, **When** 요약·설명, **Then** 추가되지 않는다(추측 금지).

### Edge Cases

- 논리명 근거 부족(접근 코드 빈약·설명 없음) → 빈 논리명 미저장(날조 금지).
- 요약 문체를 바꾸다 값/코드 누락 → 금지(값 보존이 문체보다 우선).
- 요약 변경이 검색(별도 시스템) 정확도에 영향 → 재측정 동반, 회귀 시 재고.
- framework(테이블 R/W 있으나 PL/SQL 아님) → 논리명 규칙 동일 적용(전략무관).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 테이블 설명 생성 시 **짧은 논리명(도메인 표시명)** 을 문단 설명과 **별도로** 산출하고 테이블에 저장해야 한다.
- **FR-002**: 테이블 논리명은 **물리명과 다른 사람이 읽을 도메인 표현**이어야 하며, 물리 식별자(테이블명) 그대로 쓰지 않는다.
- **FR-003**: **빈 논리명은 저장하지 않는다**(근거 없으면 미부여 — 빈값미저장·날조 금지).
- **FR-004**: 화면(노드 표시)은 테이블을 **논리명으로 표시**하고 물리명을 병기해야 한다.
- **FR-005**: 요약·설명은 **업무 이벤트 중심**으로 표현하되, **의미 있는 식별자·값·상태코드(도메인 코드값)는 반드시 보존**해야 한다.
- **FR-006**: 요약·설명은 **입력에 없는 내용을 추가하지 않는다**(추측 금지 — 기존 규칙 유지).
- **FR-007**: 모든 변경은 **전략무관**(DBMS·framework 공통)이어야 한다.
- **FR-008**: 요약 생성 지침 변경은 **반복 측정 비용을 늘리지 않아야** 한다(공통 지침의 동일성 유지 — 캐시 친화).

### Key Entities *(include if feature involves data)*

- **테이블 노드**: 물리명 + **논리명(신규, 짧은 도메인 표시명)** + 문단 설명(analyzed_description). 논리명·설명은 분석이 산출.
- **노드 요약**: [핵심]+내용. 업무 이벤트 중심 + 값·코드 보존 + 날조 금지.
- **테이블 표시(화면)**: 논리명 우선 + 물리명 병기.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 재분석 후 코드가 사용하는 테이블 중 **논리명 보유 비율이 높다**(근거 있는 테이블 대부분). 빈 논리명 0건 저장.
- **SC-002**: 테이블 논리명이 **물리명과 다른 읽을 수 있는 도메인 표현**(샘플 대조로 확인).
- **SC-003**: 화면에서 테이블이 **논리명으로 표시**된다(물리명 병기).
- **SC-004**: 요약 샘플 대조 시 **도메인 값·코드(M/Q/S/D/P 등) 보존율 100%**, **입력에 없는 내용 추가 0건**.
- **SC-005**: 요약 변경 후 검색(별도 시스템) 정확도 **재측정** — 의미 있는 하락 시 재고.

## Assumptions

- 코드노드 logical_name 생성 메커니즘이 이미 있으므로 테이블에 같은 패턴을 확장한다.
- 요약 생성 규칙은 이미 "비즈니스+값보존+날조금지"를 명시 — 변경은 **예시·지침 보강**이지 규칙 재정의가 아니다.
- 측정 데이터는 RWIS(단일 오라클). framework는 구조 일반화로 대비.
- 요약은 임베딩 검색(별도 프로젝트)의 입력이므로, 문체 변경 시 그쪽 재측정을 동반한다(회귀 모니터).
- 본 작업은 spec 024(설명 유실 복구·식별자 정규화)와 함께 1회 재분석으로 검증한다(공유 그래프 1회 변경).
