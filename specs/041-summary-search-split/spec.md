# Feature Specification: 요약·검색 서술 분리 (summary 다이어트 + 검색 전용 서술 신설)

**Feature Branch**: `041-summary-search-split`

**Created**: 2026-07-09

**Status**: Draft

**Input**: User description: "analyzer summary/검색필드 재설계 — (1) 검색·비즈니스용 별도 속성(가칭 search_text) 신설: 실제 소스코드의 조건분기·상태전이·상태코드·테이블 상호작용을 자연어로 담되 코드 복붙 금지, 비즈니스 의미 융합, 프론트 비노출·임베딩/검색 전용. framework·dbms 양 전략 공통. (2) 검색 필드가 놀이터 골드셋 ablation으로 수치 입증되면 summary를 진짜 요약으로 다이어트(통상 1~2줄, 최대 3줄 마지노선, 한 줄 달랑 금지). 프론트 수정은 후속. 마이그레이션 = 더하기 먼저 → 검증 → 빼기. 전량 재분석 전 소수 대표노드 파일럿 + 민감질의 재검색으로 방향 확인."

## 배경 (왜 지금 이 재설계인가)

현재 코드노드의 `summary` 하나가 두 주인을 섬긴다 — ① 사람이 읽는 "요약"(프론트 표시·상위 분석 입력) ② 요구사항 검색의 임베딩 재료. 그 결과 요약이 길어지고, 검색 쪽은 요약들이 서로 비슷해 **코드 원문 180자를 임베딩에 섞는 "지문 목발"**로 겨우 변별하는 상태다(놀이터 실측: 코드 원문 제외 시 SKT 결제망 정답 2개 유실). 근본책은 **역할별 필드 분리**: 사람용 요약은 짧게, 검색용 서술은 변별력 있게 따로.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 검색 전용 서술 필드 신설 (Priority: P1)

분석 실행 시 각 코드노드에 대해, 사람이 읽는 summary와 **별개의 "검색·비즈니스용 서술"**을 함께 생성해 그래프에 저장한다. 이 서술은 소스코드의 **조건 분기·상태 전이·상태/결과 코드 값·상호작용 테이블(읽기/쓰기)**을 자연어 비즈니스 의미로 융합해 담는다(예: "주문 처리 상태코드는 결제 완료면 'PAID', 한도 초과면 'OVER_LIMIT'으로 분기"). 코드 문장 복붙은 금지하되, 코드 어휘(테이블명·상태코드 리터럴 등)는 자연어 설명과 함께 보존한다 — 사람 말과 코드 말의 어휘 간극을 잇는 것이 목적이다. 이 필드는 프론트 화면에 노출되지 않으며 검색(임베딩·재순위·용어집 생성) 전용이다.

**Why this priority**: 검색 변별력의 근본책이자 모든 후속 단계(수치 게이트→summary 다이어트)의 전제. "더하기 먼저" 순서상 첫 단계라 기존 동작(요약·검색) 어느 쪽도 건드리지 않아 위험이 가장 낮다.

**Independent Test**: 소수 대표 노드(민감질의 관련: 결제망·정산·주문취소)만 새 프롬프트로 재분석해, 생성된 서술을 원문 소스코드와 정밀 대조 — 조건분기·상태코드·테이블 상호작용이 자연어로 정확히 담겼는지, 코드 복붙이 없는지 확인.

**Acceptance Scenarios**:

1. **Given** 새 프롬프트로 분석된 코드노드, **When** 검색 서술을 원문 코드와 대조, **Then** 원문의 조건 분기·상태 전이·상태코드 값·읽기/쓰기 테이블이 자연어 문장으로 빠짐없이 담겨 있다.
2. **Given** 생성된 검색 서술, **When** 형태 검사, **Then** 코드 라인·SQL 문장 복붙이 없다 — 단 테이블명·상태코드 리터럴 같은 코드 어휘는 자연어 설명과 병기되어 있다.
3. **Given** framework(함수 단위)·dbms(배치) 양 전략, **When** 각각 분석 실행, **Then** 두 전략 모두 동일한 규칙으로 검색 서술을 생성한다(전략별 품질 편차 없음).
4. **Given** 프론트 화면 전체, **When** 노드 상세·목록·비교 등 어떤 화면을 열어도, **Then** 검색 서술은 노출되지 않는다.

### User Story 2 - 검색 성능 수치 게이트 (ablation 입증) (Priority: P2)

**위험질의 세트**로 임베딩 재료 두 안을 비교 측정한다: **[현행: 요약+코드 원문 180자] vs [신규: 요약+검색 서술(코드 원문 제외)]**. 위험질의 세트 = 골드셋 중 과거 검색이 실패했었거나 코드 원문 목발에 의존해 정답을 건졌던 민감질의(결제망·정산·주문취소 등 소수). **골드셋 전체(53문항) 전량 측정은 하지 않는다 — 질의가 많으면 측정이 너무 오래 걸린다(사용자 지시 2026-07-09).** 신규 재료가 위험질의에서 무회귀(정답 유실 0)임이 확인되어야만 다음 단계(summary 다이어트)로 진행한다. 미달이면 다이어트에 착수하지 않고 실패 부검→서술 생성 규칙 개선을 반복한다.

**Why this priority**: "검색이 새 필드로 서는가"를 숫자로 증명하는 관문. 이 게이트 없이 summary를 줄이면 검색 회귀(과거 요약 재생성 시 77→34% 폭락 실측)를 재현할 위험. 판정은 가장 무너지기 쉬운 질의(위험질의)에 집중하는 것이 시간 대비 검증력이 최대다.

**Independent Test**: 파일럿 노드 재분석 → 위험질의만 재검색해 방향 확인 → 이상 없으면 전량 재분석 → 위험질의 세트로 최종 판정.

**Acceptance Scenarios**:

1. **Given** 파일럿 재분석된 노드들, **When** 위험질의(결제망·정산·주문취소)를 신규 재료로 재검색, **Then** 해당 질의의 기존 정답 유실이 0이다.
2. **Given** 전량 재분석된 두 그래프(쇼핑몰·SKT), **When** 위험질의 세트를 신규 재료로 측정, **Then** 정답 회수가 현행과 동등 이상(유실 0)이다.
3. **Given** 측정 결과가 무회귀 미달, **When** 게이트 판정, **Then** summary 다이어트에 착수하지 않고 실패 질의 부검→생성 규칙 개선을 반복한다.

### User Story 3 - summary 다이어트 (진짜 요약으로 축소) (Priority: P3)

검색이 새 필드에 안착한 뒤, summary를 "아, 이게 뭐 하는 거구나"를 즉시 파악하는 진짜 요약으로 축소한다: **통상 1~2줄, 코드 용량·내용에 비례해 최대 3줄이 마지노선. 성의 없는 한 줄 달랑은 금지.** 분기·상태코드 등 세부는 검색 서술이 담당하므로 요약에서 중복 서술하지 않는다. 2섹션(`[핵심]`+내용) 구조는 요약 전체가 곧 핵심이 되므로 존재 이유가 사라진다 — 마커 처리를 확정하고 산출 형식 검증·프론트 표시 양쪽 정합을 보장한다.

**Why this priority**: 순수 UX 개선 — 검색 게이트(US2) 통과 후에만 안전하게 가능. 순서를 어기면 검색 회귀 위험.

**Independent Test**: 다이어트 프롬프트로 파일럿 노드 재분석 → 요약 길이·파악성(원문 대조 표본 검수)과 위험질의 무회귀를 함께 확인.

**Acceptance Scenarios**:

1. **Given** 다이어트 프롬프트로 재분석된 그래프, **When** 전 노드 summary 길이 검사, **Then** 최대 3줄 이내이며, 표본 검수에서 "무엇을 하는지" 파악에 충분하다(한 줄 달랑 없음 — 단순 노드도 무엇을 어디에 하는지는 담김).
2. **Given** 다이어트 후 그래프, **When** 위험질의 세트 재측정, **Then** 무회귀(검색은 이미 검색 서술 기반이므로 요약 축소의 영향 0).
3. **Given** 마커 처리 확정안 반영, **When** 분석 실행과 프론트 표시 확인, **Then** 산출 형식 검증(마커 강제 등)과 프론트 요약 표시(첫 문단 분리)가 모두 정상 동작한다.
4. **Given** 상위(부모·호출자) 노드 분석, **When** 자식 요약이 입력으로 전달되는 상향 분석 실행, **Then** 부모 요약·규칙 품질이 다이어트 전과 동등하다(자식→부모 전달 재료 재정의 포함).

---

### Edge Cases

- **단순 노드(위임 한 줄·COMMIT·커서 open 등)**: 검색 서술 재료가 빈약 — 빈 값 허용 여부와 검색 폴백 규칙(빈 값이면 summary로 폴백) 필요.
- **프론트의 속성 일반 나열 화면**: 노드 속성을 동적으로 전부 나열하는 화면이 있으면 새 필드가 의도치 않게 노출될 수 있음 → 프론트 소비 지점 전수조사가 선행돼야 함.
- **summary의 다른 소비처**: 프론트 표시 외에 summary를 재료로 쓰는 곳(상향 분석 입력, 카탈로그 임베딩, 모듈 요약 등)이 있으면 다이어트가 그쪽 품질에 파급 → 계획 단계 전수조사 필수.
- **혼재 그래프**: 재분석 전 노드(새 필드 없음)와 혼재 시 검색 파이프라인이 깨지지 않아야(필드 부재 폴백).
- **LLM이 검색 서술에 코드 복붙**: 생성 규칙 위반 감지 기준(코드 라인 인용·식별자 나열 비율)을 품질 게이트로.
- **놀이터 캐시·용어집 stale**: 재분석 후 임베딩 캐시·용어집 자산이 낡음 → 자동 재생성(지문 감지)이 실제로 동작하는지 확인.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 분석 산출물은 코드노드마다 **검색 전용 서술 필드**(가칭 search_text)를 생성해야 한다. 내용 = ① 조건 분기(어떤 조건이면 어떤 결과) ② 상태 전이(무슨 상태가 무엇으로 바뀌는지) ③ 상태·결과 코드 값과 그 의미 ④ 상호작용 테이블(읽기/쓰기)과 그 업무 맥락 — 전부 자연어 비즈니스 의미로 융합해 서술한다. **작성 관점은 코드의 자연어 번역이 아니라 "어떻게 쓰면 의미 검색에 잘 걸리는가"** — 사람이 업무 말로 묻는 요구사항형 질의에 걸리도록 업무 어휘로 서술하되, ①~④(특히 상태·코드 값과 분기 갈래, 도메인·비즈니스 로직)는 **하나도 빠짐없이(누락 0)** 담는다. 값 집합(IN 리스트·복수 분기값)은 모든 값을 나열한다 — 하나라도 빠지면 그 값을 묻는 질의가 이 노드를 영원히 못 찾는다.
- **FR-002**: 검색 서술은 **코드 원문 복붙 금지** — 코드 라인·SQL 문장 인용이나 식별자 단순 나열이 아니라 의미 문장이어야 한다. 단 **코드 어휘(테이블명·상태/결과 코드 리터럴·핵심 도메인 식별자)는 자연어 설명과 병기해 보존**한다(사람 말↔코드 말 어휘 간극을 잇는 검색 변별력의 핵심).
- **FR-003**: 검색 서술은 **프론트 비노출** — 사용자 화면 어디에도 표시되지 않으며 검색(임베딩·재순위·용어집 생성) 전용이다. 기존 프론트 소비 계약은 변경하지 않는다(프론트 코드 수정 0이 이 스펙의 범위).
- **FR-004**: framework·dbms **양 전략이 동일 규칙**으로 검색 서술을 생성해야 하며, 특정 도메인(재고·주문·특정 테이블명 등)에 의존하는 하드코딩 규칙이 생성 로직에 없어야 한다.
- **FR-005**: **마이그레이션 순서 강제** — ① 더하기(검색 서술 신설, summary 불변) ② 수치 게이트(FR-006) ③ 빼기(summary 다이어트). 게이트 통과 전 summary 축소 착수 금지.
- **FR-006**: **수치 게이트(위험질의 한정)** — [현행: 요약+코드 원문 180자] vs [신규: 요약+검색 서술(코드 원문 제외)] 임베딩 재료를 **위험질의 세트**(골드셋 중 과거 실패했었거나 코드 원문 목발로 겨우 건졌던 민감질의: 결제망·정산·주문취소 등 소수)로 비교 측정하고, 신규가 위험질의 정답 유실 0일 때만 통과로 판정한다. **골드셋 전체 전량 측정은 하지 않는다**(질의 많으면 과다 소요 — 사용자 지시 2026-07-09). 미달 시 실패 질의 부검→생성 규칙 개선을 반복한다.
- **FR-007**: **위험 최소화 파일럿** — 전량 재분석 전에 소수 대표 노드만 새 규칙으로 재분석해 ⓐ 서술 품질을 원문 소스와 정밀 대조 ⓑ 위험질의(결제망·정산·주문취소)만 재검색해 정답 유실 0을 확인한 뒤 전량 재분석으로 확대한다.
- **FR-008**: **summary 다이어트** — 게이트 통과 후 summary를 통상 1~2줄, 코드 용량·내용에 비례해 **최대 3줄 마지노선**으로 축소한다. 성의 없는 한 줄 달랑은 금지(단순 노드도 "무엇을 어디에 하는지"는 담아야 함). 분기·코드값 세부는 검색 서술로 이관하고 요약에서 중복하지 않는다.
- **FR-009**: **2섹션 마커 정리** — 다이어트로 `[핵심]`+내용 2섹션 구조가 소멸하므로 마커 처리(제거 또는 유지)를 확정하고, ⓐ 산출 형식 검증 규칙 ⓑ 프론트 요약 표시(첫 문단 분리 방식) 양쪽이 확정안과 정합하게 동작함을 보장한다.
- **FR-010**: **상향 분석 입력 무회귀** — summary는 자식→부모(호출자) 상향 분석의 입력이므로, 다이어트 후에도 부모 노드 분석 품질이 유지되도록 자식→부모 전달 재료를 재정의하고(다이어트 요약 그대로 또는 검색 서술 병용) 실제 분석 실행으로 검증한다.
- **FR-011**: **편애 0** — 신규 임베딩 재료(검색 서술 기반)는 이득이 수치로 입증되기 전 기본 채택하지 않으며, 현행 재료와의 ablation 비교로 승자를 선정한다. 진 결과도 측정 장부에 그대로 기록한다.

### Key Entities

- **코드노드 분석 산출물**: 코드노드(함수/실행문)마다 LLM이 생성하는 의미 정보 묶음 — 요약(summary), 역할 라벨(stereotype), 도메인 표시명(logical_name), 그리고 이번에 신설되는 검색 전용 서술.
- **검색 전용 서술 (가칭 search_text)**: 조건분기·상태전이·상태코드·테이블 상호작용의 자연어 융합 서술. 프론트 비노출. 소비처 = 임베딩 검색·재순위·용어집 생성. 요약과 같은 분석 호출에서 함께 생성(호출 횟수 증가 0).
- **골드셋·위험질의 세트**: 골드셋 = 놀이터의 질의→정답 노드 검증 자산(쇼핑몰 30문항·SKT 23문항). **위험질의 세트** = 그중 과거 실패했었거나 코드 원문 목발로 겨우 건졌던 민감질의(결제망·정산·주문취소 등 소수) — 이번 게이트 판정은 이 세트만 사용(정답 노드 회수율, 판정 변동 0). 전량 측정은 수행하지 않음.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 신규 임베딩 재료(코드 원문 제외, 요약+검색 서술)로 **위험질의 세트** 정답 회수가 현행과 동등 이상(유실 0) — 전체 골드셋 전량 측정은 판정 요건이 아님.
- **SC-002**: 파일럿 단계 위험질의(결제망·정산·주문취소) 재검색에서 기존 정답 유실 0.
- **SC-003**: 다이어트 후 전 노드 summary가 최대 3줄 이내이고, 표본 원문 대조 검수에서 "무엇을 하는지" 파악에 충분하다고 판정된다(한 줄 달랑 0건).
- **SC-004**: 프론트 화면 변경 0으로 기존 표시가 전부 정상이며, 검색 서술은 어떤 화면에도 노출되지 않는다.
- **SC-005**: 분석 비용 — LLM 호출 횟수 증가 0(기존 호출에 출력 필드만 추가), 노드당 출력 토큰 증가는 소폭(수십 토큰 수준)에 그친다.
- **SC-006**: 검색 결과 뭉치의 크기·정밀도(precision) 지표가 현행 대비 무회귀 또는 개선.
- **SC-007**: 상향 분석 품질 무회귀 — 다이어트 후 재분석에서 부모 노드 요약·비즈니스 규칙 산출물이 표본 원문 대조에서 다이어트 전과 동등 품질로 판정된다.

## Assumptions

- **필드명은 가칭(search_text)** — 확정 명칭·저장 위치는 계획(plan) 단계에서 정한다.
- **`[핵심]` 마커는 다이어트(US3) 시 제거 — 사용자 확정(2026-07-09)**. 근거: 요약 전체가 곧 핵심이 되어 2섹션 구조가 소멸하고, 프론트는 마커 텍스트를 파싱하지 않아(첫 문단 분리 방식) 무영향. analyzer 형식 검증은 **결정론 정규화**(마커 벗김 + 3줄 초과 절단, 실패 없음)로 교체 — 거부 방식은 재시도 부재 구조에서 노드 분석 유실을 일으켜 기각(research D7 개정, 실측 근거).
- **spec 040 supersede (부분)** — spec 040-rules-node-gate FR-005·AC는 "`[핵심]` 한 줄(UI용) 보존"을 요구하나, 실측 결과 프론트는 마커를 파싱하지 않으므로(NodeDetailBase 첫 문단 분리) 그 "UI 계약" 전제는 성립하지 않는다. 이 스펙은 040의 **`[핵심]` 마커 유지 조항만** supersede한다(040의 노이즈 제거·값 보존 취지는 계승 — 다이어트가 더 강하게 달성). 040 문서는 역사기록으로 보존.
- **module_summary(ModuleSummaryOutput)는 범위 밖** — 모듈 개요(~2단락)는 코드노드 요약과 다른 산출물·소비처라 이번 다이어트·마커 제거 대상 아님(별도 유지).
- **검색 서술은 기존 요약 생성 호출(분할 1)에 출력 필드를 추가하는 방식** — 별도 호출 신설 없음(비용 전제).
- **측정 인프라는 놀이터(임베딩서칭) 자산 재사용** — 골드셋·상시 측정기(질의 부분집합 실행 지원)·임베딩 재료 전환 토글. 놀이터의 그래프 접근은 읽기 전용(재분석 쓰기는 analyzer 실행이 담당하며, 실행 정책상 전체 재구축).
- **위험질의 세트 선정은 계획(plan) 단계에서 측정 장부 근거로 확정** — 과거 실패 이력(결제망 0/2→2/2 구제 등)·코드 원문 의존이 실측된 질의(코드 제외 시 정답 유실이 관찰된 질의)를 우선 포함. 전체 골드셋 전량 측정은 하지 않는다(사용자 지시 2026-07-09 — 질의 많으면 과다 소요).
- **재분석 대상 = 놀이터 두 그래프**(쇼핑몰 데모·SKT 자동납부). 운영/타 그래프 재분석은 범위 밖.
- **프롬프트 수정은 KV 캐시 계약 준수** — 3분할 공통 시스템 프롬프트의 byte-identical을 깨지 않도록 공통 수정은 단일진실 지점에서만(analyzer 헌법 V).
- **교차 서비스 영향**: 그래프에 속성 1개 추가는 부가적(additive) 변경 — 하위 소비 서비스(robo-architect·프론트·카탈로그)의 계약 변경을 요구하지 않는다는 전제. 단 summary 다이어트는 summary 소비처 전수조사 후 진행(Edge Case 참조).
- **프론트 요약 표시 개선(다이어트 반영 UI)은 후속 스펙** — 이 스펙은 "프론트가 깨지지 않음"까지만 보장.
