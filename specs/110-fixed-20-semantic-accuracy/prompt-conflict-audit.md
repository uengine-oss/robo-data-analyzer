# 프롬프트·로직 원인 감사

이 문서는 고정 20개 전 속성 직접 판정에서 발견한 실패를 특정 코퍼스용 예외가 아니라
최초 실패 단계와 공통 책임 충돌로 분류한다. 직접 판정이 끝나기 전 수치와 원인군은
잠정값이며, 같은 20개 재실행으로 수정 효과를 검증한다.

## 판정 원칙

- 의미의 정답은 활성 원문과 고정 골드의 원자 의무를 사람이 직접 대조해 판정한다.
- 문자열 유사도, 별도 LLM judge, 재작성 LLM, 반값/fallback 결과는 정확도 판정에 쓰지 않는다.
- 결정론 로직은 입력 조립, 닫힌 값 검증, 근거 보존, 병합·저장 무결성만 담당한다.
- 프롬프트는 사례별 정답을 넣지 않고 모든 언어·도메인에 적용되는 증거·소유권·필드 책임만
  규정한다.
- 상한은 의미 목표가 아니라 구조 폭주 비상 경계다. 누락을 상한으로 숨기지 않는다.

## 확인된 상호충돌

### C1. 자연어화와 정확한 계약 복원의 충돌

Framework 공통 system은 `summary·이름·설명·Rule·Example`에서 물리 변수명·함수명·
매크로명을 노출하지 말라고 한다. 반면 Rule/Example 계약은 조건 필드, 값 매핑, 직접 호출,
조회 키, 테이블을 정확히 복원하라고 한다.

이 충돌은 모델이 긴 함수에서 어느 조건의 어느 값을 말하는지 지우게 만들며, 실제 출력에서
skip flag/reason, 호출별 결과 코드, 필드별 필수 조건이 소실된 사례와 맞닿는다.

수정 방향은 필드별로 경계를 분리한다.

- `summary`, `logical_name`, 일반 설명: 업무 자연어 중심
- `search_text`: 검색을 구별하는 실재 식별자와 대표 조건·결과 쌍 보존
- `Rule`, `Example`: 자연어를 기본으로 하되 조건·결과·대상·호출을 구별하는 데 필요한
  원문 식별자는 괄호로 보존
- 내부 임시변수·매크로·한 줄 구현의 무의미한 나열은 모든 필드에서 금지

### C2. Rule 경계의 상충

공통 Rule 계약에는 “관측 결과가 다르면 분리”와 “있으면 갱신, 없으면 생성 같은 완결된
분기쌍은 한 Rule”이 함께 있어 기준이 모호하다.

통일 기준은 다음 하나다.

- 동일한 업무 판단축에서 상호배타적인 조건→결과의 **완전한 매핑**은 한 Rule로 둘 수 있다.
- 독립적으로 적용되는 단계, 서로 다른 시점의 효과, 별도 종료 계약은 다른 Rule이다.
- 한 Rule로 묶었다면 statement만으로 모든 조건→결과 매핑을 복원할 수 있어야 한다.
- Example은 Rule을 검증할 뿐, Rule에 없는 정책의 저장소가 아니다.

### C3. 반복 지침으로 인한 우선순위 희석

Rule 계약과 Framework 제출 직전 감사가 CONTROL/GUARD/DATA/CALL, 분기 회계,
Example 개수, 완전한 매핑을 여러 번 반복한다. 내용 일부는 표현이 달라 모델이 독립 지침으로
해석할 수 있다.

수정은 하나의 순서로 계층화한다.

1. 활성 SOURCE의 관측 의무를 CONTROL/GUARD/DATA/CALL로 회계
2. 업무 판단축과 종료 계약으로 Rule 경계 결정
3. statement에 전체 조건→결과 매핑 작성
4. 필요한 최소 Example 작성
5. 실제 외부 정보 공백만 Question 작성

### C4. domain_terms 상한의 목표값 앵커링

현재 계약은 `10`을 비상 상한이라고 말하면서 제목·본문·경계 예시에서 반복한다. 실제 결과는
일부 함수가 정확히 10개를 채우며 함수·테이블·변수·상수를 표제어로 만들었다.

수정은 후보 자격을 먼저 판정하고 상한을 마지막에 한 번만 제시한다. `0개`를 정상으로
명시하며, 표기와 뜻을 함께 입증하는 원문 구절이 없으면 후보를 만들지 않는다.
결정론 후처리는 실제 구조 입력에서 확정된 함수·테이블·컬럼 ID와 정확히 같은 후보만
구조 사실로 제거할 수 있고, 식별자 모양을 정규식으로 의미 판정하지 않는다.

### C5. 생성하지만 소비하지 않는 Component 필드

`ComponentNamingOutput`은 `name`, `description`, `stereotype`을 생성하지만 저장 경로는
`name`만 소비한다. 정확도를 측정하거나 저장하지 않는 두 필드는 dead output이다.
또 component naming 로그의 `target_id`가 `unknown`이라 원인 추적이 끊긴다.

소비 계약을 새로 만들 근거가 없으므로 현재 요구에는 이름만 생성하도록 축소하고,
실제 `component_id`를 호출 추적 ID로 전달하는 방향을 우선 검토한다.

## 아직 확정할 항목

- 219개 Rule/Example 의무의 직접 판정과 추가 출력의 Faithfulness/Extra
- FILE 23, TABLE 7, COLUMN 36 및 모듈·컴포넌트·용어 최종 산출물
- 각 실패의 최초 단계: prompt input / response / parser / merge-filter / graph write
- whitespace flood guard의 현재 동작과 서버 constrained JSON 옵션의 저장소 밖 운영 경계
- 직접 정확도와 cap-hit를 함께 본 Rule·Example soft 권고 및 hard emergency cap
