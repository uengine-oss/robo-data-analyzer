# 090 — 노드 내부 3분할 동시 발사 (#1 을 기다리지 않는다)

작성: 2026-07-23. 근거: 배치 실험(spec 087)이 준 교훈의 역방향 적용 — **이 워크로드는
스트림이 많을수록 이득**이므로, 노드 안에서 만든 직렬 구간도 손해다.

## 원인

`analyze_code_three_split` 은 `#1 요약` 을 await 한 뒤 `#2 테이블통찰 ∥ #3 규칙` 을 발사했다.
이유는 KV 프리픽스 캐시 워밍(#1 이 공통 프리픽스를 올리면 #2·#3 이 적중)이었다.

그러나 **#2·#3 은 #1 의 결과를 입력으로 쓰지 않는다**(입력은 `common` / `rules_values` 뿐).
그리고 콜 시간의 97%가 decode 라 prefill 절감은 2~3%에 불과하다(spec 086). 즉 캐시 워밍으로
아끼는 것보다 노드 내부 직렬로 잃는 것이 훨씬 크다.

## 파일럿 (실제 프롬프트 16노드, 동일 입력, 노이즈 통제)

| 방식 | 벽시계 |
|---|---:|
| 직렬(#1 → #3) | 32.8초 |
| **동시(#1 ∥ #3)** | **20.7초** |
| 직렬 재측정 | 28.0초 |

동시/직렬(평균 30.4초) = **0.68 — 32% 단축**. 재측정으로 서버 변동을 통제했다.

## 계약 (변경 후)

- `#2·#3` 을 먼저 `ensure_future` 로 띄우고 `#1` 을 그 옆에서 진행한다. 프롬프트·입력값이
  그대로이므로 **산출물 불변**.
- summary 실패로 노드를 포기할 때는 `_drop_pending()` 으로 `#2·#3` 을 취소·수거한다
  (고아 태스크 금지). `BudgetExceededError` 경로도 동일.
- `on_summary_ready`(spec 082 조기 해제)는 종전대로 `#1` 확정 직후 호출된다.
