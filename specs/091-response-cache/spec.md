# 091 — LLM 응답 콘텐츠 해시 캐시

작성: 2026-07-23. 근거: 딥리서치 2차의 2순위 권고. 두 문제를 한 장치로 푼다.

## 왜 필요한가

1. **재현성(사건 G)**: 서버가 배치 크기에 따라 같은 입력에 다른 출력을 낸다 — 실행마다
   규칙 수가 ±3% 흔들린다(876~899). `temperature 0.1·top_k 1` 로는 못 막고, 서버측
   `--enable-deterministic-inference` 는 우리 권한 밖이다. **캐시는 이 문제를 클라이언트에서
   끝낸다** — 한 번 나온 답이 그 입력의 답이 된다.
2. **재실행 비용**: 공유 GPU 서버 처리량이 시간당 30% 흔들려(16:20 2,056 → 18:09 1,242
   토큰/초) 우리 코드와 무관하게 실행 시간이 널뛴다. 캐시는 **서버 상태와 무관하게** 재실행
   비용을 없앤다.

## 계약

- 키 = SHA256(rule_name + system_prompt + user_content + model + max_tokens + 응답 스키마명).
  **모델에 실제로 보낸 것 전부**다. 프롬프트가 곧 키라서 코드·프롬프트가 바뀌면 그 함수만
  자동으로 미적중된다 — **별도 무효화 로직이 없다**(있으면 그게 버그의 원천이 된다).
- 값 = 파싱된 산출물(`model_dump`). 읽을 때 같은 스키마로 `model_validate`.
- 위치 = `ROBO_DATA_DIR/.llm-cache/<앞2자>/<키>.json`. 프롬프트가 코퍼스 내용을 품으므로
  코퍼스와 수명을 같이하고 저장소를 오염시키지 않는다.
- 통합 = `run_yaml_rule` 진입 직후 조회, 파싱 성공 후 적재. 적중 시 `cache_hit` 로그
  (조용한 동작 금지).
- 실패 정책 = 읽기 손상·스키마 불일치·쓰기 실패는 **경고 후 미적중으로 강등**. 캐시 때문에
  분석이 죽으면 안 된다.
- 킬스위치 = `ROBO_LLM_RESPONSE_CACHE`(기본 ON).

## 정직 고지 — 무엇을 개선하고 무엇을 개선하지 않는가

**첫 분석(콜드) 시간은 줄지 않는다.** 캐시는 재실행을 없앤다. "첫 실행 10분" 목표를 캐시로
달성했다고 보고하면 안 된다. 다만 실무에서 분석기는 같은 코퍼스를 반복해서 돌리고(설정 조정·
프롬프트 개선·부분 수정), 그 경우 이 장치가 지배적이다. 그리고 **재현성 개선은 첫 실행에도
즉시 적용된다** — 두 번째 실행부터 산출물이 흔들리지 않는다.
