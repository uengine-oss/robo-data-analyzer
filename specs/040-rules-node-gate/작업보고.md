# DBMS 비즈니스 규칙 추출 재설계 — 작업보고

> **2026-07-08 · robo-data-analyzer · DBMS(PL/SQL) 전략의 비즈니스 규칙(RULE)·시나리오(EXAMPLE) 품질**

**한 줄 요약:** 레거시 DB 프로시저에서 뽑은 "비즈니스 규칙"의 품질 문제는 **프롬프트(AI 지시문) 수정만으로 해결되지 않는다 — 파이프라인의 근본 구조 문제**임을 원문 대조로 확정하고, 구조를 고치는 확정 솔루션을 설계했다.

---

## 1. 배경 — 우리가 뭘 하려는 건가

이 시스템은 **레거시 코드(DB 프로시저·함수)를 읽어 "비즈니스 규칙"을 자동으로 뽑아** 설계 그래프로 만든다.
예: `FN_EDIT_YN` 함수 → "시간자료(60)이고 공급량·적산차가 아니면 수정 가능(Y)" 같은 **업무 규칙**을 추출.

**문제:** DBMS(PL/SQL) 전략에서 이 규칙 품질이 나빴다.

| 증상 | 예시 |
|---|---|
| 과추출 | 125줄 함수 하나에 규칙 26개 |
| 파편·중복 | 한 결정이 여러 노드에 쪼개져 중복 |
| 환각 | 주석처리된 **죽은 코드**를 실제 동작으로 오인 |

**앞선 시도(이미 완료):** 프롬프트를 4번 강화·재작성했으나 **과추출/파편/중복은 4번 다 실패.**
→ 원인 = **추출 "단위"의 문제**. 그래서 규칙 추출 단위를 바꿨다:

```
  [옛날]  문장 하나하나 쪼개서 규칙 → 자식 규칙을 부모로 합침  →  파편·중복 (RULE 244개)
  [현재]  루틴의 "톱레벨 문장" 통째로 규칙 (레벨1)            →  파편·중복 해결 (RULE 38개)
```

**이번 세션의 목표:** 이 "레벨1" 구조가 **정말 완전한지** 원문과 1:1 대조로 검증.

---

## 2. 검증 방법 — 원문에서 "정답지"를 만들어 대조

매번 원문을 다시 읽으면 비효율적이라, **RWIS 9개 파일 원문에서 비즈니스 규칙 "정답지"를 1회 작성**하고
(→ `answer_key.md`), 이후엔 **정답지 ↔ 그래프**만 비교했다.

---

## 3. 원인 — "프롬프트만으론 안 된다"를 실측으로 확정

정답지와 대조하니, 레벨1로 파편·중복은 잡았지만 **새로운 4가지 문제**가 드러났다.
그리고 그 원인은 **전부 프롬프트가 아니라 구조에 있었다.**

### 🔴 문제 ① — 반복문(LOOP)에서 규칙이 뭉개짐 (과소추출) · 최우선

| 파일 | 톱레벨 문장 | 뽑힌 규칙 | 정답지 대비 |
|---|---|---|---|
| `MINUTE_2` | **LOOP**(반복문) | **1개** ❌ | 6개 결정인데 **일데이터 생성 등 손실** |
| `DATA_ANALYSYS` | LOOP(반복문) | 3개 ✅ | 정상 |

**같은 LOOP인데 왜 하나는 성공, 하나는 실패?**

- `IF` 문장 = **결정 하나** → 규칙 하나. 맞다.
- `LOOP` = **결정 하나가 아니라 여러 작업이 담긴 "그릇"** (적산차 재계산 + 일데이터 생성 + …)
- `MINUTE_2`의 LOOP는 **175줄에 SQL이 깊게 중첩** → AI에게 통째로 던지니 **압도돼서 "1개"로 뭉갬**
- `DATA_ANALYSYS`의 LOOP는 안이 단순 → AI가 3개 다 봄

> **핵심:** AI에게 주는 재료가 "175줄짜리 날 것(RAW) 덩어리"라서 뭉개진다.
> **프롬프트로 "다 뽑아라" 다그쳐도, 재료 자체가 감당 안 되면 못 이긴다.**

### 🔴 문제 ② — 커서(cursor)의 검증 규칙이 아예 사라짐

커서 = "조건에 맞는 데이터만 골라내는 조회". `MINUTE_2`의 커서는 **"적산·적산차가 불일치인 날짜만 골라낸다"** 는 진짜 비즈니스 규칙을 담고 있다.

**실측:** 커서 노드 5개 **전부 요약·규칙 0개.**
**원인:** 커서를 **단순 "변수 선언"으로 취급**해 분석 대상에서 **통째로 제외.** → 프롬프트로는 손도 못 댐(재료에 아예 없으니까).

### 🔴 문제 ③ — 죽은 코드(주석)를 사실로 환각

`TB2`에서 활성 코드는 **단순평균**인데, 규칙은 **"대수평균으로 계산"** 이라고 나옴.
→ **주석처리된 죽은 코드**의 수식을 실제 동작으로 오인. (원인 = 규칙 추출만 원문을 다시 잘라 써서, 버려진 주석이 되살아남.)

### 🔴 문제 ④ — 값 매핑이 뭉개짐

`TB2` 규칙이 **"Q/S/D는 집계 처리"** 로 뭉개서, **Q=평균 / S·D=합산** 구분(중요한 계산 정의)을 잃음.

### 종합 진단

> **문제 4개의 뿌리는 프롬프트가 아니라 "AI에게 주는 재료와 분석 구조"다.**
> - RAW 175줄 → 뭉갬(①)
> - 커서 제외 → 손실(②)
> - 원문 재슬라이스 → 죽은코드 환각(③)
> - RAW 요약 → 값 손실(④)
>
> **= DBMS 근본 구조 문제. 프롬프트 수정만으로는 못 고친다.**

## 4. 해결책 — 구조를 고친다 (확정)

핵심 아이디어 하나로 수렴한다:

> **AI에게 "175줄 날 것"이 아니라, "이 문장이 하는 일들의 깨끗한 목록(결정 지도)"을 주고,
> 목록 항목마다 규칙 하나씩 뽑게 한다.**

이걸 뒷받침하는 결정적 실측: **LOOP 아래 각 작업(적산차 재계산·일데이터 생성)은 이미 요약이 다 달려 있다.**
즉 **결정들은 이미 존재**하는데, RAW 1콜이 **열거를 못 했을 뿐**이다. 그 요약들을 지도로 주면 끝.

### 뿌리 B — 재료를 바꾼다 (RAW → compact "결정 지도")

```
[지금]  LOOP ─→ AI에게 175줄 날 것 통째        →  뭉갬·환각·값손실
[해결]  LOOP ─→ AI에게 자식 요약 지도:
                [116~224] 적산차 재계산 …
                [234~264] 일데이터 생성(Q=평균/S·D=합산) …   →  항목마다 규칙 하나
```

- ① 과소추출 해결 (지도라 열거만 하면 됨)
- ③ 죽은코드 환각 해결 (요약은 주석이 없음)
- ④ 값 매핑 유지 (요약이 값을 담음)
- 덤: **거대 프로시저(1000줄+)도 크기 안전**(요약이라 안 터짐)

### 뿌리 A — AI 지시문(프롬프트)을 새 구조에 맞게

- **버림:** "각 노드 = 완결된 문장 하나" (← 이 말이 AI를 뭉치게 함)
- **넣음:** "노드에 결정이 **여러 개일 수 있다. 반복문·여러 작업 든 블록은 작업마다 규칙 하나.** 규칙 6·8개도 정상."
- **명확화:** "폭주 금지 = **같은 결정 중복 금지**"이지 "규칙을 적게"가 아님. "순수 조회·로그·커밋은 규칙 아님(⑤)."

### 커서 — "별도 처리"가 아니라 "제외를 제거"

- 커서를 **분석 대상 문장에 포함** → 다른 문장과 똑같은 파이프라인으로 **요약·규칙 자동 생성.**
- 인라인·짝짓기·타이밍 처리 **전부 불필요** (커서가 자기 규칙을 자기 노드에 가짐).
- 원칙에 부합: 특수처리 **추가**가 아니라 잘못된 **제외 제거** → 로직이 **더 깨끗해짐.**

### 요약 조이기 (compact가 깨끗하려면 필수)

- **유지:** `[핵심]` 한 줄(UI 표시용) + 값·"어느 테이블에 무슨 작업(읽기/쓰기/집계)"
- **제거:** 커밋/롤백/예외 반복, 코드 토큰(테이블·변수명), 장황한 산문
- 실측: 현재 요약 최대 860자·200자 초과 107개 = **대부분 노이즈**(알맹이는 그 안에 묻힘)

### 원칙 관점 — 근본수정인 이유

```
  이슈 ①②③④⑤ + 로드맵(compact·요약조이기)  →  뿌리 2개 + 요약조이기 로 수렴
```
분기·특수케이스가 **늘어나는 게 아니라 하나로 합쳐진다** = 땜빵이 아닌 구조 정리.

## 5. 검증 근거 (실측 데이터)

- **정답지 대조:** RWIS 전체 RULE 38개, 파일별 위치 확인. `MINUTE_2`만 명확한 과소추출.
- **커서:** CURSOR_VARIABLE 5개 전부 요약·규칙 0 (선언 취급 확정).
- **결정은 이미 있음:** `MINUTE_2` LOOP 아래 DML(MERGE 등) **전부 요약 보유** — 예 MERGE[234-264]="일별 집계를 일보에 반영"(=정답지의 일데이터 생성).
- **요약 노이즈:** 435노드 중앙 144자·**최대 860자**·200자 초과 107개 + 코드토큰 누출.
- **죽은코드:** `TB2` 규칙에 '대수평균'(주석 속 죽은 수식) 실측.

## 6. 구현·검증 결과 (최종 — 6회 재분석 실측)

```
 ① 정답지 작성 ..................... ✅ (answer_key.md)
 ② spec 040 갱신 ................... ✅
 ③ 코드 수정 ....................... ✅ 전부 구현 (미커밋)
     · 재료: RAW → compact + 자식 타입 명시([범위] TYPE: 요약)
     · 커서: 분석 포함(제외 제거) — 자기 규칙을 자기 노드에
     · 골격 주석 스트립(결정론) — 죽은코드 공급로 원천 차단
     · 규칙 프롬프트 재탄생(발동기준 §2 최대상세 + 전 지침 인라인 범용 예시)
     · 요약 프롬프트: 집합 완전·괄호병기 금지·기술노드 한줄·범용화
 ④ 재분석 → 정답지 대조 (6패스) ..... ✅ 실측 완료
```

**최종 판정 (9패스, 정답지 45결정 채점):**
- **정확도: 엄격 58% → 78% / 부분점수 74% → 86%.** 만점 3파일(FN_CALC·TRG·4RVR), 최난 파일(MINUTE_2) 4/7→6.5/7.
- ✅ **결정적 전환 = "예산 내 원문" 통합 원리**: 요약(전언)을 규칙의 증거로 쓰면 전달게임 손실(F 누락·매핑
  뭉갬 — LLM 입력로그로 실증)이 불가피 → 증거를 **원문(1차)**으로 회귀. 큰 문장만 예산 기준으로 자식 단위로
  쪼개고(descent — 9파일에서 4곳뿐), 쪼개진 컨테이너의 **입구 조건은 전용 게이트 프롬프트**로 회수(4/4 성공).
- ✅ 구조(결정론)가 잡은 것: 파편·중복 0 / 커서 규칙 / 잔심부름 배제 / **죽은코드 환각 0**(지침 25% → 골격
  스트립 100%) / 게이트·음수보정·일데이터·값집합(F)·축 라벨 회수.
- ⚠️ 잔여(~14%) = 소형(36B) 진동: 호출연쇄·전역예외 규칙이 패스마다 있다없다 / 일부 집계방식·축 뭉갬 /
  examples 코드토큰 누출. **후속 레버**: 규칙 분할만 대형 모델 / 사후 결정론 검증.
- **잔여 작업**: FW(zapamcom) 무회귀 재분석 · 그래프 계약 소비처 견적 · ontology `rule_bearing` 제거.

## 부록 — 교훈

- **프롬프트가 아니라 구조가 문제일 때가 있다.** 소형 모델이 못 지키는 판단은 프롬프트로 다그치지 말고, **애초에 그 판단이 쉽도록 재료·구조를 고친다.**
- **개수로 판단하지 않는다.** 기준은 오직 원문(정답지). "적을수록 좋다"는 편향은 위험.
- **검증 효율화:** 매번 원문 재독 대신 원문→정답지 1회 추출 후 그래프와 대조.
