# 085 — 동시 요청 상한을 콜 단위로 옮기기: **기각 (실패 실증)**

작성: 2026-07-23. 결론: **가설 틀림 — 원복함.** 같은 계열 시도를 반복하지 않기 위한 기록.

## 가설

`framework_per_node` 의 세마포어 단위가 코드노드라, 한 노드가 슬롯을 쥔 채 `#2 rules` 와
`#3 insights` 를 동시 발사한다 → 실제 서버 요청이 `상한 × 2 = 128` 로 서버
`max_running_requests`(64)를 초과 → 서버 큐 대기가 개별 콜 지연으로 잡혀 꼬리가
부풀고(run17 실측 p95 97.8초·max 217.1초), 짧은 `#1 summary` 가 굶어 의존 해제가
늦어진다. **콜 단위 상한으로 옮기면 큐 대기가 사라져 빨라질 것이다.**

## 원인 해석

서버는 continuous batching 이라 **큐에 쌓인 요청이 파이프라인을 채우는 버퍼로 작동**한다.
클라이언트가 정확히 64로 조이면 한 응답이 돌아온 뒤에야 다음 요청이 나가므로, 네트워크
왕복과 클라이언트 스케줄 지연만큼 서버가 논다. 즉 **오버서브스크립션은 낭비가 아니라
서버를 굶기지 않는 장치**였다. 큐 대기가 지연 통계에 섞이는 것은 사실이나, 그것이 곧
손실은 아니다.

## 두 번째 시도도 기각 — 깊이 우선 투입 순서 (run19)

첫 실험의 교훈("유휴는 큐가 아니라 의존 사슬 꼬리에 있다")을 따라, 투입 우선순위를
`자기 비용 + 사슬 rank` 합산에서 `(사슬 깊이, 비용)` 사전식으로 바꿨다. 근거는 한 홉이
콜 한 번(p50 30초)이라 깊이가 종료 시각을 지배하고, 합산하면 큰 독립 함수(수백 줄)가
사슬 아래쪽 작은 노드를 밀어낸다는 것이었다.

| 항목 | run17 (합산 rank) | run19 (깊이 우선) |
|---|---:|---:|
| 총 시간 | **11분 16초** | 12분 44초 |
| step7 | **516초** | 589초 |

역시 느려졌다 → 원복. 세 run(17/18/19)의 step7 이 516·660·589초로 흩어지는데, 그중
어느 변경도 원본을 이기지 못했다. **step7 스케줄은 현재 형태가 지역 최적**으로 보이며,
추가 이득은 스케줄 바깥(일량·토큰 속도)에서 찾아야 한다.

## 남는 교훈

- 이 워크로드에서 "클라이언트 동시성 = 서버 상한" 은 최적이 아니다. 초과 발사가 이득이다.
- 스케줄 재배치는 두 방향 모두 손해였다. 스케줄 최적화는 여기서 종료한다.
- 서버 지연 자체가 run 마다 흔들리므로(같은 코드에서 p50 30.2↔34.3초), 스케줄류 A/B 는
  단발 run 으로 판정하기 어렵다. 다음 시도는 효과 크기가 분명한 것(일량 감축·MTP)만 한다.
