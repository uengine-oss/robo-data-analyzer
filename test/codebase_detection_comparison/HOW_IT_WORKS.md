## 1. 이 시스템이 푸는 문제

### 상황

회사에 수천 개 파일로 된 오래된 프로젝트가 있다고 상상하세요. 누가 만들었는지, 어떤 기술로 만들었는지, 데이터베이스는 어떻게 다루는지 기록이 남아있지 않습니다.

**사람이 직접 알아내려면?**
- 모든 파일을 하나씩 열어본다 → 수 시간~수 일
- 아니면 "이 파일 뭐야?" 누구한테 물어보기 → 아무도 모름

### 우리가 원하는 것

경로 하나만 주면, **자연스러운 한국어 한두 문단**으로 답해주기:
- 어떤 언어로 만들어졌는지 (C? Java? Python?)
- 어떤 프레임워크를 쓰는지 (Spring? Django? 이름 없는 독자 프레임워크?)
- 데이터베이스에 어떻게 접근하는지 (SQL 직접? ORM? 특이한 방식?)
- 테이블 이름에 규칙이 있는지

### 조건

- **2000 개 파일을 다 뒤지지 않음** — 그러면 너무 오래 걸림
- **미리 "이런 프레임워크가 있다" 고 알려주지 않음** — 어떤 프로젝트든 동작해야 함
- **20 초 안에** — 사람이 기다릴 수 있는 시간

## 2. 등장 인물 소개

시스템은 크게 **3 명** 의 등장인물이 협업합니다. 수사물 비유로 설명합니다.

### 2.1 탐정 (LLM / GPT-5.4)

- **역할**: 모든 판단을 내리는 두뇌
- **한계**: 직접 파일을 열거나 디스크를 읽지 못함. "보고서" 만 받아서 추리함
- **강점**: 일반 지식 (세계 프레임워크 목록, 프로그래밍 패턴 등) 을 많이 알고 있음
- **실체**: OpenAI API 호출 — `POST /responses` 로 요청, JSON 응답

### 2.2 조수 (파이썬 도구 — quick_collect)

- **역할**: 탐정의 지시로 파일을 열어보고 보고서를 만듦
- **한계**: 판단하지 않음. 기계적으로 수집만 함
- **강점**: 빠름 (0.03 초). 정해진 일을 정확히 함
- **실체**: [collector.py:118 `collect()`](collector.py) 함수

### 2.3 서브조수 (file-tracker)

- **역할**: 조수가 뭘 빠뜨렸을 때, 탐정이 직접 시키는 현장 요원
- **한계**: 파일 2 개 + 검색 1~2 번 만 허용
- **강점**: 특정 단서 하나에 집중해서 깊이 조사
- **실체**: Deep Agent 프레임워크의 서브에이전트 ([agent.py:112](agent.py))

## 4. 단계별 상세 설명

### 4.1 준비 단계 (LLM 호출 없음)

**위치**: [analyze.py:29-36](analyze.py)

사용자가 명령어를 칩니다:

```
python -m test.codebase_detection_comparison.analyze /some/path
```

파이썬이 하는 일:
1. 경로가 실제로 존재하는지 확인
2. `create_agent(root_path)` 호출 → 탐정 객체와 결과 담을 빈 상자(`holder`) 만듦
3. 탐정에게 사용자 메시지 전달

### 4.2 Turn 1 — 탐정의 첫 지시

**위치**: [agent.py:32-61 SYSTEM_PROMPT](agent.py)

탐정(LLM)이 받는 입력:
- "너는 코드베이스 분석 전문가다" 로 시작하는 **역할 지시문**
- 사용할 수 있는 **도구 목록**:
  - `quick_collect` (내가 만든 조수)
  - `submit_report` (최종 답 제출)
  - `read_file`, `grep`, `ls`, `glob` (Deep Agent 가 자동 제공하는 범용 도구)
  - `task` (서브조수 불러내기)
- 사용자 메시지: "이 프로젝트 분석해줘"

탐정이 추론 후 응답:
```json
{"tool_call": "quick_collect", "arguments": {}}
```

*여기서 대략 5 초 소요 — GPT-5.4 추론 시간.*

### 4.3 조수의 수집 작업 (파이썬 코드만, LLM 없음)

**위치**: [collector.py:118 `collect()`](collector.py)

조수가 실행하는 5 가지 작업:

#### ① 확장자 세기

```
폴더 전체를 훑으면서
  - 각 파일의 확장자를 하나씩 꺼내서
  - {'.c': 1, '.py': 0, ...} 식으로 카운트
```

이 결과로 "주요 언어가 C 인지 Python 인지" 짐작.

#### ② 표준 매니페스트 찾기

전 세계 공통 파일 목록 확인 ([collector.py:17-21](collector.py)):
```
package.json, pom.xml, build.gradle, go.mod, Cargo.toml,
requirements.txt, pyproject.toml, Pipfile, Gemfile,
composer.json, Makefile, CMakeLists.txt ...
```

위 파일 중 하나라도 있으면 → 앞 60 줄 복사.
없으면 → 빈 칸 (이 프로젝트는 매니페스트 없음).

#### ③ 설정 파일 찾기

마찬가지로 `application.yml`, `.env`, `settings.py` 같은 표준 설정파일 확인. 앞 40 줄 복사.

#### ④ Import 목록 뽑기

**위치**: [tree_sitter_tools.py:110 `extract_imports_sample()`](tools/tree_sitter_tools.py)

이 단계가 핵심입니다:

1. 주요 언어의 파일을 **랜덤으로 30 개** 고름 (2000 개 다 보지 않음)
2. 각 파일을 **tree-sitter** 라는 범용 파서로 분석
   - tree-sitter 는 130 개 언어를 공통으로 파싱할 수 있는 도구
   - 결과로 **AST (추상 구문 트리)** 를 돌려줌
3. AST 에서 **import / include 노드** 만 골라서 텍스트 추출
   - C 파일이면 `#include <...>` 줄
   - Python 이면 `import ...`, `from ... import ...` 줄
   - Java 면 `import ...;` 줄
4. 전체에서 빈도 세어 상위 20 개 보관

**중요**: 이 과정에 "pfm 이면 ProFrame" 같은 매핑이 없습니다. tree-sitter 는 import 구문을 **언어 문법대로** 찾을 뿐, 안에 든 이름이 뭐든 상관 안 합니다.

#### ⑤ 대표 파일 뼈대 추출

**위치**: [tree_sitter_tools.py:47 `extract_skeleton()`](tools/tree_sitter_tools.py)

주요 언어 파일 중 대표 1 개 선택해서:

1. **파일 앞 주석 블록** 유지 (최대 30 줄) — 파일 맨 위에 대개 설명이 있음
2. **모든 import 줄** 유지
3. **함수/클래스 첫 줄만** 유지 (본문 제외)
4. **매크로 정의** 유지

왜 본문을 제외? → 본문은 구현 디테일. 판단엔 **시그니처** 만 있으면 됨. 덕분에 한 번 볼 때 더 많은 정보 전달.

#### 조수의 최종 산출물

위 5 가지를 템플릿에 끼워 넣어 **한 장의 문자열** 로 만듦.

**위치**: [prompts/analysis_context.txt](prompts/analysis_context.txt)

```
[1] 확장자 분포: {.c: 1}

[2] 매니페스트 (없음): (없음)

[3] 설정 파일 (없음): (없음)

[4] import/include 빈도 상위 20 (파일 1 개 랜덤 샘플):
  #include <pdb_zpay_ap_rltm_auth_hst_u0005.h>
  #include <pdb_zngm_comm_cd_dtl_s0058.h>
  ... (17 줄)

[5] 대표 소스 파일 뼈대 (zapamcom10060.c):
  /*********************************************
   * 1. module 명 : zapamcom10060
   * 5. 호출함수들
   *    1) proframe   : 사용
   *    2) tmax       : 사용
   * ...
   */
  #include <pfmdbio.h>
  #include <pdb_zpay_...>
  ...
  #define ZAPAMCOM10060_DOCU_RCV "ZAPAE0021"
  static long a000_input_validation(...);
  static long b000_main_proc(...);
  static long b100_dbio_comm_cd_dtl_canyn(...);
  static long b200_dbio_rltm_auth_his_i0002(...);
  ...
```

이 문자열이 탐정에게 넘어갑니다. **총 0.03 초**.

### 4.4 Turn 2 — 탐정의 최종 판단

탐정이 위 보고서를 읽고 추리:

> "매니페스트는 없다. 하지만 보고서를 보면:
> - 언어는 C 파일 뿐이니 C 프로젝트다.
> - 주석에 **`proframe : 사용`** 이라고 대놓고 써 있다.
> - `pfmdbio.h`, `pfmerr.h`, `pfmutil.h`, `pfmcom.h` 라는 일관된 접두어 헤더가 반복된다.
> - `#include <pdb_zpay_ap_rltm_auth_hst_u0005.h>` 같은 헤더가 여럿 있고, 파일명이 `s####`, `i####`, `u####` 로 끝난다.
> - 함수 이름이 `b100_dbio_*`, `b200_dbio_*` 로 시작한다.
>
> 종합하면 — ProFrame 계열의 C 프레임워크 + 코드 생성 DBIO 방식이다. 테이블 이름 규칙도 뚜렷하다.
> → 확신 충분. submit_report 호출."

탐정이 자연어 1~2 문단 답안을 `summary` 인자로 제출.

*이 추론에 대략 10 초 소요.*

### 4.5 submit_report — 마무리

**위치**: [agent.py:99-110](agent.py)

파이썬 코드가 실행하는 일:
1. `holder["summary"]` 에 답 저장
2. (캐시 켜져 있으면) `skills/auto_generated/<해시>.json` 에 백업
3. `"submitted"` 리턴 → Deep Agent 가 "끝" 신호로 인식 → 루프 종료

## 5. 왜 20 초 만에 답이 나오는가

### 시간 분해

| 구간 | 시간 | 설명 |
|---|---|---|
| 탐정 1 차 호출 (도구 선택) | ~5 초 | GPT-5.4 추론 포함 |
| 조수 수집 작업 | 0.03 초 | 순수 파이썬, 파일 시스템 읽기 |
| 탐정 2 차 호출 (최종 답 작성) | ~10 초 | 추론 + 긴 문장 생성 |
| 네트워크 왕복 | ~2 초 | OpenAI API 지연 |
| **합계** | **~17 초** | |

### 왜 이렇게 짧은가

**한 번의 "크게 물어보기" 로 충분하기 때문입니다.**

예전에는:
- "파일 목록 봐봐" → 답 듣고 → "어떤 파일 열까?" → 답 듣고 → "그 파일 내용은?" → ...

지금은:
- "자, 확장자 + 매니페스트 + 설정 + import + 뼈대 몽땅 한 번에 줄게. 이거 보고 답해." → 끝

**정보를 쪼개서 여러 번 묻지 않고, 한 묶음으로 전달** 이 핵심입니다.

## 6. 이전 버전은 왜 30 분이었나

### 이전 구조의 문제

```
탐정 → "파일 목록 보여줘"     (LLM 호출 1)
시스템 → ls 실행
탐정 → "이 중 a.py 열어봐"     (LLM 호출 2)
시스템 → read_file
탐정 → "grep "import" 해봐"    (LLM 호출 3)
시스템 → grep
탐정 → "b.py 도 열어봐"        (LLM 호출 4)
...
```

GPT-5.4 는 **추론 모델** 이라 호출 한 번당 수 초~2 분. 10~20 번 왕복하면 30 분.

### 현재 구조

```
탐정 → "quick_collect 해"      (LLM 호출 1)
시스템 → 0.03 초 만에 모든 정보 수집
탐정 → [모든 정보 한 번에 받음] → 최종 답 (LLM 호출 2)
```

**왕복 횟수가 10 분의 1** 로 줄어서, 시간도 10 분의 1 이하.

## 7. LLM 이 "찍은 것" 이 아니라는 증거

가장 의심스러운 부분. "GPT 가 그냥 일반 지식으로 찍은 거 아니야?" 에 대한 답.

### 증거 1: 회사 고유 문자열을 인용함

LLM 의 최종 답변에 다음 문자열이 등장:

- `zpay_ap_rltm_auth_hst`
- `zngm_comm_cd_dtl`
- `b100_dbio_comm_cd_dtl_canyn`
- `_u0005`, `_i0002`, `_s1015`
- `pfmdbio.h`, `pfmerr.h`, `pfmutil.h`, `pfmcom.h`

이것들은 **특정 회사의 내부 테이블 / 함수 이름** 입니다. 인터넷 어디에도 공개된 적 없습니다. GPT 의 사전 학습으로 알 수 없는 값입니다.

→ 이 문자열을 답에 쓰려면 **반드시 실제 파일을 봤어야 함**.

### 증거 2: 경로는 로그에 찍혀있음

HTTP payload 로그 ([스크린샷 생략] — `POST /responses` 요청 본문) 에 quick_collect 결과 전문이 들어가 있습니다. 그 안에 위 문자열들이 그대로 있습니다.

원하시면 `--verbose` 로 실행하여 LLM 이 본 입력을 **한 글자도 빠짐없이** 확인할 수 있습니다.

### 증거 3: ProFrame 이라는 이름은 어디서 왔나

답변에 "ProFrame" 이 나옵니다. 이건 두 경로로 얻은 것:

1. **파일 주석에 실제로 적혀 있음**:
   ```
   * 5. 호출함수들
   *    1) proframe   : 사용
   ```
   이걸 조수가 그대로 복사해서 보고서에 넣었고, 탐정이 봄.

2. **+ LLM 일반 지식**: `pfm*` 헤더 + `proframe` 주석 → "아, 이게 한국에서 많이 쓰이는 ProFrame 이란 미들웨어구나" 연결.

코드 자체에는 `ProFrame` 이라는 문자열 매핑이 없음. 주석에 적힌 글자를 본 것.

### 증거 4: 캐시 없이도 재현됨

```bash
python -m test.codebase_detection_comparison.analyze <path> --no-cache
```

`--no-cache` 로 돌리면 캐시 조회/저장 모두 건너뜀. 그래도 매번 동일 품질의 답이 17~20 초에 나옴 → **로직이 실제로 돌아간다는 증거**.

## 9. 자주 묻는 질문

### Q1. "사전 지식" 이 주입된다는 건 뭘 말하나요?

**답**: 코드 안에 "만약 pfm 이 보이면 ProFrame 이라고 답해라" 같은 조건문을 넣어놓는 것. 지금 코드엔 **없습니다**. 확인 방법:
```bash
grep -rn "ProFrame\|pfm_\|pdb_" test/codebase_detection_comparison/*.py
# → 결과 0 건
```

### Q2. GPT 가 일반 지식으로 답을 "찍는" 것과 "관찰" 의 차이?

**답**:
- **찍기**: "C 파일이 있으면 ProFrame 이겠지" — 근거 없음
- **관찰**: "파일 이름, 함수 이름, 주석을 실제로 읽고 → 그 안의 특이 패턴을 일반 지식으로 해석" — 증거 있음

현재 시스템은 후자. 답변에 **회사 고유 문자열** 이 인용되므로 관찰했다는 증거가 남음.

### Q3. 80 줄이 너무 짧지 않나요?

**답**: 이전 버전은 "앞 80 줄 단순 자르기" 였어서 주석 길면 코드 못 봄. 지금은 `extract_skeleton` 으로 **의미 단위 추출** (import + 함수 시그니처 + 매크로 + 헤더 주석) — 한 파일에서 100+ 개의 의미 단위가 담길 수 있음.

그래도 부족하면? 탐정이 직접 `read_file` / `grep` 을 써서 다른 부분을 더 볼 수 있음.

### Q4. 다른 프로젝트에도 통하나요?

**답**: 통합니다. 어떤 언어든:
- `_ALIAS_EXT_TO_LANG` 에 등록된 확장자면 tree-sitter 파싱 됨
- `WELL_KNOWN_MANIFESTS` 에 있는 매니페스트면 자동 인식
- import 구문은 tree-sitter 가 **범용 노드 타입** 으로 잡음

Python + FastAPI + SQLAlchemy, Java + Spring, Go + GORM 등 다 통해야 함. (ProFrame 한 건 외엔 미검증.)

### Q5. 재현성은 어떻게 보장되나요?

**답**:
- tree-sitter 샘플링은 **시드 42** 로 고정 — 항상 같은 30 개 파일 선택
- 캐시 비활성화 (`--no-cache`) 하면 LLM 만 비결정적 (미묘한 단어 차이는 있을 수 있음, 핵심 결론은 동일)

### Q6. 뭔가 틀린 답이 나오면?

**답**:
- 5 분 타임아웃 안에서 LLM 이 답은 하지만 오답일 수 있음
- 답변에 항상 **관찰 근거** 를 명시하도록 프롬프트로 지시 → 사용자가 근거 읽고 검증 가능
- 근거가 얕으면 "추정" 이라고 적게 되어 있음

### Q7. 2000 개 파일이면 어떻게 처리하나요?

**답**: 변함 없이 빠름. 이유:
- 확장자 카운트: 파일 이름만 봄 (내용 안 읽음) → 0.1 초
- 매니페스트 검색: 이름 매칭 → 0.05 초
- Import 샘플: **30 개만** 파싱 → 2000 개여도 30 개만 고름
- 대표 파일: 1 개만 파싱

2000 개 → 30 개로 줄이는 게 "패턴 기반 표본" 의 핵심.

## 끝으로

이 시스템은 **파이썬의 기계적 수집** 과 **GPT 의 해석** 을 조합합니다.

- 수집은 "어떤 이름을 찾아라" 같은 지시 없이 **범용 문법 기준** 으로 함.
- 해석은 수집된 증거 안에서만 이뤄지며, 답에 **실제 관찰한 문자열** 을 근거로 인용하도록 강제됨.

그래서 어떤 프로젝트를 주든 코드 수정 없이 동작하며, 판단의 근거가 항상 답변에 남아 있어 사용자가 검증할 수 있습니다.
