# BL 검색, 어떻게 해야 정확할까?

> 발표 대본처럼 읽으시면 됩니다. 하나의 질문을 끝까지 따라가면서 모든 기법을 설명합니다.
> 실제 실행 로그: `c:/tmp/bl_search_result.log`

---

## 1. 우리가 풀려는 문제

저희는 코드를 분석해서 Neo4j에 **"업무 규칙"**들을 저장해두고 있습니다. 이걸 저희는 **BL(Business Logic)** 이라고 부릅니다. BL은 "조건 → 상황 → 결과" 형식으로 쓰여 있습니다.

| 구성 | 뜻 | 예시 |
|------|------|------|
| **title** | 규칙의 제목 | "카드 비밀번호가 입력되면 인증여부를 'Y'로 기록한다" |
| **given** | 시작 상태 | "card_pwd_auth_yn 값이 비어있음" |
| **when** | 어떤 일이 벌어지면 | "비밀번호='12'로 등록 요청" |
| **then** | 결과 | "card_pwd_auth_yn='Y'로 저장된다" |

이런 규칙이 지금 테스트 모듈 하나에만 **55개** 있습니다. 실제로는 수백~수천 개로 늘어날 수 있습니다.

**오늘 풀어볼 문제는 이겁니다.**

> 사용자가 평범한 말로 질문했을 때, 수많은 BL 중에서 **정확히 맞는 것만** 어떻게 찾아줄까?

---

## 2. 하나의 질문을 끝까지 따라가 봅시다

오늘 설명은 **이 질문 하나**로 끝까지 갑니다.

> ### 💬 "SKB 은행에서 결과코드 'A002'일 때 오류 메시지는?"

이 질문이 들어오면 어떻게 답을 찾아낼까요? 두 가지 방법을 차례로 보여드리겠습니다.

---

## 3. 먼저, 가장 흔한 방법 — **벡터 검색**

### 벡터 검색이 뭐냐면요

모든 문장을 **숫자 1,536개짜리 좌표**로 바꿔서, 지도 위의 점처럼 펼쳐 놓는 겁니다.

```
BL 55개를 각각 점으로 찍어둠
    ●         ●
      ●  ●  ●
   ●    ●  ●    ●
     ●      ●
       ●  ●
```

질문도 같은 방식으로 점으로 찍은 다음, **가까운 점 10개**를 뽑아 옵니다. 빠르고 (0.3초) 쉽습니다.

### 그런데 이 질문에 돌려봤더니…

벡터 검색이 뽑은 top-10입니다.

```
#1  [0.887] b000: SKB 은행 실패는 전용 오류코드 규칙으로 메시지를 만든다
#2  [0.863] b000: SKB 은행 외부인증에서 허용되지 않은 결과코드는 실패로 반영한다
#3  [0.843] b000: SKB 은행 외부인증은 결과코드 '0000' 또는 '000'만 성공으로 반영한다
#4  [0.824] zapamcom10060: 회사 'B'의 은행 외부인증 결과가 허용코드가 아니면 거부한다
...
#10 [0.753] b000: 카드 등 그 밖의 외부인증은 앞 3자리가 'A00'일 때만 성공이다
```

### 😱 문제가 보이시나요?

정답인 **b800 (생년월일/사업자번호 불일치 → A002 오류메시지 조립)** 이 **top-10에 없습니다.**

왜냐하면 벡터 검색은 단어가 비슷한 걸 찾는 거지, **'A002'라는 코드값에 특별한 의미를 두지 않기 때문**입니다. 그냥 "SKB", "은행", "결과코드" 단어가 많이 겹치는 BL들만 위로 끌어올립니다.

**이게 벡터 검색의 한계입니다.**

- "A002"같이 중요한 **코드값을 놓칩니다**
- "B이면" vs "B가 아니면" 처럼 **조건의 반대를 구분 못 합니다**
- 단어가 겹치면 **내용이 달라도** 상위로 올립니다

## 4. 그럼 어떻게 해결했냐 — **DeepAgent 시맨틱 검색**

똑똑한 검색 전문가 한 명을 붙여뒀다고 생각하시면 됩니다. 이 전문가는 **LLM(gpt-5.4)** 이고, 5개의 도구를 마음대로 쓸 수 있습니다.

| 도구 | 하는 일 |
|------|---------|
| `bl_vector_search` | 의미로 검색 (위의 벡터 검색) |
| `bl_keyword_search` | **정확한 문자열** 검색 — 'A002' 같은 코드값 |
| `get_bl_detail` | 후보의 **GWT 전문**을 다시 읽기 |
| `get_function_context` | BL이 속한 **함수 맥락** 읽기 |
| `select_relevant_bls` | 최종 답 제출 |

그리고 이 전문가에게 **5단계 수사 매뉴얼**을 줬습니다.

> 1. 질문을 분석하고 가설을 세워라
> 2. 여러 방식으로 넓게 훑어라
> 3. 유력 용의자의 전문(全文)을 다시 읽어라
> 4. 부족하면 다른 각도로 재시도해라
> 5. 확실한 것만 제출해라

이 매뉴얼 자체를 시스템 프롬프트에 "반드시/필수"로 박아뒀습니다. LLM은 이걸 따라가면서, **어떤 도구를 언제 쓸지는 스스로 결정**합니다.

이제 전문가가 같은 질문을 받으면 어떻게 답을 찾는지, **실제 로그 그대로** 따라가 봅시다.

## 5. 🔍 전문가의 수사 과정 — 11번의 도구 호출

### 🧠 1단계. 질문을 분석하고 가설을 세운다

전문가가 질문 `"SKB 은행에서 결과코드 'A002'일 때 오류 메시지는?"` 을 받자마자 속으로 이렇게 정리합니다.

```
┌ 핵심 동작 : 오류 메시지를 만든다
├ 대상     : SKB 은행 / 결과코드별 메시지
├ 조건     : 결과코드 = 'A002'  ← 이 코드값은 반드시 키워드 검색할 것
└ 가설(HyDE) : "SKB 은행 연계 처리에서 결과코드가 'A002'이면 해당 코드에
              매핑된 오류 메시지를 설정하거나 조립한다. Given/When에
              결과코드='A002' 조건이 명시되고..."
```

### 🎯 여기서 첫 번째 기법 — **HyDE (Hypothetical Document Embeddings)**

질문은 짧습니다 (**"오류 메시지는?"**). 그런데 정답 BL은 길고 구체적인 서술형 문장입니다 (**"~이면 ~를 조립한다"**). 이 격차 때문에 벡터 검색이 잘 안 맞을 수 있습니다.

그래서 LLM이 **"정답 BL은 아마 이렇게 생겼을 것이다"라고 가상의 답변을 지어냅니다.** 그리고 그 가상 문서로 벡터 검색을 다시 합니다. 질문이 아니라 **답변의 모양**으로 검색하는 겁니다.

### 🔎 2단계. 여러 방식으로 넓게 훑는다

전문가는 세 갈래로 나눠서 동시에 수색합니다.

```
[1] bl_vector_search(원본 질의)
    → "SKB 은행에서 결과코드 'A002'일 때 오류 메시지는?"
    → b000 계열 후보들 반환 (정답 b800 없음)

[2] bl_vector_search(HyDE 가상 문서)   ← 🎯 HyDE 적용!
    → "SKB 은행 연계 처리에서 결과코드가 'A002'이면..."
    → 역시 b000 계열 위주

[3] bl_keyword_search("A002")          ← 🎯 키워드 검색 적용!
    → 🎉 b800_skb_rltm_auth_err_msg_make 발견!
    (이 BL은 벡터 top-10에 없었음 — 키워드 검색이 건져 올림)
```

### 🎯 여기서 두 번째 기법 — **키워드 검색 (벡터의 사각지대 보완)**

`'A002'` 같은 코드값은 벡터가 놓치기 쉽습니다. 그래서 질문에서 **리터럴(구체적 값)** 을 뽑아내서, 그걸 통째로 BL 텍스트 안에서 직접 찾습니다. 이 간단한 기법이 Q5의 **결정타**였습니다.

### 🎯 세 번째 기법 — **다중 전략 + 자율 판단**

세 갈래 검색을 모두 하는 게 아닙니다. **전문가가 질문 성격을 보고 판단**합니다.

- 코드값('A002')이 있다 → 키워드 검색 **필수**
- 질문이 짧다 → HyDE로 확장해서 한 번 더
- 결과가 부족하면 → Step-back(질문을 더 일반화)으로 재검색
- 결과가 충분하면 → Step-back 스킵

지금 이 케이스는 [3]에서 b800이 발견됐으니 Step-back은 **건너뜁니다.** 매뉴얼은 엄격하지만, 상황에 따라 유연하게 작동합니다.

### 📖 3단계. 유력 용의자의 전문을 다시 읽는다

이제 후보가 b000 계열 + b800 까지 여럿 나왔습니다. 여기서 실수하기 쉬운 지점은, **"제목이나 미리보기만 보고 판단"** 하는 겁니다. 전문가는 그 유혹을 거부하고, 상위 후보 5개의 **Given/When/Then 전문(全文)** 을 다시 읽습니다.

```
[4] get_bl_detail(b000 후보1) → "SKB 은행 실패는 전용 오류코드..."
[5] get_bl_detail(b800)        → Given: rltm_auth_rslt_cd='A002' ✅
[6] get_bl_detail(zapamcom10060) → 상위 흐름 BL
[7] get_bl_detail(b000 후보2) → 다른 결과코드 건
[8] get_bl_detail(b000 후보3) → 일반 은행 실패
```

각 후보에 대해 전문가는 속으로 **3요소 매칭**을 체크합니다.

```
b800 :  동작(메시지 조립) ✅   대상(SKB 결과코드) ✅   조건(A002) ✅   → EXACT
b000#1: 동작(메시지 조립) ✅   대상(SKB 결과코드) ✅   조건(A002) ✅   → EXACT
b000#2: 동작(반영여부 판단) ❌ 대상 ✅                조건 ❌           → 제외
```

### 🎯 네 번째 기법 — **후보 검증 (미리보기 금지)**

미리보기로 판단하면 "SKB 관련 BL이니까 맞겠지" 같은 착각이 생깁니다. 전문을 읽고 **3요소 매칭을 엄격히 적용**하는 것이 노이즈를 걸러내는 핵심입니다.

### 🌐 4단계. 함수 맥락까지 확인한다

EXACT 후보가 나왔다고 바로 제출하지 않습니다. 이 BL이 속한 **함수의 역할**까지 확인합니다.

```
[9]  get_function_context(b000_main_proc)
     → summary: "회사='B' 은행 실패 시 b800을 호출하는 메인 흐름"
[10] get_function_context(b800_skb_rltm_auth_err_msg_make)
     → summary: "SKB 실시간 인증 결과별 오류메시지/코드 조립 전담"  ✅
```

b800이 **실제로 SKB 오류메시지 조립을 전담하는 함수**라는 게 함수 레벨에서도 일치합니다. 확정.

### 🎯 다섯 번째 기법 — **함수 맥락 확장**

BL 하나만 보면 속을 수 있습니다. 같은 단어가 다른 도메인에서도 쓰이니까요. 하지만 **그 BL이 속한 함수의 summary, 호출관계, 같은 함수의 다른 BL** 까지 보면 도메인이 명확해집니다. 이건 Neo4j가 그래프 DB이기 때문에 가능한, 벡터 DB만으로는 못 하는 단계입니다.

### ✅ 5단계. 최종 답만 제출한다

```
[11] select_relevant_bls([
  { b800, "EXACT", reason: "Given에 A002 명시, Then에 해당 오류메시지 생성" },
  { b000, "EXACT", reason: "상위 흐름에서 SKB 실패 시 b800 호출하는 동일 규칙" }
])
```

**사용자에게 나가는 최종 답:**

```
✅ [EXACT] b800: 생년월일/사업자번호 불일치 계열 코드는 무인증 오류로 즉시 처리
✅ [EXACT] b000: SKB 은행 실패는 전용 오류코드 규칙으로 메시지를 만든다
```

**정답 2개. 노이즈 0개.**

## 6. 지금까지 쓴 기법 한 번에 정리

하나의 질문을 처리하는 동안, 이 기법들이 **순서대로 자연스럽게** 적용됐습니다.

| 단계 | 기법 | 하는 일 |
|---|---|---|
| 1 | **HyDE** | 질문을 정답 모양의 가상 문서로 바꿔 벡터 검색 |
| 2 | **키워드 검색** | 벡터가 놓치는 코드값('A002')을 직접 매칭 |
| 2 | **다중 전략** | 벡터 + HyDE + 키워드를 상황 맞게 조합 |
| 3 | **후보 검증** | 미리보기 금지, GWT 전문 읽고 3요소 매칭 |
| 4 | **함수 맥락 확장** | BL이 속한 함수의 역할까지 확인 |
| 전체 | **에이전트 자율** | LLM이 11번의 도구 호출을 스스로 설계 |
| 전체 | **Step-back (조건부)** | 결과 부족 시만 질문 일반화 — 이번엔 불필요 |

핵심은 **이 모든 걸 LLM이 매뉴얼에 따라 알아서 한다**는 점입니다. 저희가 "이 질문엔 이걸 써라" 하드코딩한 게 아닙니다.

## 7. 8개 질의로 검증한 결과

같은 파이프라인으로 질문 8개를 돌렸습니다. 실제 업무에서 나올 만한 질문들입니다.

| # | 질문 | 🅰️ 벡터 | 🅱️ DeepAgent |
|---|------|--------|----------------|
| Q1 | 카드 비밀번호가 입력되면? | #1,#2 정답 + 노이즈 8 | **2 EXACT** |
| Q2 | 예금주명이 비어있으면? | **#2가 "있으면"(반대)** 섞임 | **2 EXACT** (반대 제외) |
| Q3 | op_cl='03' EDI 저장? | #1 정답 | **1 EXACT** |
| Q4 | 정상전화여부 코드군? | #1 정답 + b800 노이즈 | **1 EXACT** |
| Q5 | SKB A002 오류 메시지? ⭐ | **정답 top-10에 없음** | **2 EXACT** (키워드로 구제) |
| Q6 | 간편결제사 미등록? | **#2가 "고객번호 없음"(다른조건)** | **2 EXACT** |
| Q7 | 외부인증 '0000' 반영? | 여럿 관련 | **2 EXACT + 2 STRONG** |
| Q8 | 회사구분 'B' 예금주명? | **#1이 "B 아니면"(반대)** | **2 EXACT** (반대 제외) |

### 요약하면

- **🅰️ 순수 벡터: 8문제 중 7문제만 정답 도달** (Q5 실패 — top-10에 정답 자체가 없음)
- **🅱️ DeepAgent: 8문제 전부 EXACT 매칭 성공**
- **반대 조건** (Q2, Q6, Q8) 은 벡터가 **못 구분**, DeepAgent는 **정확히** 구분
- **코드값 매칭** (Q5) 은 키워드 검색이 결정적

## 8. 결론

### 🅰️ vs 🅱️ 한눈에

| 항목 | 순수 벡터 | DeepAgent |
|------|----------|-----------|
| 정확도 (8개 질의) | 7/8 (한 건 누락) | **8/8** |
| 노이즈 | 70~80% | 거의 0% |
| 반대/다른 조건 구분 | ❌ | ✅ |
| 코드값 매칭 | ❌ | ✅ |
| 응답 시간 | 0.3초 | 20~70초 |
| 토큰 | 거의 0 | 80K~150K |

### 한 문장으로 말하면

> **벡터만으로는 부족하다. LLM이 가설을 세우고, 키워드로 사각지대를 메우고, 전문을 읽고, 함수 맥락까지 확인해야 비로소 "정확히 맞는 답"이 나온다.**

### 권장 구조

```
사용자 질문
    ↓
DeepAgent (5개 도구 + 5단계 매뉴얼)
  1. 분석 & HyDE 가설
```
